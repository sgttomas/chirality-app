# DEL-05-01 — Minimal-loop and model receiving contract

## Purpose and Objective Traceability

A host that embeds a Chirality agent runs it on a model the person chose, sends the person's data only where the person allowed, and acts on a model's tool call only when the call arrived whole and fits the host's catalog. This deliverable contributes the App/shared side of that result: the contract a host's minimal loop must meet at its four boundary subjects (messages, tools, events and checkpoints); the fixtures that express the contract; the conformance cases and the checker by which a host's supplied documents and observed behaviour are examined against it; and the account of who builds what. The host builds the loop. This deliverable never does.

It is the DEL-05-01 row of the [accepted decomposition](../../_Decomposition/Deliverables.csv), an API contract in PKG-05, and serves OBJ-004: App/shared host contracts and a coordinated SWBPIPE journey that preserve operation meaning, host authority and recovery. Its sources are [PRD](../../../docs/PRD.md) V4-HOST-01, V4-HOST-02, V4-WF-05, V4-AUT-03, V4-AUT-05, V4-REC-03 and V4-REC-05; [ARCHITECTURE](../../../docs/ARCHITECTURE.md) §4 (V4-ARC-10 to V4-ARC-14 and the properties the host agent must hold) and V4-ARC-20; [HOST_INTEGRATION](../../../docs/HOST_INTEGRATION.md) §1, V4-HI-20, V4-HI-25, V4-HI-30 to V4-HI-33, V4-HI-42, V4-HI-70 and V4-HI-71; and [EXAMINATION](../../../docs/EXAMINATION.md) V4-EXM-23.

## Deliverable Definition — Ontology

- **OUT-001** — The loop receiving contract: the document that states what a host's loop must do at its four boundary subjects and at its model, destination and credential boundary, with the schemas of the two records the checker reads, the received tool call and the destination request. The meanings under *Terms* below bind it; what it proposes beyond them is undecided (TBD-008). It selects no wire field, protocol version, placement or library. Scope: SOW-015, SOW-016, SOW-017, SOW-136 to SOW-142; OBJ-004.
- **OUT-002** — The tool-call and model-interface fixtures: streamed model responses in the shape of the fixture basis, each with the result expected for every call in it, and the model-choice and destination scenarios with their expected contacts, request outcomes and record entries. Each fixture names the catalog edition and the model-interface basis it is written against. Scope: SOW-015, SOW-016, SOW-017, SOW-136 to SOW-140, SOW-142; OBJ-004.
- **OUT-003** — The conformance cases and the checker that applies them: malformed and truncated calls, validation order, destination confinement and recording, key and credential separation, responsiveness and the separation of acts. The checker takes a host's assembled tool calls, its catalog and its destination-request records as supplied and reports, without altering them, which calls are ready for the host's validation and why each other call is refused. Scope: SOW-015, SOW-016, SOW-017, SOW-136 to SOW-139, SOW-141, SOW-142; OBJ-004.
- **OUT-004** — The allocation and open-choice account: for loop construction and placement, streaming and parsing, conversation persistence, native networking and panel assembly, who builds each, what this contract requires of it, which inputs it needs from which owner, and each choice still open with the owner who makes it. It is kept as a part of the contract document, as are the scenario and case definitions of OUT-002 and OUT-003. Scope: SOW-136, SOW-144; OBJ-004.

Terms:

- **Host loop.** The minimal Chirality agent loop a host embeds, over the OpenAI-compatible Chat Completions interface with tool calls. It has host consumers only: the App runs stock Codex and no Chirality loop, and the two model interfaces are never merged, even where one local server serves both. The loop reaches its model through one model-interface boundary, so that another interface or library, Pi's among them, can replace what is behind it. None is a current dependency.
- **Boundary subjects.** Messages, tools, events and checkpoints. A replacement loop conforms when it preserves their meanings; its code shape does not matter.
- **Message.** One item of a conversation, with its speaker and its content, kept in order. A message is associated with its conversation, its run and the run's workflow identity and holding library as `DEL-02-01` defines them. Each turn records the model setting in force, never a key or a sign-in credential. The conversation store is operational state and never the authority for a human act.
- **Tool.** One entry of the catalog edition the host supplies for the embedded surface, as `DEL-03-01` defines an entry. The catalog is the loop's only tool source: the loop invents no tool and reads no tool list from an MCP server or anywhere else. An operation unavailable to the person is unavailable to the agent, with the same reason.
- **Received tool call.** One call as the loop received it from one model response, with its argument text as received. Argument text is never repaired or completed.
- **Validation order.** (1) The call is complete. (2) The operation it names is an entry of the edition offered. (3) Its arguments fit that entry's declared input. Then the call is dispatched to the host's one route, where the host validates it and resolves its treatment. A call that fails any of the three is not dispatched and never reaches the host's validation. A call that passes them is schema-conformant and nothing more: it is not validated, applied or accepted, and it is no human act.
- **Rejection rules.** A call is truncated when its response ended before the call was whole, and malformed when what was received cannot be read as one identified call with its arguments. Either is rejected. A rejected call is a reported failure of that kind, in the loop's events and in the run record. It causes no call on the host's route and is never executed with empty, repaired or completed arguments.
- **Tool-result classes.** Four, never collapsed: (1) a loop-side failure, not dispatched; (2) a host non-success (unavailable, not permitted, not exposed on this surface, refused, error, or destination not allowed); (3) a host outcome as `DEL-03-02` defines it; (4) dispatched with its outcome not observed, reported by the loop as *outcome unknown* with the last observed state. The loop never restates queued as applied, applied as accepted, or a host's refusal as a person's rejection.
- **Dispatch.** Each dispatch carries its origin (agent, embedded channel, conversation, run and workflow identity), the settings version in force as `DEL-04-02` defines it, the requested mode (apply directly or propose), the basis relied on, the catalog edition and entry version offered, and the call correlation identity. The host's route decides the treatment; the loop carries the intent.
- **Event.** What the loop observed or did, with its subject, actor, reporter and evidence. An event is never itself a human act. An event that reports a person's act, a declined act or a proposal decision relays the host's capture record and never comes from model text, a success, a queue position or a receipt. An absent observation stays absent, and events carry references, not copies. Events report what the sources require to be reported or recorded: a turn's start and end, a failed turn among them; a tool call received, rejected or dispatched, and its outcome; each destination contacted, requested, granted, declined or refused; a checkpoint reached and its act requested; and a person's act as the host captured it.
- **Model setting.** One of: local chosen (a model server the person controls); cloud chosen and signed in by OAuth; cloud chosen with a key supplied; cloud chosen with no credential; unconfigured. There is no default and no fallback: no setting is applied for the person, and nothing switches between local and cloud on a failure. Only the person changes the setting, signs in or supplies a key; an agent may ask. With no model selected a run does not start and the person is asked to choose. With a cloud model and no credential no request is made and the turn fails. "Local" is the person's label for the service they chose and never a test of where it runs.
- **Destination rules.** A destination is a category (web access, MCP servers, other APIs; the list is open) and, within it, a named destination. A contact is allowed when it goes to the selected model service or, for a cloud model, its sign-in service, both allowed by the person's model choice; when its category is switched on; when it is a named entry, which is allowed on its own whether or not its category is on; or when a grant made during work covers it. Analytics or usage reporting, a silent switch of model or provider, and background downloads or updates stay off unless the person turns them on. An MCP server is allowed only if it follows the stateless MCP revision 2026-07-28; one that does not is not offered and cannot be allowed by list or by grant.
- **Native layer.** The host's own layer through which every request of the loop passes. It is the enforcement point: it allows only what the destination rules allow, refuses the rest with nothing sent, records every destination contacted with its category and the grant or list entry that allowed it, and holds any key or sign-in credential where the interface's script cannot read it.
- **Destination request.** The agent's request during its work, made through the host's destination-request entry (`DEL-03-01`), for a destination or category that is not allowed. Only the person grants, once, for this run or always, for the destination or its category; the agent never grants itself a destination and never edits the list. Only the requesting call, the one that needs the destination, waits, and other work continues. A decline is reported to the agent as "destination not allowed by the person". Silence is never a grant.
- **Failed-turn closure.** When a turn is observed to fail, only the still-unanswered destination requests bound to that host source, conversation, run and turn close, as unanswered at end with the cause "turn failed". Nothing is granted, no call waiting on that permission is dispatched, and no later answer in that turn is taken. Outcomes already dispatched stay as observed or unknown. Where the binding is ambiguous, permission is withheld and a limit is reported.
- **Outside process.** An MCP server or other process the host starts for the agent. Unless it is sandboxed, the host can only decide whether to start it and record the destinations it declares, with the limit "process network not observed". Nothing claims it contacted only what it declared.
- **Checkpoint at the loop.** The loop evaluates each declared checkpoint's reached-when only against events it observed, never against model text. On a match it records the arrival with the subject bound by its declared subject class, its purpose and its scope. In the current phase it holds no call, stops no run and reports no workflow unsupported because a hold cannot be enforced. The agent carrying out the workflow asks the person for the act; the loop records that request where it can be identified, and the act only when the host's capture shows the person performed it. For a workflow that takes up the governance phase, the loop holds as `DEL-02-03` defines.
- **Acts at the loop.** The act kinds are `DEL-04-01`'s. The loop may emit a dispatch and "queued" for a proposal, "applied" with its branch and receipt, examination findings (never "checked"), and relayed acts with their actor, recorder and capture-evidence reference. It creates none. A host has no classifier permission mode and the loop presents no tool-permission prompt; a destination request is the agent's request answered by the person's grant, not a tool permission.
- **Fixture basis.** FB-CC-1: the published OpenAI OpenAPI specification `openapi.yaml` of `openai/openai-openapi`, `info.version` 2.3.0, SHA-256 `976053bfe228984127c1c4def7cb9fe0810252adbd8c41651812f68beb6426ad`. It is a fixture basis and not a product selection: it selects no provider, server, model or version for any host, and no host is claimed to follow it.
- **Evidence kinds.** `DEL-03-01`'s three: illustrative (the contract reviewed), test-double (a fixture run on scripted stand-ins) and actual host (observed on an identified candidate). What was not observed is recorded as a gap.

Boundary:

- **CLM-001** — The App/shared embedded-integration owner owns this contract, its fixtures, cases and checker, and the account. The host owner, SWBPIPE's own project for the first host, builds and selects the loop, where it runs, its parsing and streaming, conversation persistence, the native layer with its destination enforcement and credential custody, and the panel's assembly. Host evidence is received from that owner and holds only for the candidate it was observed on.
- **CLM-002** — Neighbours own what this contract uses and does not define: `DEL-03-01` the catalog, its entries and read basis; `DEL-03-02` the proposal lifecycle and host outcomes; `DEL-02-01` workflow identity and checkpoint declarations; `DEL-02-03` the recording of checkpoint arrivals and acts and the governance-phase hold; `DEL-04-01` the operation policy and act kinds; `DEL-04-02` the grant display states, the settings version and the display of destinations contacted; `DEL-04-03` the run and act record; `DEL-05-02` what a host panel shows of the loop's events. `DEL-01-05` owns the App's own provider access; its capability handoff identifies the App's provider interface so that it stays apart from a host's model interface, and no requirement of this contract is taken from it. The destination rules, the destination request and the failed-turn closure are defined here once, and the display, the record entries and the panel's prompt are built on them by their owners.
- **CLM-003** — No common loop or service is selected. A common implementation of any part needs a concrete repeated responsibility agreed by the App/shared contract owners and the affected consumers. The App runs no Chirality loop, so SWBPIPE is the one identified consumer.
- **CLM-004** — The person performs proposal acceptance, marking work checked, approval, professional reliance, any change of grant and enabling external access; the accountable professional owns professional claims. The host offers, records and presents those acts and produces its receipts. An agent may prepare or request an act within the scope granted and never performs one. Additions to the reserved acts for a specific operation are undecided (the owner with the affected App and host design owners); once decided, `DEL-04-01` carries them.

## Production and Verification Method — Praxeology

Choices that define the product:

- Names in the contract and its schemas are this contract's own labels for meanings. No transport, protocol version, hash or canonical form, persistence, thread or process placement is selected by them.
- Fixtures are written against the fixture basis. A rule drawn from it holds for the fixtures; the edition a host's loop speaks is that host's to name.
- The destination flow is stated once, here. The display, the record entries and the panel's prompt cite it and add no second account.
- The checker receives a host's documents as supplied and keeps their original bytes. It never repairs, completes or narrows what it was given, and it refuses a check it cannot make instead of passing it.
- Scenarios run on a scripted native layer and a scripted host control, and their record entries are checked against `DEL-04-03`'s record schema. Such a run observes no host.
- Cases use the shared fixture catalogue of `DEL-03-01` wherever it has a subject for them; parse-level, endpoint and responsiveness cases use invented local subjects.
- The two schemas are checked by the same registry as the catalog's.
- This contract and its questions for the host owner reach SWBPIPE through the human-relayed repository files of the App's exchange with SWBPIPE. A prepared file is neither delivery nor adoption, and an answer is recorded as an answer, not a commitment.
- Cases on a SWBPIPE candidate are outside App v4's release and are run in support of SWBPIPE. The contract, its fixtures and its checker do not wait for them.

- **VER-001** — Executable check (observes, for each model-choice and destination scenario run on a scripted native layer and host control, the destinations contacted, the state each request ends in, the result its call receives and the record entries written) and comparison with a named reference (on a host candidate, the destinations that host's native layer reports under its stated configuration and grants): every scenario of AC-001, including the request closed by its turn's failure.
- **VER-002** — Judgment by a reviewer who did not write the contract (reads the native-layer and credential obligations against ARCHITECTURE V4-ARC-12) and, on a host candidate, comparison with a named reference (that host's native trace and its interface script inspected for key or credential content): the enforcement point, the destination record and the absence of credential content in script memory, messages, events, records and errors.
- **VER-003** — Judgment by a reviewer who did not write the contract (reads the contract and fixtures against ARCHITECTURE V4-ARC-10 and V4-ARC-14, and the host's model interface against the App provider interface that `DEL-01-05`'s capability handoff identifies): the minimal capability, the four subjects, and that nothing is selected for a host.
- **VER-004** — Executable check (observes which calls the checker reports ready and which it refuses, with the reason, for schema-invalid, schema-conformant and schema-conformant but domain-invalid calls against an identified catalog edition) and, on a host candidate, comparison with a named reference (that host's trace showing rejection on the catalog schema before its own validation runs).
- **VER-005** — Executable check (observes the record assembled for every call of every fixture stream, and whether any rejected call is reported ready) and comparison with a named reference (the response shapes of the fixture basis, and the shapes observed from one local OpenAI-compatible server and reproduced as fixtures).
- **VER-006** — Judgment by a named role (the examiner observing the host candidate, who performs the listed interactions under each load): continued usability, stated as observed for those interactions on that candidate, with the environment and limitations recorded.
- **VER-007** — Judgment by an independent reviewer (reads the account against the decomposition's DEL-05-01 and PKG-05 rows, its open issues on loop placement and shared-component placement, and its external dependency on SWBPIPE): each excluded act one for one against CLM-001, CLM-002 and CLM-003, and each proposed common part for its agreed repeated responsibility.
- **VER-008** — Executable check (observes what the cases accept and refuse as a person's act: a success alone, a queued proposal, a receipt, findings, an agent's request, an agent-authored record and a relayed capture record) and judgment by an independent reviewer (reads the event and checkpoint definitions against HOST_INTEGRATION V4-HI-25, V4-HI-30 to V4-HI-33 and V4-HI-42).
- **VER-009** — Judgment by an independent reviewer (reads every conformance statement in the cases and the account for its evidence kind, candidate and observation): a statement about a host with no observation of that host fails.

## Governing Values and Decisions — Axiology

- **AX-001** — The person's data goes only where the person allowed, and the loop stays replaceable. Better means fewer of a host agent's contacts that the contract leaves unrecorded, unattributed to a grant or beyond what a case can examine, and fewer obligations that only one loop implementation could meet; never by a default model, a fallback, a grant the person did not make, or the selection of a wire field, placement or library for a host.
- **AX-002** — Receiving stays with the App/shared side and construction with the host. Better means more of a host's conformance decided from documents and observations that host supplies, each with an expected result fixed before the observation; never by building or choosing a host's loop or native layer, by a common service its owners have not agreed, or by stating host behaviour from a fixture.
- **TBD-001** — Where a host's loop runs, how it parses and streams, how its conversation persists, how long its events are held for replay and how its panel is assembled are undecided (the shared contract owner with the SWBPIPE implementation owner). The contract requires the outcomes and none of the means.
- **TBD-002** — Whether any part of the loop becomes a common implementation, and where shared contracts and components are placed, is undecided (the App/shared contract owners with the affected consumers). None is selected.
- **TBD-003** — The Chat Completions edition a host's loop speaks, and that host's catalog, record and checkpoint interfaces, are the host owner's to name; none is selected. No conformance is stated for a host before its candidate supplies them.
- **TBD-004** — Whether every event the loop emits belongs in the run record, or only those with a record entry, is undecided (owner).
- **TBD-005** — How a turn ends when a response is cut off at its length limit or filtered and carries no tool call, including while a destination request of that turn is pending, and how a model-service or transport error is represented apart from a termination reason, are undecided (owner).
- **TBD-006** — Whether the loop may itself refuse a call to an entry that the supplied catalog marks as not exposed on the embedded surface, or must offer whatever the host supplies and relay only the host's own "not exposed" result, is undecided (owner). Until it is, a loop-side refusal is labelled as the loop's and never as a host's response.
- **TBD-007** — What evidence shows that an MCP server follows the stateless revision, which endpoints a cloud model's sign-in service comprises, and whether traffic a host operation makes without declaring it counts as the agent's are undecided (the contract owner with the host owner).
