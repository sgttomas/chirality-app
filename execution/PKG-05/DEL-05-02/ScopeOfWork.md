# Host panel and shared interaction receiving

## Purpose and Objective Traceability

A person working in a host talks with the agent, chooses its workflow, decides on its proposals and reads its checks in one panel, while everything the agent did or proposes is in the host's own tables and views, with the standing the host gives it and nowhere else. This deliverable contributes the App/shared side of that result: the panel receiving contract, which says what a host panel shows for each of the loop's events and the host's results and what it passes back; the account of which panel parts could be shared; the cases that compare a panel with the host's tables, with a panel double to run them on; and reusable components only where a repeated responsibility is agreed. The host builds its panel, its tables and its views.

It is the DEL-05-02 row of the [accepted decomposition](../../_Decomposition/Deliverables.csv), an API contract in PKG-05, and serves OBJ-004: App/shared host contracts and a coordinated SWBPIPE journey that preserve operation meaning, host authority and recovery. Its sources are [PRD](../../../docs/PRD.md) V4-HOST-04, V4-HOST-05 and V4-AUT-01 to V4-AUT-05; [HOST_INTEGRATION](../../../docs/HOST_INTEGRATION.md) §1, V4-HI-10 to V4-HI-12, V4-HI-20 to V4-HI-25, V4-HI-30 to V4-HI-33, V4-HI-40 to V4-HI-42, V4-HI-70 and V4-HI-71; [ARCHITECTURE](../../../docs/ARCHITECTURE.md) §4 and V4-ARC-20; and [EXAMINATION](../../../docs/EXAMINATION.md) V4-EXM-20 to V4-EXM-22. The draft 4.0.0 release target names no exit criterion for this deliverable; the live SWBPIPE journey of its criterion 5 is observed through a host panel and the host's own tables, in this contract's terms.

## Deliverable Definition — Ontology

- **OUT-001** — The panel receiving contract: the document that states what a host panel shows for each of the four interactions, what it refers to in the host's views and what it passes back to the loop. The meanings under *Terms* below bind it; what it proposes beyond them is undecided (TBD-007). It is a contract of behaviour; wire fields, wording and layout are the host's. Scope: SOW-019, SOW-020; OBJ-004.
- **OUT-002** — The reusable-component allocation account: for each panel part that could be shared, its possible consumers, whether the responsibility is repeated, whether its consumers have agreed and where it would be placed, or the statement that this is open; and the boundary of what the host constructs. Scope: SOW-019; OBJ-004.
- **OUT-003** — The panel-to-host-table receiving cases, with their expected results, the comparison that judges them and a panel double to run them on, and the results obtained on an identified host candidate. Scope: SOW-019, SOW-020; OBJ-004.
- **OUT-004** — Reusable panel components, only for a part whose repeated purpose, App/shared ownership and receiving consumers have been agreed. Until a part is agreed there is no component and none is implied. Scope: SOW-019; OBJ-004.

Terms:

- **Panel.** The host-assembled surface for four interactions: conversation, workflow selection, the proposal queue and checks. It lists, summarises, links and offers the host's decisions. It holds no domain truth. A host presents one agent seat and the selected workflow; choosing a role is not a panel interaction.
- **Host view and reference.** A host view is a table, view, diagnostic or result display the host gives the person. A reference is a pointer to a host object, a position in a view, a proposal, a change item, a receipt or a record that can be followed into the host's view. The panel shows references, not copies.
- **Agent-private result surface.** Any place where an agent's results or proposed changes are visible only outside the host's views, or differ from them. Prohibited. An **alternate mutation route**, any path to host objects other than the host's one validation and application route, is prohibited too.
- **Conversation.** The message stream with each speaker and whether each message completed; tool activity as the loop reports it (requested; rejected before the host's validation, with the kind; dispatched; the host's outcome; outcome unknown, with reporter and last observed state); an agent's request for an act, shown only when one was issued; the model setting in force, with no credential content; and failures. Prose is never shown as a host result, and a rejected call is never shown as executed.
- **Workflow selection.** The workflow's identity with its origin and holding library; its declared checkpoints, shown as plan guidance; and its required tools, each with its requirement outcome and necessity as `DEL-02-01` defines them. The requirement check is shown as passing only when it passes. A workflow whose requirements are undeclared stays selectable and is labelled so. A selection is never silently rebound to a same-named workflow.
- **Proposal queue.** For each proposal and each change item: the objects affected, the old and new values, the reason, the origin, the basis relied on and the current disposition, with the authoritative values in the host's views. A proposal's state is derived from its items and never stronger than them. The person accepts or rejects item by item, several items or a batch. Decisions say "accept", never "approve". A host's refusal is never shown as a rejection, queued is never shown as applied, and an accepted item that the host then refuses as stale is shown as accepted and not applied.
- **Checks.** Three things kept apart: an agent's examination findings, which refer to rows and results and to the basis that was read; the host's check results, each named with the basis it was evaluated on and whether it is current or historical; and the person's mark, shown as checked by that person with its bound content and lapse state. Findings are never shown as checked or approved, and an examination changes no domain table.
- **Recorded act.** Shown with its actor (the person), its recorder, whether it was captured directly or recorded faithfully afterwards, its capture-evidence reference and its bound content. It is shown as lapsed once that content changes. A record with no capture evidence has no act standing. An act that was not performed is never shown.
- **Checkpoint in the panel.** In the current phase a declared checkpoint is plan guidance. An arrival is shown only when the loop reports it, with the required act, the bound subject, the purpose and the scope. *Waiting* means reached with the act not yet recorded, never that the run is held; no call or run is shown as held or stopped. The act is shown as performed only from the host's capture.
- **Grant.** Shown in the display states `DEL-04-02` defines. The grant display and a checkpoint's indicator never merge into one "allowed" signal, and an agent's request for a grant is never shown as a grant.
- **Return input.** What the panel passes back to the loop: only what the person does in conversation and workflow selection. What the person decides (accepting, rejecting, marking checked, approving, relying, changing a grant, answering a destination request, enabling external access or changing the model setting) goes through the host's own control and reaches the loop as the host's capture record. The panel shows the result of what it passed only from the loop's events, never from having sent it.
- **Failure displays.** A model or turn failure shows the partial message as incomplete, never as complete, and no model the person did not choose. A reference that no longer resolves keeps its last known label, marked so, with nothing substituted. A destination request still pending when its turn fails is shown as REQ-001 states.
- **Panel-to-table comparison.** What the panel carries for a read (its host, operation, catalog edition, basis, views and standing) is compared with the host's own table observation. The result is same content, different content, or host table not supplied; the last is never a pass.
- **Panel double.** A scripted stand-in for running cases with no host: it replays loop events and can fail a turn, resolves or fails references, and emits scripted capture records. It performs no act and is never evidence of one, and a result obtained on it holds for the display rule only.
- **Case standing.** Each case is defined, executed on the panel double, or executed on an identified host candidate; a case waiting for an input or a decision says which, and is never a pass.

Boundary:

- **CLM-001** — The App/shared panel receiving owner owns this contract, the account, the cases and the double. The host owner, SWBPIPE's own project for the first host, owns its panel's assembly and layout, its tables and views, domain construction, conversation persistence, the resolution of treatment and the capture of acts. A contract or a prepared handoff is no evidence that a host agreed, delivered or adopted anything.
- **CLM-002** — Neighbours define what the panel shows and this contract does not redefine: `DEL-02-01` workflow identity, checkpoint declarations and requirement outcomes; `DEL-02-03` the recording of checkpoint arrivals and acts and, for the governance phase, the hold; `DEL-03-01` the catalog, read basis and standing; `DEL-03-02` proposals, change items and outcomes; `DEL-04-01` the operation policy, act kinds and labels; `DEL-04-02` the grant display states and the display of destination settings and of destinations contacted; `DEL-04-03` the act and run record; `DEL-05-01` the loop's messages, tools, events and checkpoints, its destination rules and requests, and the failed-turn closure.
- **CLM-003** — The App/shared contract owners decide the placement of shared contracts and components against actual consumer responsibilities, and the shared contract owner with the SWBPIPE implementation owner agrees the boundary between host and common construction. A common implementation needs an agreed repeated responsibility; the word "shared" selects no library or service.
- **CLM-004** — The person sets autonomy and performs each checking, acceptance, approval or professional-reliance act. The host offers, records and presents those acts and enforces the adopted policy; it is not the person performing them. An agent or a host facility may faithfully record an act a person performed, with the actor kept apart from the recorder, and never fabricates one. A host has no classifier permission mode, and nothing the panel shows stands in for a reserved or professional act.
- **CLM-005** — The operation, autonomy, environment and externally supplied interfaces of the first connected activity are chosen by the owner with the App manager and the SWBPIPE owner, and a host's panel, views and candidate evidence are that host's to supply. A case that needs them is unexecuted until they are supplied. The human relays this contract, its questions and proposed interfaces, and the answers, between the App and the SWBPIPE owner through repository files; the App manager keeps the account of that exchange.

## Completion and Reliance Basis — Epistemology

- **REQ-001** — The contract defines conversation, workflow selection, the proposal queue and checks as receiving requirements, each connected to the host's objects and results and to the workflow, catalog, proposal, standing, record and loop-event definitions CLM-002 names, and it names an input that is unavailable or undecided as such. A destination prompt closed by its turn's failure closes only on that request's actual source, conversation, run and turn, shows "not answered — turn failed", grants nothing, dispatches no waiting call and takes no later answer in that turn; where the binding is ambiguous the choices are withheld and a limit is shown. The panel keeps the basis, outcome and receipt references it received and invents no domain truth of its own. An act a person performed is presented faithfully, with the decision actor apart from the recorder, its content binding kept and its lapse visible once that content changes; no act is fabricated. The interface applies the adopted policy and checkpoint distinctions as `DEL-04-01` carries them and decides no operation-specific addition. ## Production and Verification Method — Praxeology

Choices that define the product:

- The panel shows what it received. Each display is traced to the definition that owns its meaning, and a missing definition or host input is shown as missing.
- Names in the contract and its schema are this contract's own labels; no wire field, wording, layout or component is selected by them.
- No case runs on a SWBPIPE candidate while the owner holds live SWBPIPE joins; only the owner releases that hold, by resuming SWBPIPE UI-SUCCESSOR work. The contract and its panel-double cases do not wait for it.
- A person's decisions never travel as panel inputs. They are the host's captures, relayed.
- Cases run on the panel double until a host candidate exists, and results on the double are kept apart from results on a candidate.
- Cases use the shared fixture catalogue of `DEL-03-01`.
- A component is built only after its allocation is agreed; the account can stay open.

- **VER-001** — Judgment by a reviewer who did not write the contract (reads each of the four interactions against PRD V4-HOST-04 and traces what it shows to the definitions CLM-002 names and to host objects and results), with an executable check (observes what the panel double shows for a turn failure, an unresolved reference, a message passed back before the loop reports it, and a destination request pending when its turn fails).
- **VER-002** — Comparison with a named reference (on a host candidate, the host's own tables and views for a proposed edit and for an agent check, before and after the check) and, with no candidate, an executable check (observes the result of the panel-to-table comparison on the double for the same content, changed content and a table not supplied): affected rows, old and new values, reason, basis, outcomes, receipt references and standing, with a detached agent-private result and a bypass route as the cases that must be refused.
- **VER-003** — Executable check (observes what is shown for a success alone, a queued proposal, an acceptance and application, agent findings and a relayed capture of a check, approval or reliance, and for a changed bound content) and comparison with a named reference (the host's capture record of an act a person actually performed, recorded by a separate recorder): no act is shown without its record, the actor and recorder stay apart, and proposal text says "accept".
- **VER-004** — Judgment by an independent reviewer (reads the account against the decomposition's DEL-05-02 row and its open issues on loop placement and shared-component placement, and against ARCHITECTURE V4-ARC-20): the repeated purpose, the actual consumers and their agreement or its absence for each part. No agreement is inferred from an authored file.
- **VER-005** — Judgment by an independent reviewer (reads the case inventory for its coverage of AC-001 to AC-003, the definitions and inputs each case names, and the standing each case claims against the evidence kept for it). This examines the accounting of the cases and is not an execution of them.
- **VER-006** — Judgment by an independent reviewer (reads any delivered component against its agreed responsibility and the panel contract, or, where none is agreed, confirms that no component is presented as built).
- **VER-007** — Judgment by an independent reviewer (reads each act REQ-006 excludes one for one against its owner in CLM-001 to CLM-005 and the decomposition's rows for those owners).

## Governing Values and Decisions — Axiology

- **AX-001** — The host's views are where the work is seen, and shared meaning transfers no host ownership. Better means fewer things a person can learn about the agent's work only from the panel, and fewer differences between what the panel carries and what the host's table shows; never by copying host values into the panel, by a route to host objects outside the host's own, or by a shared component its consumers have not agreed.
- **AX-002** — Each act keeps its own subject, actor and evidence. Better means fewer displays in which a person could mistake an agent's output, a success or a routine permission for a check, acceptance, approval or reliance; never by hiding an act a person performed, and never by showing one that was not performed.
- **TBD-001** — How a host's panel is assembled, where its loop runs and how its conversation persists are undecided (the shared contract owner with the SWBPIPE implementation owner).
- **TBD-002** — Whether any panel part becomes a shared component, and where shared contracts are placed, is undecided (the App/shared contract owners). No part is agreed.
- **TBD-003** — A host's panel, tables, views, capture of acts and stable references to positions in its views are the host owner's to supply, and whether a host holds an agent's findings itself or leaves them as message content with references is that owner's choice. No conformance is stated for a host before them.
- **TBD-004** — Operation-specific additions to the reserved acts, and the operation, autonomy, environment and externally supplied interfaces of the first connected activity, are undecided (the owner, through the SWBPIPE session, with the App manager, as CLM-005 states). The contract shows such an operation's policy as undecided.
- **TBD-006** — Whether this deliverable owns a host panel's network-destination surfaces (the allow-list settings, the prompt for a request made during work and the list of destinations contacted) or only receives `DEL-05-01`'s rules and `DEL-04-02`'s displays for them is undecided (owner). Until it is, the contract commits only to how a pending request closed by its turn's failure is shown (REQ-001), and to nothing else of those surfaces.
- **TBD-007** — Whether the rules the contract document proposes beyond the *Terms* are adopted as commitments is undecided (owner). They are: the kinds and fields of a return input and the loop's answer to one; what is shown for an input that was not delivered; and how a panel learns that it missed events, what it shows for them and whether it asks the loop to send them again. Until one is adopted it binds no host, and no criterion here rests on it.
