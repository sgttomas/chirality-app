# R2-S storage interface — proposed source/proof hypothesis

PROPOSED only, basis12a306d6ed7a67d13063bf908136306772a8659a. Implements no storage, journal, schema or policy. C3-OD-02 selects recoverable current status; PR1177 source plan and PR1178 select R2-S as the first proof hypothesis, not an implemented mechanism or numeric capacity. Group C owns semantic integration and its work graph. This source addresses storage obligations only, separate from CCE minting, W2 ordinary supplier file work and held Host/Stop work.

## 1. Current source and proposed scope

connector_route_store.rs opens an explicit project, retains root/directory identities, uses descriptor-relative no-follow operations, syncs and publishes immutable accounts with no-replace rename. Its documented comparison limits do not exclude transient external rename. Its current read_account allocates read_to_end before the format0.3/0.4 size rejection: not an R2 bounded-reader primitive. connector_materialization.rs has per-App Mutex/Registry, one payload,64 consumed lifetime identities and no eviction/reset; it is not cross-process quota. recovery.rs newline JSON append/sync_data and torn-tail refusal retains pointer records, not R2 artifacts or shared locking; it loads entries and offers no R2 bounded-allocation proof. Reuse patterns only after reviewed adaptation; change none of these sources here.

Candidate placement: an R2-private subdirectory under the opened project, distinct from immutable route-accounts and App recovery ledger. Exact relative name/version remains owning review input. Components below describe an interface, not permission to create them. One stable project control identity and lock object; a bounded set of journal slots; each live slot has immutable journal identity, snapshot A, snapshot B, one descriptor and at most one small descriptor-temporary. No timestamp/latest-file discovery. No cloned project automatically inherits live journal authority.

## 2. Original identity and symbolic resource contract

Project control binds format/method version, original random project-journal namespace ID, selected policy identity and opened root provenance. Journal identity is a fresh never-rebound ID plus original undertaking binding/creation record; it is not a pathname, slot number, PID, role name or inferred work-graph heading. Snapshot and descriptor repeat this identity, monotonically increasing revision and exact predecessor descriptor digest. Store root inode/device is a live custody check, not a portable enduring project ID. Cold open validates the original control identity and explicit selected project; copied/moved roots require named reconciliation and cannot silently resume writing.

Numeric choices remain UNSELECTED: N admitted journals, S snapshot serialized-byte maximum, D descriptor maximum, T terminal-marker/identity-history maximum, Q total project disk budget, and bounded metadata/ref count/depth limits. The earlier1MiB snapshot/64KiB descriptor are candidates only. Existing one-full-payload/1MiB development constraint is preserved; two disk slots never authorize two full resident payloads. Implementation must refuse missing/unsupported resource policy, not choose convenient defaults. Policy changes/migration require their own review, not silently reinterpret old entries.

Before admission reserve worst-case storage, not current compressed size: per live slot2*S + descriptor + descriptor-temporary + identity/terminal metadata, plus filesystem overhead and explicitly selected evidence storage. All staging, orphan candidates, ambiguous journals and terminal markers consume shared quota until reconciled by a reviewed policy. No per-agent/process multiplication; unknown entries conservatively block admission rather than being ignored. Temporary names are fixed-cardinality and identity-bound; repeated errors cannot accumulate new files. If recovery-critical exact evidence exceeds S or shared Q, refuse advancement, retain current committed state and expose the missing progress. No truncation, summary substitution or automatic old-journal eviction.

## 3. Shared writer and quota exclusion

Proposed ProjectJournalSession owns opened root/directory descriptors and the stable control/lock handle. An OS-backed exclusive advisory lock on the same stable lock object serializes **all** cooperating App processes' journal admission, update, reconciliation and retirement. Each independent opener obtains its own lock acquisition, not a duplicate assumed to be independent. Use nonblocking acquisition with explicit busy; no lock upgrade race. While holding it, boundedly enumerate/account all slots and validate control policy/identity before admitting or writing. Quota is derived/reconciled from actual committed and reserved slot state under this same exclusion; no separately incremented counter that can diverge from journal publication. No supplier request or model wait while locked.

The lock file is never replaced/deleted during normal operation; open no-follow, regular/single-link/type validation, descriptor identity checked against current entry before and after operations. Initialization itself needs exclusive-create plus directory sync and deterministic collision handling. Owner creation/admission is serialized before any journal identity escapes. No PID-file stale-lock override; OS lock loss/unsupported filesystem is unavailable, not permission to write concurrently. Process death releases runtime ownership but does not erase reserved disk state.

This is cooperating-process mutual exclusion, not protection against a same-user actor replacing the lock/control files or ignoring advisory locks. Descriptor/path rechecks detect observed substitution but cannot prove absence of transient replace/restore. If the required threat model includes that adversary, this file-lock design does not establish exclusion/quota and must fail its proof or adopt a separately warranted custody mechanism. Do not imply normal Codex file permissions are revoked, do not silently add a privileged broker. Local/network/synced filesystem support must be selected/tested; documented primitives alone do not qualify it.

## 4. Proposed operations and linearization

Private APIs: open_project(policy, opened_root); inspect_journals(budget); admit(original_undertaking); load_committed(journal_identity); prepare_snapshot(expected_revision, recovery_content); commit(prepared); reconcile_attempt(attempt); prepare_retirement(proof). These are source labels, no public tools. Every mutation requires the same project writer exclusion and root association. CCE/Host locks are not held across disk operations; obtain immutable bounded source evidence first, then revalidate relevant semantic revision separately. A disk commit never creates a Host capability or atomically commits a supplier action.

Snapshot content includes original journal/undertaking identity, stage/revision, exact selected0.4 raw base identity/bytes or preserved immutable reference, answer/review exact authored bytes and distinct request/emission/role references, original intended ordinary request/target/limits, attempt state, observed supplier outcome, independently observed target state, manager reconciliation, final-account outcome and explicit gaps/actor responsibility. Keep not-requested, intent-confirmed/dispatch-unknown, terminal failure, observed tool completion, target match and integration outstanding distinct. Group C defines exact semantic enums/schema; storage checks structural identity/byte survival, not meaning or performance.

### Update sequence (all under project exclusion)

1. Resolve exactly the descriptor-selected current slot, identity/revision/hash/size and required references; recheck expected revision. Refuse ambiguous/corrupt/forked basis. First admission is explicit revision0/no committed snapshot, durably reserves identity/quota before tracked action.
2. Prove replacement survival: every recovery-critical old artifact is carried exactly in the new snapshot or resolves through an independently retained immutable object whose lifetime exceeds all referring records. A hash into either reusable snapshot slot is NOT such an object. Compare required-reference set; unresolved attempts cannot disappear. Refuse preparation if survival cannot be established within selected bounds.
3. Select inactive A/B. Never truncate the descriptor's active slot. Write inactive through its retained validated descriptor; replacement/truncation is confined to that journal and inactive identity. This deliberately uses the second slot, not a hidden third full snapshot. Enforce cap while serializing/writing; flush and supported data/device sync; reread/hash/size with bounded buffers and validate identity/revision. Prior active snapshot remains intact.
4. Create the one bounded descriptor-temporary exclusively; include journal identity, new revision/active-slot/hash/size, previous descriptor digest and explicit format/policy identity. Sync descriptor bytes; compare root/chain/control/lock and expected old descriptor again. Atomic replacement of descriptor is the namespace linearization point, NOT by itself confirmed durability.
5. Sync its containing directory under the selected filesystem protocol; reopen/read exact descriptor and selected snapshot, verify identities/hash, then return confirmed commit receipt. No acknowledgement before these checks. Do not reuse the previous active slot on a failed/ambiguous operation.

Exact snapshot sync, descriptor sync/replace and directory/device sync protocol is a platform proof obligation. F_FULLFSYNC/file sync semantics and directory sync support must be validated for selected storage; unsupported/error refuses confirmation. Archive docs are not present-runtime evidence. No guarantee of torn-write immunity, power-loss durability or adversarial tamper resistance is declared now.

## 5. Crash, ambiguity and cold reading

Before descriptor replacement: old committed descriptor remains the only selected state; incomplete inactive bytes are an uncommitted candidate, never newest-timestamp recovery. After replacement but before confirmed sync/readback: commit outcome is uncertain. Cold reader may observe a structurally complete descriptor+snapshot; report committed-descriptor observed, not proof the original caller received confirmation or a supplier request was sent. Lost acknowledgement and actual later effect remain separate. Reconciliation can verify/synchronize observed disk state under lock; it must never retry supplier work or blindly reissue storage mutation.

Malformed/torn/missing descriptor, hash mismatch, wrong revision/identity, duplicate original journal IDs in different slots, competing descriptor evidence or unexpected control-policy change returns explicit unavailable/ambiguous/forked status. Do not choose a higher snapshot revision, roll back silently, rewrite bytes, merge histories or delete candidate files. A previous valid snapshot can be exposed as historical salvage only, never silently current. A fully consistent rollback/copy cannot be proven fresh without an external trusted monotonic anchor; this design offers no such anchor. That limitation must be acceptable for the selected recovery claim or R2-S fails the requirement.

A reader takes shared exclusion or reads under the same exclusive protocol for an initial implementation hypothesis; readers cannot observe inactive truncation concurrently with writers and then label it a valid active state. Acquire OS exclusion without holding App semantic locks. Read descriptor through bounded D+1 allocation/stream limit, regular/no-follow/single-link checks; validate lengths/integers before allocation. Read selected snapshot with S+1 limit, exact raw hash and bounded JSON depth/member/string/reference budgets; reject duplicate keys. Metadata length alone is not trusted; actual bytes are capped. Never read both full slots into memory, never use read_to_end before checking the budget. Enumerate names and issues with finite policy bounds; refuse overflow instead of allocating an unlimited directory listing. Use bounded streaming buffers for hashes/reference checks and at most one full parsed snapshot; avoid a second serialized full copy unless total peak stays within existing envelope.

## 6. External action ordering and exact reference survival

For a newly App-initiated tracked supplier request, confirm exact intent snapshot before dispatch through current Host permission/custody. Crash after that commit but before dispatch and crash after dispatch before outcome commit are indistinguishable: recover unknown, no replay. Source closure does not turn uncertainty into failure/no-effect. Matching graph bytes may support a current observation, never recreate a missing request or exclusive causality. Ordinary untracked Codex work has no fabricated write-ahead intent. Journal, supplier edit, source receipt and target reread are not one transaction.

Reference rules: original locator/kind/claimed identity/method plus exact bytes/hash/size; current resolution and retained historical subject differ. Mutable external files, Host memory and retired snapshot paths do not ensure future resolution. Either carry exact recovery-critical material within the current payload or use a separately established bounded immutable artifact store/record with retention coupling. This proposal does not introduce an unbounded blob store. Missing bytes remain a named gap; if required for the selected recoverable status, advancement/retirement refuses. A valid checksum does not establish actor, role, permission, review performance or source currentness.

Final account publication is separate CAM/CRP one-use operation. Bind exact pre-final committed journal state in that account only if its required bytes survive future slot reuse: embedding/independent immutable retention needs the owning carrier contract and capacity proof. A bare hash of a reusable slot fails. Later journal revision can reference final account to avoid a hash cycle. If final account succeeds but journal update fails, retain publication uncertainty and original attempt; cold reconciliation may observe exact final bytes but cannot revive a consumed CAM token. Journal success never proves account publication, and account existence never proves prior dispatch/manager contribution.

## 7. Terminal marker and retirement (policy NOT selected)

Candidate terminal transition is an ordinary confirmed descriptor/snapshot commit with exact final outcome, no unresolved attempt, surviving evidence closure and prospective retirement reason. Cancellation is not automatically terminal if effects/attempts remain unresolved. Preparing a terminal marker never deletes anything or releases quota. Marker contains original journal identity/incarnation, terminal revision/hash, final reference and retained evidence resolution limits, bounded by selected T/D policy.

Required crash order for any later selected reclamation: commit/sync terminal state; publish/sync its durable terminal identity marker; verify all references survive; only then may policy permit reclaiming bulk slots; synchronize each removal/accounting boundary before quota is considered reusable. Crash before marker means no reclamation; crash after marker before bulk removal leaves both counted; crash during removal keeps marker authoritative for identity and unknown cleanup; crash after removal before accounting reconciliation does not grant extra capacity by guessing. Original ID is never rebound even if physical slot reused with a new ID. Bounded marker/tombstone exhaustion visibly refuses retirement/admission; no eviction/reset/restart trick.

This is a required ordering sketch, NOT a selected retention period, deletion/reuse policy or authorization. Until that policy and finite identity history are chosen, treat terminal journals as quota-consuming, no bulk deletion or slot reuse. If product workload cannot fit without different retention, bring the concrete capacity/retention tradeoff to HELP_HUMAN. Final CAM64 suitability is a separate product obligation; journaling cannot reset or expand it.

## 8. R2-L comparator and go/no-go criteria

R2-L may beat R2-S when evidence grows incrementally and rewriting a full bounded snapshot dominates sync/write cost, or when the selected filesystem cannot warrant descriptor replacement but can warrant framed append plus independently committed offset/checkpoint. It still needs the same shared lock/quota, exact reference survival, finite log/checkpoint/compaction space and one-payload reader budget. Torn tail cannot be treated as confirmed prefix success without a committed boundary; compaction must retain old confirmed bytes until checkpoint confirmation. Append does not solve external-action atomicity, hostile replacement, marker lifetime or CAM64.

Falsify R2-S if any required recovery-critical working set exceeds selected S/Q, directory/descriptor sync cannot be qualified, cooperating-process exclusion fails, immutable reference survival needs unbounded retained blobs, bounded reader proof fails, or usable retirement cannot fit finite marker capacity. Compare actual bounded workload/fault evidence before selecting R2-L, not aesthetic preference. No benchmark, fault injection or process test ran here.
