## Purpose and Objective Traceability

Define the App/shared receiving and conformance contribution to the minimal embedded host loop, which runs on a local or cloud model the person chooses. This API_CONTRACT deliverable supports OBJ-004, establishing App/shared host contracts and a coordinated SWB journey that preserves operation meaning, host authority and recovery. ## Completion and Reliance Basis — Epistemology

- **REQ-001** — The receiving contract shall present local and cloud models as options the person chooses among, with no default: a user-controlled local model server, or a cloud model reached by OAuth sign-in or an API key. The host's agent shall send data only to the model service the person selected and to destinations the person has allowed — in advance in an allow list (by category, such as web access, MCP servers or other APIs, or by named destination) or when the agent asks during its work — and contact nothing else: no analytics, silent provider switch or background download unless the person turns it on. Only the person grants a destination; the agent never grants itself one. An MCP server is allowed only if it follows the stateless MCP revision 2026-07-28. Every destination contacted shall be recorded and shown. The host native layer shall carry the loop's requests, enforce the selected model service and allowed destinations, and keep keys and sign-in credentials outside interface scripts; an outside process that is not sandboxed is recorded with the destinations it declares, as a stated evidence limit. Organization-locked allow lists and enforced sandboxing of outside processes are a later governance phase. Sources: PRD V4-HOST-01/02 and Architecture V4-ARC-11/12 as amended by `SCA-V4-001`; `APP-V4-SWBPIPE-INTAKE-20260928-DECISION-4` D4-3; `APP-V4-SWBPIPE-INTAKE-20260928-DECISION-5`; Architecture §4; SOW-015/016/017/137/138.
- **REQ-002** — The receiving contract shall require minimal host-agent capability over OpenAI-compatible Chat Completions with tool calls and define a replaceable boundary for messages, tools, events and checkpoints. It shall keep the host model contract distinct from the standalone App's Codex App Server/provider interface and leave exact protocol versions and payload details unselected until their actual basis is available. Pi is a possible later replacement, not a current dependency. Sources: Architecture V4-ARC-10/14 and §§3/6; SOW-136/140.
- **REQ-003** — Tool arguments shall be checked against the adopted host catalog schemas before host domain validation. Truncated or malformed tool calls shall produce reported failure and shall never be executed as empty arguments. A schema-valid call remains subject to host validation and application authority; it is not evidence of host acceptance or a person's act. Sources: Architecture V4-ARC-13 and §4, Host V4-HI-20/25, CLM-001/002/004; SOW-139/142.
- **REQ-004** — The receiving contract and cases shall require streaming and long parsing to leave the host interface responsive, using off-main-thread work where the host needs it. They shall preserve loop placement, parsing strategy, conversation state/persistence and panel assembly as owner-selected means under OI-013 rather than prescribe a worker, service, storage technology or unsourced timing threshold. Sources: Architecture §4, Issues, CLM-001/003; SOW-141/144.
- **REQ-005** — The allocation account shall name required inputs, their owners and actual standing: catalog schemas; shared workflow/role/checkpoint meanings; record and human-act meanings; panel receiving needs; and host-specific native/loop evidence. It shall distinguish unresolved detail from the included required outcome, retain OI-013/OI-014 and DEP-001 at their recorded points of need, and allocate common implementation only on an agreed repeated responsibility. Sources: Basis, Issues, Clarification, CLM-001/002/003; SOW-136/144.
- **REQ-006** — This deliverable shall perform no act owned by another deliverable or external owner: defining the catalog/read-basis schemas of `DEL-03-01`; defining proposal/validation/outcome meaning of `DEL-03-02`; defining workflow/role/checkpoint declarations or shared allocation of `DEL-02-01`; implementing workflow execution/checkpoint behavior of `DEL-02-03`; defining the autonomy-grant display states or standing exchange of `DEL-04-02`; defining the operation-policy/human-act distinction contract of `DEL-04-01`; defining the shared record format of `DEL-04-03`; or constructing the panel receiving contribution of `DEL-05-02`, each resolved in CLM-002. It shall exclude SWBPIPE host loop/native-layer construction, destination and key/credential enforcement implementation, parser/streamer construction, conversation persistence and panel assembly, each owned by the external host owner in CLM-001. Common implementation allocation remains with the owners in CLM-003. This exclusion preserves this deliverable's requirements, fixtures, conformance cases and owner coordination. Stating the receiving obligations under which a host loop evaluates reached-when and records checkpoint arrivals and acts as observation (current phase), and, for the governance phase, realizes `DEL-02-03`'s retained hold machine and hold-support values, is this deliverable's receiving work, not implementation of `DEL-02-03` (`APP-V4-SWBPIPE-INTAKE-20260928-DECISION-4` D4-1).
- **REQ-007** — Loop event/checkpoint and record receiving definitions shall preserve distinct acts from CLM-004 and the shared meanings in CLM-002. They shall exclude performing proposal acceptance, marking work checked, approval or professional reliance on behalf of the person; those actual acts belong to the person in CLM-004, while the host's offering/recording/presentation and domain receipt production belong to the host in CLM-004. An observed execution result is evidence of execution only. No generic sequence requiring acceptance before every independently evidenced check, approval or reliance is introduced; a declared workflow checkpoint still requires its specified act. Sources: Host V4-HI-25/30/31/33/42, PRD V4-WF-05 and sealed brief distinct-acts clarification.

- **AC-001** — OUT-001 and OUT-002 require the person's choice between local and cloud models with no default, cloud access by OAuth sign-in or an API key, and host-agent traffic only to the selected model service and person-allowed destinations, with each destination recorded and shown. Verification: VER-009. Sources: Basis DEL-05-01 verification, Issues DEP-001, Clarification and Setup.

## Production and Verification Method — Praxeology

Develop the receiving definition from the assigned accepted scope and sources, obtain the adopted upstream contract identities at their points of use, and express fixtures and conformance cases against those identities. Prepare independent local definition work while retaining open allocation and external host inputs. Coordinate host questions through the authorized human-relayed file path in Acceptance J/O; preparation of a file is not delivery or adoption. No current supplier selection or live network experiment is needed to define this contract.

Inspect the expected model-choice, credential, allow-list, in-work request and decline outcomes, the destination record and evidence separation; later host execution observations must identify configuration, the grants in force and observed destinations. Record missing host observations explicitly.
- **VER-002** — Inspect the native-network receiving contract and destination/credential cases against Architecture V4-ARC-12 as amended. Require evidence of the actual native routing/enforcement, the destination record and script/credential separation before claiming host conformance; model fixtures alone verify only the expressed receiving expectations.
- **VER-003** — Review the loop contract and interface fixtures for all four replacement subjects and minimal Chat Completions tool calls; compare their interface identity to the distinct App Codex boundary and inspect the open supplier/version/wire choices and Pi exclusion against Architecture V4-ARC-10/14 and §§3/6.
- **VER-004** — Examine validation-order cases and, when supplied, host traces showing catalog-schema rejection before domain validation and schema-valid input proceeding to domain validation, which may reject it. Bind checks to adopted catalog identity and keep host application/human acts distinct.
- **VER-005** — Review and exercise conformance fixtures for malformed and truncated tool calls plus valid comparison calls; inspect failure reporting and absence of empty-argument dispatch for rejected input. Label fixture execution separately from received actual-host execution evidence.
- **VER-006** — Review the host responsiveness case definition for concurrent long parsing/streaming and interface interaction. Receive the host owner's candidate-bound observations of continued usability before claiming actual responsiveness; record environment, observations, implementation choice and limitations without inventing quantitative thresholds.
- **VER-007** — Independently compare the allocation/open-choice account to accepted Deliverables, Packages, OI-013/OI-014, DEP-001 and Clarification. Check excluded acts one-for-one against CLM-001/002/003; confirm required receiving work remains included and every proposed common construction identifies an agreed repeated responsibility before allocation.
- **VER-008** — Review checkpoint/event/evidence examples against adopted workflow, policy and record inputs. Check success-only, actual acceptance, independently evidenced checking, approval and reliance as distinct observations; reject cross-act inference and agent impersonation, and verify that a declared checkpoint awaits its own specified act.
- **VER-009** — Audit the conformance and owner account for exact source/candidate identity, actual observations and evidence gaps. Compare the claimed host standing to received DEP-001 material; require the host-specific evidence for any actual host claim and route any joined-journey claim to its owning examination contribution rather than infer it from this contract.

Each case records its source requirement, received basis, expected behavior, observed outcome or absence of observation, and limitation. These are evidence contents, not a selected wire schema. Tests implement these methods; they do not create scope. No method here preselects a provider, closes an open issue, or changes another project's state.
