## Blocking findings

### I1-1 [P1] Ledger accepts an unterminated record and corrupts it on the next append

Original locations: `src/recovery.rs:101–115`, `:120–132`.

Trigger: an existing ledger ends with a complete schema-valid JSON object but no newline, for example interruption after the object's last byte before the appended newline. BufRead.lines() returns that object; open() accepts it. The next append opens with append=true and writes the next JSON object directly against the old closing brace, producing `}{...}\n` on one line. The writer reports success and updates in-memory entries; the next open rejects the concatenated line as unavailable history.

Impact: preserved prior observations become unreadable and the new successful append violates RECOVERY §7's append-only **one entry per line** contract. Existing malformed-ledger test uses `{\n`, which fails earlier and does not cover a complete unterminated tail.

Repair: detect/report a non-newline-closed tail before append, preserving bytes and withholding success, or apply an explicitly governed non-destructive delimiter repair. Recheck at the append boundary too so changed/torn bytes cannot evade open-time checking. Add complete-valid-no-newline and partial-write/next-append regressions with unchanged bytes on refusal. A provisional source repair was observed; this original finding remains until successor verification.

### I1-2 [P1] Current closed-generation frames can enter new request custody

Original locations: `src/native_requests.rs:232–295`; `src/hosting.rs:651–697`, closing via `:488–503`.

Trigger: close generation g, then deliver a queued stdout request from that same tuple before a successor starts. on_line rejects only tuple inequality; g still equals i.generation after close. RequestRegister.receive validates shape/duplicate ID but never checks its closed set. It appends a fresh known request as outstanding, or prepares/writes an explicit error for an unknown/unsupported request in the closed generation. prepare's closed guard does not undo the attribution or automatic receive-error write.

Impact: H5 and HOSTING closed-generation refusal are violated. A dead generation gains fresh outstanding custody after the close scan, contradicting truthful ended-unanswered display and allowing transport activity after closure. Existing tests close then create a request in a **different** tuple; they do not deliver a late new ID within the already closed tuple.

Repair: refuse receive/automatic reply for every closed tuple, and retain the late native frame as a closed-generation observation without attributing it to live custody. Host state/closed tracking must distinguish a same-valued closed tuple before processing requests or resolutions. Add delayed same-tuple known/unknown requests after close, asserting no new outstanding entry, no reply write and unchanged successor custody.

### I1-3 [P2] Native item request links can bind a different generation

Original location: `src/native_items.rs:418–435`.

Trigger: a new ready tuple in the same home reuses thread/turn/item IDs; supplied request history contains only an old tuple's request for those IDs (or it occurs later in the supplied slice). snapshot_with_requests selects by home and native IDs, then writes requestRef/settlementOrigin before applying the full-generation equality check used only for the waiting overlay.

Impact: a current item receives another generation's request reference/origin despite H5's non-attribution rule and NPTD TR-3/TR-6's source-faithful link. Omitting waiting-on-request does not make the wrong reference correct. Original tests never call this API with stale/foreign requests and reused IDs.

Repair: bind live item/request association to the full current tuple before assigning any ref/origin. Keep historical links in explicit historical namespace/custody rather than silently attaching them to current observations. Add same-home foreign-session/old-counter references with reused IDs plus a mixed old/current list. A provisional full-tuple repair was observed but needs frozen successor backcheck.

### I1-4 [P2] Failed explicit-error writes can become acknowledgment “after written reply”

Original location: `src/native_requests.rs:382–398`.

Trigger: an unfamiliar/unsupported request produces an error; written(..., false) sets state errored with replyWriteResult write-failed. A later matching serverRequest/resolved enters the errored branch and records acknowledgment text `serverRequest/resolved after written reply` without checking that any reply was written.

Impact: the real supplier-resolution observation is promoted to evidence of a written-reply acknowledgment. RECOVERY U-09 and HOSTING RT-12/13 require **after the written reply**; failed writes cannot satisfy that guard. The projection remains schema-shaped, so schema validation alone misses this semantic false claim. Existing projection cases validate failed error writes but never follow them with resolution.

Repair: require positive written evidence before labeling a reply acknowledgment; retain the supplier's resolution separately with its actual source and uncertainty when a write failed. Add failed-error-then-resolution and successful-write-then-resolution cases, verifying exported record and durable summary labels as well as reducer state.

### I1-5 [P2] Named App-rule declines of person-input requests are refused

Original location: `src/native_requests.rs:322–337`.

Trigger: a named rule supplies the schema-valid negative form to item/tool/requestUserInput (`{answers:{}}`) or mcpServer/elicitation/request (decline/cancel). negative() recognizes it, but app_negative explicitly excludes both methods, so prepare returns origin-not-permitted.

Impact: HOSTING R9 and §6.4 allow a named App rule to **decline or error** person-input kinds while reserving content answers to the person. The implementation narrows that accepted operation contract. A rule being permitted does not authorize a timer/default decline; the repair need only preserve the callable named operation. The seven decline tests use person origin only, so they cannot establish this guard.

Repair: admit only the native negative/error forms from named rules for those methods; continue refusing affirmative/content answers and preserving exact rule attribution. Provide the known-request explicit-error path if that operation is claimed implemented; otherwise explicitly retain it as missing implementation. Test named negative versus named content/affirmative forms for both kinds and schema-check the exported settlement.

### I1-6 [P2] Recovery summaries label distinct custody events as entry-settled

Original location: `src/recovery.rs:168–189`.

Trigger: request_summary sees errored (RT-02/03) or a newly observed acknowledgment on an already closed request. Every non-listed state other than ended-unanswered gets transition RQ-03. The same generic mapping therefore writes an explicit-error receipt as entry-settled, and an acknowledgment observation as a second entry-settled event.

Impact: RECOVERY's source table requires **RQ-08** for entry-errored-at-receipt and **RQ-09** for acknowledgment-observed. These transition IDs are observation facts, not interchangeable labels. The permissive schema enum accepts the mismatch. Neither current ledger tests nor the failed-write projection test check transition fidelity across error/ack changes.

Repair: map the actual source event/transition and previous summary state; emit RQ-08/RQ-09 when applicable, with unchanged native request identity/full generation and acknowledgment semantics. Retain RQ-03 for its actual RT-07/08/09/10 settlements and RQ-04 for unanswered closure. Add connected reducer-to-ledger assertions for error receipt, written reply, acknowledgment and close.
