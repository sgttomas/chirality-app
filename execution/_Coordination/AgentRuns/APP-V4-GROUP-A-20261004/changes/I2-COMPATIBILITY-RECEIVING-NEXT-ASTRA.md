## Finding

The real workflow selection → preparation → send → panel path has no required-tool/role compatibility receiving, and no equivalent implementation was found. This conclusion comes from tracing the actual path, not from compiler unused-method warnings. `WorkflowRootSession::prepare_run` validates current conversation and exact selected store, then composes text; `WorkflowRun::send` performs source-scoped Host send. Neither creates/checks an `Environment`, calls the compatibility module, reads a declaration for this check, or obtains the conversation's RoleBinding. `lib.rs:668–681` adds home/source validation only. `WorkflowRootSession::snapshot` explicitly disclaims compatibility and returns no report. `WorkflowRootPanel` (App.tsx:261–295) offers prepare/send/check-supply and renders returned run JSON; it does not display declared requirements or role results. ## Fixed role: ready producer, missing consumer

`role_lifecycle.rs` has `RoleInForce::AppObserved {role: Option<Role>, supply_ref}` and `Unknown {reason}`. `RoleBinding::role_in_force` checks home/thread and returns the immutable original role; `RoleBindings::selected_role` returns Unknown when absent. `HistorySession::binding/role` (`runtime_session.rs:1174–1186`) exposes this owning state; HomeSession holds its HistorySession. Fork/continuation code preserves original bindings; imported JSON/native `agentRole` is not authoritative original App role evidence.

**Observed None is deliberate no-role; missing binding is unknown.** `Compatibility::check_for_role(..., None)` currently means known “no role” and marks a declared-role workflow unsupported. Passing a missing original binding through that same None would invent no-role. A consuming adapter must keep the three cases distinct: known role, known no-role, unknown role. Unknown role with applicable declared-role/delegation constraints leaves that part not established, without erasing an independently established tool failure. If roles are omitted, no role-compatibility restriction arises; an unknown role still cannot prove that a TASK delegation restriction is absent when that question matters.

Use the actual home/thread's binding and original supply reference, not App.tsx's `role` state (the new-conversation selector), current role-file bytes or native role hints. ROLE SL-7/SL-8 and EXEC §3.4 fix the role for the conversation's life; a known no-role plus declared compatible roles is unsupported; omitted compatible roles inherit compatibility; required agent-delegation with known TASK is unsupported as a stated limit, without enforcing a supplier configuration change.
