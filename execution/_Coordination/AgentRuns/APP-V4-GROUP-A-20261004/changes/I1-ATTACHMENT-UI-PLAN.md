## Source failure, drift and list atomicity

Any member failure holds the entire attachment-bearing submission: no partial native inputs/supplies or fallback person-only send. Core publishes/readbacks the full array and prepared client association before commit; orphan/prepared evidence after later failure is retained with its uncertainty, not deleted or called sent. A public success/status boolean, path/hash/title, schema alone or reminted attachment token never substitutes for complete original-source readback.

If source bytes/path no longer match, keep old selected identity/list and actual failure. UI offers **confirm current source** or **remove**, never automatic reread-and-replacement. It does not reconstruct PathBuf from a returned DTO. A change again after confirmation is another hold. Current producer has no dedicated refresh API; shared can retain its own exact picker path and call the existing source constructor for the tentative selection, or coordinate a narrowly reviewed Core method—never expose a renderer source constructor. This is not reserved-act/A15 evidence.

After preparation, remove/reorder/replace invalidates/cancels that unsent packet through the actual Core cancel result; renderer cannot rewrite original array/client/token or relabel attempted/written as cancelled. Cancellation after commit is not rollback. A newly chosen/reconfirmed list is a new explicit submission with fresh identities, not an automatic resend of an unknown attempt. Actual structured member holds are used only if returned; current Host reduces producer hold to String, so do not parse guessed member IDs from diagnostic text. If final API remains unstructured, show the genuine whole-list diagnostic and hold the list without inventing per-member attribution.

Do not report cold definite no-send/native acknowledgment/provider adoption or reconstruct payload/reply cache.
