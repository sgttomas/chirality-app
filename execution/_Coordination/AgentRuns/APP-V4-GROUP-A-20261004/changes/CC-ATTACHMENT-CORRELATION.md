## Accepted-source fit and necessary clarification

NIR AT-3 requires an attachment supply record with “the turn”, and schema 0.2 requires turnRef only as nonempty string; it does not require a native supplier turn ID. SQ-A expressly holds submission until supply records are written. A new turn/start native turn ID does not exist before its actual result, so an immutable supply record cannot truthfully name that ID at pre-send recording. A source-qualified App-owned `submission:<opaque unique token>` is coherent with the schema shape and existing pre-record promise, provided AT-3/source presentation explicitly defines it as a submission reference awaiting native correlation, never already-observed native turn identity. This is a named technical clarification, not silent reinterpretation or a changed requirement. Existing historical records keep their actual references/meaning unchanged.

No incompatible accepted promise found in RECOVERY actual-state/unknown/observer/ledger and RS reference-only contracts. Hash/native send success/adoption are distinct; preserve these. The unresolved concrete correlation persistence seam is not already supplied by the current HOSTING client-request schema: it has full generation, requestIdentity, method, positions/writeResult/outcome but no submission/thread association fields. Current RECOVERY ledger also has no dedicated attachment-correlation kind. Do not claim that RPC record shape alone supplies the missing linkage.

## Exact proposed representation and custody impact

1. App creates one unique immutable submission token and the complete ordered attachment supply list from the same composed/preflight submission, before recording. All per-attachment supply records use that one turnRef, retaining individual attachment identities and exact original facts. Finish durable record creation for the entire admitted list before native input write. Failure to record any member holds the whole submission; no partly unrecorded list is sent. Neither the token nor filename is a native turn ID, grant or act.
2. At the native send boundary retain an explicit pointer-only relation `{submissionRef, generation:{appSession,home,spawnCounter}, threadId, requestIdentity:<RPC ID>, method:turn/start|turn/steer}` to the existing client-request custody source. Do not put synthetic IDs into native supplier fields. The native request/result and existing boundary records retain their own authority. Correlation metadata contains references/outcomes only, no native request payload, transcript, credentials or attachment text copy.
3. For turn/start, admit a native turn correlation only from its actually matched native result/observation linked to that full-generation/RPC request. For steering, keep the explicit native expected-turn target actually submitted and the matched accepted/observed result; validate the result against that target. A nearby turn/started event, most recent live turn, guessed next ID, thread-only equality or same spawn counter does not correlate a submission. Keep multiple submissions to one native turn distinct, preserving the entire supplied list.
4. Native write failure, missing/malformed/error result, generation loss or absent correlation remains visibly not-established/unknown as its actual custody warrants. The immutable supply records retain what the App read/recorded, not an assertion Codex received or adopted it. Do not mutate turnRef to a later native ID, synthesize a successful turn, automatically resend, or manufacture a parallel transcript. Retries require the existing explicit person/send route and their own actual custody; no new automatic retry policy is introduced.
5. Persist/reference the relation through coordinated NIR's supply-store/custody interface or an explicitly reviewed existing pointer-metadata extension. No new RS kind is warranted: RS may link the owning source using its existing references where already within its inventory. This packet does not invent a new recovery ledger kind or reinterpret opaque receiver tags as proven supplier results. Exact representation/storage/receiver adoption must be agreed by NIR/HOSTING/RECOVERY before product-ready correlation claims. Reference-only metadata is distinct from duplicating native payloads; existing ledger recovery/readability/durability limits apply wherever admitted.
