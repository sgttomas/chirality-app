## 1. Findings

### MAJOR

**M-1 — The ADAPTER → RS token mapping fails for `agent_written_configuration` (R14-3; RS §5; ADAPTER schema; claim 3).**

What the files say:

- RS §5 "Supplier tokens" states the mapping once: "ADAPTER's
  `external_dispatch_record` values map to these words once: an underscore
  is a space, and … its evidence limits are the R11 labels with
  `app_restart_interruption` → *App-restart interruption*,
  `dedup_scope_exceeded` → *de-duplication scope exceeded* and
  `host_reachable_without_evidenced_A13` → *host reachable without evidenced
  A13*".
- ADAPTER `external_dispatch_record.schema.json` admits
  `agent_written_configuration` in `evidence_limits`.
- RS `RS_RECORD.schema.json` `$defs/evidenceLimitLabel` spells it
  "agent-written configuration", with a hyphen.

So RS's rule turns a conformant ADAPTER record into "agent written
configuration", which RS's schema refuses. ADAPTER's `observe_map.py`
(`RS_LIMIT`) follows the same rule. R14-3 ruled that "the record vocabulary
covers what its suppliers emit".

How I checked: by script, every ADAPTER `outcome.value` and
`evidence_limits` enum value through RS §5's rule against RS's enums. 17 of
18 limits and 21 of 21 outcomes map. Then I passed one dispatch record
carrying `agent_written_configuration` through `observe_map.rs_chain`: 1 of
2 entries valid, with `$.body.label: 'agent written configuration' not in
enum`.

The claimed "43 of 43 RS entries valid" is true but does not exercise this
token. SH-1 never puts it on a dispatch record; it appears only in channel
statuses.

Why MAJOR and not BLOCKING: the two files name the same limit, and only the
stated mechanical mapping is wrong. Read strictly, the brief's "inconsistent
across files" could make it BLOCKING; the integrator may rule otherwise.

Fix:
- Add `agent_written_configuration` → *agent-written configuration* to RS
  §5 and to `observe_map.py` `RS_LIMIT`, or respell one side.
- Add a mapper self-check that maps every ADAPTER enum value, not only those
  SH-1 emits.

### MINOR

**m-1 — RS §13 overstates how a JSON Schema 2020-12 validator resolves RS's cross-file references.**

RS §13, row `RS_RECORD.schema.json`, says: "Because this file's `$id` is a
URN, a validator resolves that path against the schema file's location, as
the prototype's `minischema.py` does".

A conforming 2020-12 resolver resolves a relative `$ref` against the base
URI set by `$id` (here `urn:chirality:…`), not against the file's location.
Observed with jsonschema 4.26.0 / referencing (already installed with the
CommandLineTools Python 3): the resolver asked to retrieve the bare
`../../../../PKG-02_Workflow%20and%20role%20portability/…/checkpoint-record-entries.schema.json`
and failed `Unresolvable` until I supplied a retrieval hook that resolves
the path against the RS file's directory. With that hook every RS example
validated (§3). EXEC's schema `$id`
(`chirality:del-02-03/exec-checkpoint-entry-bodies/proposed-0.6`) is not
what the path resolves to either.

Fix: say that a validator needs a retrieval rule mapping the relative path to
this file's directory (minischema has one). Or reference EXEC's bodies by a
resolvable `$id` registered beside the schema, as `settings_version`
references AS.

**m-2 — An inference in the OBS record is cited as an observation (ADAPTER §3.5; GUIDE M9.3; via R13-6; claim 1 and R13-6).**

ADAPTER §3.5 says: "**Observed limit of one route (OBS-1, R13-6; …):** at
0.158.0 with a Responses provider on LM Studio 0.4.16 and one local model,

(inference, not observed directly):** Codex 0.158.0 appears to offer MCP

as OBS-1's inference. Consider the same correction to R13-6's wording;
