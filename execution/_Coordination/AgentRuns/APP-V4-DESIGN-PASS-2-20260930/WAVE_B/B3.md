## 3. R12-9 ruling proposal — a host read that lacks workspace identity or generation (R10-5)

**The two passages** (both stand until R13):

- C-v0.8 §5.2 rule 1: "**All elements, every read.** A read lacking any
  element is *basis incomplete* and cannot be cited as a relied-on basis."
  With rule 3: "**Basis is observed, not chosen.** A consumer never fills in,
  updates or copies a later basis over it."
- ADAPTER-v0.6 §4.3 RD-2: "Every read carries its **basis descriptor**
  (workspace identity, generation, model revision, canonical content
  identity, method designation) … A read lacking any element is *basis
  incomplete* and cannot be cited for a change. … A host read with only a
  whole-model identity is received with that identity standing for every
  covered subject … Such a read satisfies RD-2 and can be cited (R8-12 item
  6; F-24). … On main SWBPIPE has no workspace identity or generation;
  DRAFT #885's `inspect` returns a basis identity (SQ-07 (a))."

R8-12 item 6 settled only the subject-identity part. The open question: is a
read from a host that has **no** workspace identity or generation (SWBPIPE
main, SQ-07 (a)) *basis incomplete*, or citable?

**Options.**

| Option | Rule | Consequence |
|---|---|---|
| **A** Strict (rule 1 as written) | Any missing element makes the read *basis incomplete*; it is never cited | Simple and conservative. Every SWBPIPE-main read is uncitable; only a host that supplies lineage (e.g. #885 `inspect`'s `basis_identity`) can be relied on. Rule 1 cannot tell a host that has no such concept from one that dropped the element by fault |
| **B** Declared absence (**recommended**) | A read lacking workspace identity or generation is citable only when (1) the host declares that it has no such element — in its basis profile (C §2.1 CI-3) or, for a host with no catalog, in a documented host statement recorded as such (B2) — and the read marks the element *host declares none*; (2) the read carries its canonical content identity with method designation; (3) the record carries the evidence limit "basis lineage not supplied". Any comparison across an event that could start a new lineage or workspace (project open or create, restore, re-import; SWBPIPE SQ-07 (f)), or where the consumer cannot exclude one, is *unknown (incomparable)*, never *unchanged*; staleness rests on the host's own check and stated scope (R8-3). An element **omitted** by a host that declares it stays *basis incomplete* | Keeps rule 1 for omissions and rule 3 (nothing filled in). Follows the R8-4 principle already applied to subject identities: receive what the host has, err toward reporting *unknown*, never compute. Needs a host declaration; B2 lets SWBPIPE's documented answer serve, as R8-4 used SWBPIPE's answers for the whole-model identity, with host joins still deferred (DECISION-3) |
| **C** App supplies the element | The App fills workspace identity from its configuration, generation from its session | Rejected: contrary to rule 3 and to R8-4 ("the App never computes identities"); an App-supplied lineage is App-assured, not host evidence |
| **D** Undeclared absence citable | Any read with a content identity is citable whatever elements are missing | Rejected: loses the difference between a host design and a host fault, and would let a defective read be relied on silently |

**Recommendation: B (with B2).** Text, if ruled: C §5.2 rule 1 gains "…except
that a workspace identity or generation that the host declares it does not
have (§2.1 CI-3; marked *host declares none*) does not make the read
*basis incomplete*: the read is recorded with the limit 'basis lineage not
supplied', and comparisons across a possible lineage event are *unknown
(incomparable)*"; ADAPTER RD-2's note is replaced by a pointer to that rule;
RS R11 gains the label. Nothing else changes. SH-1's *no lineage* profile
exercises the case (C §10.8; output above: option A "not citable", option B
"citable with limit").
