## 3. BLOCKING

### B-1 (J-1) Two schemas shape the same checkpoint entries, incompatibly

**Supplier (EXEC-v0.6 §2.4.2, §2.4.5):** "The entries are defined by the
PROPOSED schema `checkpoint-record-entries.schema.json` … One entry kind per
CE event" and "Consistency with RS as it stands (read-only): the entries are
the per-checkpoint and per-arrival content of RS R8 and the references of
RS R9." §2.7: the recorder's outputs are these entries, receiver "The RS
writer (R8, R9, R11)".

**Consumer (RS-v0.8 §13.3):** "R8 | `checkpoint_arrival`, `disposition_change`
(annotations …), `run_resumed`, `run_ended`"; §13.2: one header per entry
(`format` `chirality.rs.record`, `recordId` `rec:…`, `recorder`, `context`,
`seq`, `writtenAt`); §1: "How an App run observes an arrival and identifies
a request is EXEC's …; the element itself is defined here."

Both files say the record meaning is DEL-04-03's, and each defines its own
container, entry kinds and spellings for it. EXEC wrote against RS-v0.7,
which had no format; RS-v0.8 now has one, so EXEC's "consistent with RS as
it stands" is no longer true at element level. B2's return said so and
asked V18 to choose (B2 §4 row RS).

**Check (scratch A; EXEC's valid example, 12 entries, mapped onto RS):**


### B-2 (J-2) What counts as an identified request in an App run

- **RS-v0.8 §13.6:** "**Identified by** (PROPOSED values; how an App run
  observes them is EXEC's …): an agent message that names the act kind,
  subject and purpose; a supplier input request that names them …; the host
  loop's 'A8 request issued' event …". Schema `actRequest.identifiedBy`
  enum includes "agent message naming kind, subject and purpose". **RS's
  App-run example** (`RS_RECORD.valid.app-run.example.jsonl`, entry 0007,
  `context.surface` "App") records an act request with exactly that value
  (scratch output: `identifiedBy = 'agent message naming kind, subject and
  purpose'`).
- **EXEC-v0.6 §2.4.1 RC-5:** "The agent's request is recorded (CE-4) only
  where it is a structured item the App observes … The recorder never
  classifies agent message text as a request (RW-1; E-E). Where none is
  observed, the view says 'no request observed'."
- **ADAPTER-v0.6 §7.7** (last paragraph): "The agent's request for the act …
  is a message in the App conversation, observed by EXEC's mechanism".

Incompatible statements about one exchange. A second, dependent
disagreement: RS `act_request` **requires** `actKind`, `subject` and
`purpose`; EXEC CE-4 `request_observed` carries only `form`, `ref`,
`association` (a `item/tool/requestUserInput` names none of the three as
structured elements). The scratch mapping made a VALID RS entry only by
taking kind, subject and purpose **from the arrival**, which is inference
that RC-5 does not license (RC-5 permits associating a request with the one
current arrival, not naming its act). EXEC's `host_recorded_request` form
has no RS `identifiedBy` value.

**Which side is wrong.** RS §1 and §13.6 themselves give App-run
identification to EXEC, and DECISION-K1 K1-1 has the product record "what it
observes"; so for App runs RS's "agent message" value and its App-run
example are wrong, and ADAPTER §7.7's sentence should cite RC-5. Options for
the dependent part: (a) RS makes `actKind`, `subject`, `purpose` optional
with an explicit "not named by the request" form, and adds EXEC's forms and
the arrival association; or (b) EXEC's CE-4 is recorded only as the
arrival's `requestObservation` plus an evidence reference, with no
`act_request` entry unless the request names kind, subject and purpose.
The host-loop value ("host-loop A8 event") is not in dispute.
