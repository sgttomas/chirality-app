### 1.2 What part-level semantics implies for deliverable-level cycles

These points are inference from the texts above.

1. **The nodes and the edges are at different granularity.** The 41 nodes are whole deliverables. Each edge is part-level: some stated part of A needs some stated contribution of B. A deliverable graph is therefore a projection of a part-level graph, and projection can create a cycle that the parts lack, never remove one. A → B and B → A contradict each other only if B's contribution depends, inside B, on the part of B that needs A, and the same holds for A. The registers name the consumer's part (SourceRef: CLM/REQ/VER/OUT). They name neither the supplier part that produces the contribution nor any dependency inside a deliverable. The graph therefore cannot tell a real contradiction from a projection artefact.
2. **An SCC here marks undecided order at deliverable resolution.** Doctrine §2 rule 2 calls the SCC set the authoritative signal "of *where ordering is genuinely undecided*". Under part-level semantics that holds relative to the node granularity, which is part of what checkpoint G3 fixes.
3. **The four moves map onto this mismatch.** Decompose adds the missing resolution as part nodes, which is a decomposition change. Invert removes one direction of an exchange behind a published contract. Cut takes a row out of the objective; the row stays a register obligation. Merge accepts the coarse unit. Coordination (each case's R1) works at part level in practice, but the deliverable graph stays cyclic. Doctrine §2 rule 4 then keeps every held arc non-gating, so held arcs cannot order parallel build-out.
4. **At the accepted maturity, almost every row is a definition requirement.** 82 of 83 held rows require INITIALIZED, "defined-contract maturity only". A consumer that does not define what it receives needs the supplier's definition before its stated part. The r2 kinds apply this (K-3): the held layer classifies as I 71, V 5, P 3, L 3, E 1. The admitted layer classifies as I 85, P 39, L 3, E 2, V 0.
5. **DependencyType does not carry kind.**
   - Held rows: I rows are INTERFACE (53), PREREQUISITE (17) and HANDOVER (1); V rows are INTERFACE (4) and PREREQUISITE (1).
   - Admitted rows: P rows include INTERFACE (5) and PREREQUISITE (32); I rows include CONSTRAINT (2) and HANDOVER (5).
   - An SR-3 type exclusion therefore cannot express a kind-based objective.
   - A kind-based objective can be realised in two ways. One is recorded per-arc SR-4 rulings. The other is an objective restatement at DAG-005 checkpoint 1, applied by rulings on the affected arcs.
   - A selection rule that reads kind automatically needs a recorded kind field. Adding one changes the `dependency-extract` workflow and the register schema (SPEC §6.2), which is an instruction change needing its own authorized scope (AGENTS.md, "Execution and governance").

**How the minimum was computed.** Arcs read consumer → supplier. For every ordering of the members, the backward arcs are the arcs whose supplier comes after its consumer. The fewest backward arcs over all orderings is the minimum feedback arc set. Dynamic programming over member subsets makes this exact: `best[S ∪ {v}] = min(best[S] + #arcs v → u with u ∉ S)`.
- An arc is in **every** minimum set when forcing it forward raises the minimum.
- It is in **some** minimum set when deleting it lowers the minimum by one.
- Reversing a minimum set always yields an acyclic graph, so "reverse or reclassify" both close the component.
