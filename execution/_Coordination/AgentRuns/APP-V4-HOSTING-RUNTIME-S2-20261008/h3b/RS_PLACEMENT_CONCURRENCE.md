## Exact contract boundaries

1. **RS storage remains distinct.** RS §13.7 selects project run/writer logs under `.chirality/records/runs`, outside-run act logs under `.chirality/records/acts`, project captures under `.chirality/captures`, and library act/capture custody travelling with the library. Its failure rule prohibits silently relocating those owning records/captures to user data. The proposed Host distribution artifacts are separate source evidence, so app-data placement does not contradict that selection. It must never become fallback storage for an RS log or native act capture. A path creates no authority; an RS reference to an observation retains its own evidence kind, method, identity and write/read resolution status (§9).
2. **External exact-byte resolution.** Relative path + SHA-256 is compatible with the successor artifact shape and model resolver's relative/contained-path rule. The explicit root belongs to native host custody, not an arbitrary caller, renderer or current working directory. Preserve a recoverable association between a reference and that root. Resolve exact stored bytes before parsing, refuse escapes/aliases/unstable or substituted files, verify digest and expected artifact kind/version, and expose missing/unreadable/mismatching references without claiming successful resolution. Publishing a reference requires durable immutable bytes; failed publication cannot be reported as persisted. Shared app-data ancestry alone proves neither immutability nor stable custody. Evidence dependencies require their own explicit roots/domains if stored separately; no silent bundle-relative rebasing or mixed-domain fallback.
3. **REC namespace protections remain.** Existing `RecoveryLedger` namespace-bound operations validate protected domains, checked paths, no-follow regular single-link leaves and descriptor/name association; attachment custody obtains its root from the native integrator and rejects overlap with native homes and declared sources. A distribution sibling directory is acceptable only while those existing protections remain and the new writer/resolver protects its own domain. It must not overwrite, append to, reformat or recover through `recovery.ledger.jsonl`, native supplier stores, or existing NIR/client-request custody. Distribution cleanup must be confined to its own artifacts and must not turn retained references into falsely resolved evidence. These are retained custody obligations, not a claim that current code already implements the new writer.
4. **Separate fields are not separate generations by permission.** The exact S1 `model.py:lifecycle` contract requires `verification_generation == observed.generation`, and also `legacy_event.generation == observed.generation` whenever the legacy generation is non-null. REC §1 says no actual spawn means no custody generation: omit optional references or do not emit generation-required custody/ledger events; never synthesize counter zero or borrow the previous tuple. Keep the legacy event unchanged. A pre-spawn verification attempt may retain its separate verification metadata without becoming live child/REC custody, but when attached to a non-null live event it must join that exact full H5 tuple. If H3B intends unequal non-null tuples or invented pre-spawn REC events, that is a concrete objection under existing contracts, requiring repair rather than this concurrence being used as a waiver.
5. **Standing is not promoted.** Observation, expected reference, attestation, selection and package remain distinct kinds/domains. Without S3's qualified pair and integrity/stable-custody evidence, the observer remains unavailable/unverified as briefed; exact-byte equality cannot produce qualification, human acceptance or a performed act. Contradiction precedence, closed legacy shapes, full H5 session/home/counter semantics and no transfer across generations remain intact.

## Final representation determination — reference-check transport evidence

**CONCUR: a separately versioned transport-manifest evidence artifact referenced by `checks.reference.evidence` is faithful to the existing S1 representation; no S1 schema successor is needed for this bounded use.** Direct inspection confirms that this field is either null or the closed `{path, sha256}` artifact reference. The target bytes have no prescribed payload schema there. S1's model resolves those bytes without a requested payload kind, while independently resolving and validating the expected-reference/attestation pair. Therefore original source locator/digest, distinct mirror locator/digest, preserved relative layout, original immutable compiled-selection association, and actual copy/use verification observations can live in the external evidence payload without adding properties to S1 or redefining an existing S1 field.

The new evidence payload should have its own named version and reviewed producer/reader meaning (for example `distribution-transport-evidence.v1`), under this named H3B change. That is an evidence-artifact contract, not a successor revision of `observed-verification.s1`. Do not put the additional facts directly into the closed S1 artifact reference or check object. Do not claim that historical S1 readers validate this payload's internal semantics: the existing model checks its exact bytes, not the authenticity or correctness of transport claims. The actual H3B producer/consumer must perform those checks independently before any reliance; digest resolution alone is insufficient.

Required meaning and checks:

- Preserve each original source locator and selected digest separately from its mirror locator and verified digest; retain the original unchanged reference objects and single-base relative layout. Record the compiled-selection digest and independently established build association; neither the mirror nor its manifest issues trust or supplies an authoritative replacement for the compiled anchor.
- Verify every copied artifact against its selected/linked exact-byte digest during creation **and on every subsequent reliance**. Revalidate the immutable selection association, relevant reference closure, no-follow containment, regular-file/alias checks, descriptor stability and custody at use. Use atomic publication with collision refusal; never rewrite selected artifacts or requalify mutable app data.
- A manifest can attest only to verification actually performed. A creation-time manifest cannot establish future use checks. Later reliance must perform fresh checks; when recording a new use observation, publish a new immutable evidence artifact/reference or reference separate immutable actual-use evidence. Do not update an already digest-bound manifest in place or invent future successful observations.
- Retain the full meaning of the `reference` check. A successful copy is not a passed qualification/reference-trust check. If qualification or trust is unavailable, keep `missing`/`unverifiable` and a truthful reason even when transport evidence resolves. Known mismatches stay mismatches. The manifest may explain/carry supporting evidence for the complete reference check; it cannot replace the pair, required acquisition/review/adoption evidence, or the distinct custody check.
- Preserve acyclicity: transport evidence may cite original selection/artifact hashes and already-performed checks, but must not embed the digest of the observation that points to it, its own digest, or the final package digest as a self-binding requirement. An observation then references the frozen transport evidence; lifecycle references the frozen observation.

A named reviewed successor would be required if the implementation instead changes S1's relative single-root interpretation, adds fields to its closed shapes, weakens complete attestation subject equality, changes generation joins, or claims that a transport manifest itself replaces the existing qualification/trust requirements. None of those changes is necessary for the proposed payload use. This determination adds no human gate and makes no qualification or completed implementation claim.
