# LT23 asynchronous design backcheck

Verdict: core design is suitable; one narrow terminal-status refinement remains REQUIRED before bounded implementation release. Parent retains release and source-owner concurrence remains pending. Exact proposal SHA-256 d6fcd9cf84cb586ee88acd569b375a4a05fbacde3081f8abd87e84d50c337921; source basis remains f25ba6887d85904ebef2a6321c222809d47cfabd and the prior read-basis hashes.

The detached single App-custody permit resolves the synchronous Stop-return objection. No Store/namespace IO or worker wait occurs in Stop scheduling; closing serializes only against in-memory installation, and one stuck worker cannot multiply across home/Host reopening. Closing before Exit Stops and defensively before REC session-end is concrete. Its admitted consequence—one retained permit/closure and possible retryably busy namespace admission while IO remains blocked—is explicit without claiming cancellation or a filesystem deadline. Restart invalidates source installation instead of joining the worker.

## Required refinement: terminal completion must settle pending even on panic

The proposal requires unwind-safe permit release but does not specify status settlement when publication panics. Releasing the permit alone leaves a still-current source reporting pending forever although its only worker terminated, contradicting the stated pending-until-completion meaning. Add a panic/failure completion path (or native finalizer) that, after dropping Store/namespace leases, acquires controller then Inner and changes matching pending to unavailable. Preserve exact event/attempt/H5 token and closing checks; stale or closing completion cannot mutate the source. Do not put this installation in a destructor that runs while Store guards remain held. If process abort occurs, no live completion guarantee is possible and none should be claimed.

Make initial pending publication part of that same state machine: reserve it before a worker can complete, never assign pending after successful spawn returns, and let spawn failure settle only the exact reserved token. This prevents a fast success/failure from being overwritten by the scheduling thread. Add deterministic immediate completion and worker panic controls asserting both released permit and correct current evidence status, not only availability for another job. These are small completion-path requirements within the existing fence, not a new queue/index/framework.

## Remaining implementation obligations, no additional design choice

Controller→Inner order is acceptable if every emission releases Inner first and evidence projection does not acquire controller beneath Inner. Closing projection must report unavailable/disabled for any old pending job without blocking on it; worker Store lease must be gone before installation. Test closing contending with a short installer separately from a blocked worker. Keep busy/spawn-refusal source updates token-scoped as well as successful completion.

At every actual successor LT23 emission reserve sequence even when ineligible. Installed-LT09-only eligibility, immutable original observation, preserved legacy event and full-H5/source/sequence compare remain appropriate. No claim of zero survivors or terminal integrity can be derived merely from LT23/state stopped. Same-H5 semantic reader mapping and single-envelope closure need no schema weakening; RS concurrence must cover the named producer extension. Existing native stopped read retains full exact-byte and namespace checks; pending is never durable evidence or a restored capability.

No code, tests, build, native/supplier action, downloads or MEMORY writes performed. Continuing independent harness-native TASK under hosting manager, no delegation. Prior source inspection and selected software-code-review basis reused. After this completion-status refinement and owning concurrence, this design can be released for bounded implementation and exact deterministic review.
