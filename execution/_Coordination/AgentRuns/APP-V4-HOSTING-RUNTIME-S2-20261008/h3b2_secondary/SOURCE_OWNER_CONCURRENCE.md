## Examined gap and design fit

`lib.rs:add_api_key` prepares the key namespace and commits returned namespaces to App state, replaces attachment custody, then constructs a new key Host sharing AppRuntimeCustody. It does not configure the new key Host's distribution Store. Existing Store has an immutable `Arc<NativeNamespaceBindings>`; its `guard()` and `generation()` consult that retained binding. Thus replacement of the App state's binding does not expand existing Store protection to newly admitted native sources, and a newly created key Host has no Store.

`runtime_session::prepare_native_key_namespace` currently preflights REC/attachment geometry, prepares the key resources, reconstructs and checks actual namespaces, then binds REC. Distribution is absent from both preflight and commit. `Host::configure_distribution_store` simply replaces its Store slot; `distribution_evidence` retains native-held references and checks generation/start-attempt stability around reading. Store pins root device/inode, vendor exclusion and selected source association; S1Reference retains private files and publication identity that are not serialized capabilities.

ACCESS §3 establishes separate H-acct/H-key native credential/thread custody, shared linked resources, one process per home and full generation identity. REC §1 preserves full session/home/spawn identity, no cross-home attribution, and no custody generation without actual spawn. RS §9 makes resolved evidence identity distinct from source authority; §13.7's owning project/library logs and captures remain separate from this distribution evidence placement. Namespace expansion changes protective scope, not record identity, home identity, supplier qualification or ownership of previous evidence.

## Required invariants and implementation fence

1. **Full-set preparation before admission.** Check every existing Store and every new Store's proposed geometry against the full proposed native namespace, including account/key/probe homes and declared linked resource sources. Keep existing root identity, vendor and selected-source exclusions, permissions, no-follow/alias checks and generation-membership checks. Missing Store/errors need explicit unavailable status; never silently treat omission as safe. Preflight before key-resource materialization where possible; repeat against actual post-preparation namespaces before commitment. Do not mutate Store bindings or publish newly admitted capabilities merely to test geometry.
2. **One coherent admission outcome.** REC currently binds inside prepare_native_key_namespace. Therefore merely adding fallible Store rebind/open calls after that function returns does **not** satisfy “failed admission preserves old bindings.” Integrate Store preflight and prepared replacement into the admission transaction, with coordinated commit/rollback or a single stable shared native binding holder switched only after all required components are ready. No admitted key becomes usable while account Store retains the old protective set. Serialize namespace changes against Store publication/read and relevant setup, or revalidate a binding epoch before operation completion. `key_setup` alone excludes duplicate key setup, not necessarily concurrent account evidence operations. Lock ordering must preserve existing REC/Host writer ordering and avoid blocking/cyclic callbacks.
3. **Preserve actual evidence capabilities.** Rebinding retains the same publication-root device/inode, location, selected trust association and native-held reference objects; neither recreate the root nor mint replacement references from displayed JSON. Existing observations/transport manifests/digests and generation tuples remain immutable. If choosing replacement Store objects, prove they preserve the original root identity and selected association and that all holders performing operations observe the admitted binding; stale Arc handles must not remain a use path under reduced protection. Replacing only the Host slot is insufficient if in-flight operations continue with old guards unchecked.
4. **New key Store is established before dependent use.** Configure it with the admitted full namespace and the same production selection rules before starting a distribution-dependent key Host. The same external root may be shared if existing collision, unique-publication and full-generation rules remain intact; it does not merge account/key observations. A key-home operation never borrows account generation, reference or qualification. Existing key-home replacement follows the same preflight rules and retains history, as ACCESS requires.
5. **Failure is truthful.** Pre-admission failure leaves previous committed binding/evidence usable at their original standing; retain old native-held references. If preparation already created native resources before a later failure, record that actual partial state rather than claim no filesystem action occurred. Do not automatically delete resources, roll back a human credential act or discard evidence. If a binding commit partially succeeds, do not report “original bindings retained”; either reliably restore all owned bindings before exposure or refuse affected use with explicit partial/unavailable status until coherent recovery. A store-root substitution is a refusal, not an opportunity to reopen a fresh root and continue.
6. **Creation and every reliance remain checked.** No namespace rebind substitutes for exact-byte source/mirror validation, compiled-selection authority, descriptor/path stability or full S1 semantic validation. Bindings must be native-owned and must cover current actual source geometry; they are not JSON capability inputs. Do not promote unavailable S3 qualification or installed custody to verified. Keep observation/attestation/selection/act standing distinct.
7. **Restart hydration remains separate.** This method updates live native-held capabilities within the current App session. It neither reconstructs capabilities from serialized references nor proves retained artifact discovery, fresh-session source custody, generation recovery or credential discovery on restart. Do not silently close that residual in this tranche.

## Ownership and review requirements

Choice of synchronization/shared-holder versus prepared replacement mechanics is an implementation-owner decision within the above semantics, not a new human gate. Root setup owns admission sequencing; REC owns shared ledger/writer custody; ACCESS owns home/account routing and actual key acts; distribution owner owns Store authority and root preservation. Coordinate any change to those existing APIs/semantics within the named reviewed fence. Human-reserved credential acts, qualification, restart-hydration expansion or canonical contract change remain outside this assessment. No new human decision is needed solely to add missing Store participation in the existing admission.

Independent review on the implemented revision should establish: account evidence still resolves after successful expansion; key evidence works under its own full generation; collision with an existing distribution root is refused before admission; actual linked-source drift is caught after preparation; failed preflight retains old bindings/references; injected late failures never yield a falsely successful or falsely rolled-back admission; concurrent reads/publication cannot escape through an old binding; replaced root/inode refuses; unsupported JSON/restart rehydration does not create capabilities. These are required evidence targets, not tests performed by this assessment.

## Addendum — concrete author plan assessment

Read `/private/tmp/H3B_SECONDARY_HOME_PLAN.md`, SHA-256 `335bb60db21b95647305d6b4c02206cf705f07e7cdb349f1bb8b53320144bc32`. **Concur with this as the bounded implementation plan**, with the following precise scope reading. It directly addresses the discovered REC-before-Store failure and old-Arc bypass: shared Store binding read leases covering the full operation, nonblocking exclusive admission, a prepared proposal bound to old state/root/selection, fallible checks before a narrow Store+REC commit, and truthful post-admission setup failure are faithful to the retained evidence semantics. Sharing an admitted Store with a key Host is acceptable only where vendor/selection/root associations are identical and generation checks remain per home.

The proposed fence remains ordinary implementation of existing protective namespace admission; it does not choose a new global identity algorithm, storage location or human act. No new owner-held human choice is identified. Parent implementation-owner/source-owner coordination must settle the exact lock order and commit boundary before authoring; those are concrete engineering choices, not an extra approval gate introduced by RS.

The narrow transaction must be described as **Store+REC binding commitment**, not whole-App atomic admission. Existing immutable attachment capabilities and AppState projections are not automatically synchronized by a Store lease. The author's plan correctly names this limitation. A scoped implementation can preserve the existing Root sequence without claiming it fixes unrelated historic attachment races, provided review shows it introduces no new window, exposes no new key operation before the required Root capabilities are installed, and never rolls back or mislabels the committed Store/REC state after a later failure. If existing attachment use can access a newly protected distribution/native domain through stale bindings during the proposed sequence, or if a required invariant needs simultaneous attachment replacement, return that concrete case for a narrowly expanded coordination fence; do not hide it behind a successful Store test.

The nonblocking exclusive lease may refuse key admission while account evidence use is active; report that as retryable setup contention, preserve existing work, and never terminate a turn or drop evidence to obtain the lease. Avoid recursive lock acquisition and prove no opposing REC→Store path before adopting Store→REC order. All fallible final checks must precede either committed assignment; a prepared object is not permission to skip use-time physical checks. No tests have yet established these properties.

I support preparing the key capability ahead of commitment and labelling later Host/router failure as post-admission setup failure. Whether a prospective Host can be safely prepared before commit depends on its actual source-registration side effects and must be checked in implementation. This report does not authorize materializing a native key home outside the existing explicit user key action or starting a supplier during testing. The existing merge/review implementation hold remains in force.
