## Confirmed mechanism

`lib.rs:submit_attachments` clones the account attachment slot before submitting. `AttachmentCustody` stores immutable `Arc<NativeNamespaceBindings>`; scope/generation/leaf guards reobserve only that retained finite home set. Slot replacement in `add_api_key` does not revoke escaped clones. `Host::prepare_attachment_turn` additionally retains the custody in PreparedAttachmentDispatch and AttachmentLink. `dispatch_attachment_turn` checks it twice, and `persist_attachment_observation` later reuses it. Thus new key-only resource drift can be invisible not only at publication but during dispatch checks, cold resolution and outcome persistence. This is source-reachable reasoning, not an executed reproduction or arbitrary-write finding.

The current complete binding already reobserves declared resources and refuses wrong/missing links, aliases and missing home membership. This proposal changes how a live capability finds the current complete protective set; it does not broaden attachment paths or change immutable evidence identity.

## Proposed narrow contract

1. Root owns one stable live native namespace authority with an epoch, shared by Store and all production attachment capabilities. Its committed binding is the full finite Root descriptor set; no serialized snapshot, unbound fallback or caller safety Boolean may replace it. REC's binding must commit coherently with that authority. Existing clones resolve the same authority on every operation. An epoch-pinned variant is acceptable only if stale clones refuse before reliance and callers obtain a new native-issued capability; simply polling an epoch before a write is insufficient.
2. Every attachment metadata publication, check, mutation and cold read obtains one operation read lease spanning all protected filesystem reliance. Nested path/guard/check methods use the already-held lease. Do not reacquire recursively. A path returned by a helper is not a durable authority token. Existing root/leaf identity, no-follow, typed generation and source-list validation remain required.
3. Dispatch takes a fresh lease after any prior lease was released and holds it through final durable check, original-generation/source validation and actual native write reliance. A namespace admission cannot slip between the last protective check and that reliance. Preparing a request does not freeze the protective set indefinitely: a prepared packet dispatched after admission rechecks the new set, preserving its original immutable request/list identity. Admission while such a lease is active refuses as retryable contention; it never waits for or terminates the turn. The lease may cover blocked IO only because admission is nonblocking and Stop/EOF do not acquire its exclusive side. Required native reply and Stop liveness remain unchanged.
4. Proposed admission: prepare prospective REC, Store and attachment geometry before home materialization; prepare actual home resources only in the existing explicit key act; reconstruct and validate actual complete set. Prepare all capabilities/root associations before publication. Try the shared authority exclusive lease first; busy refusal precedes REC mutation. Then acquire REC writer and existing bounded preflight locks. Recheck expected epoch, Store root/selection identity, actual namespace geometry, attachment domains and REC admissibility. Complete every fallible check before assignments. Commit REC binding plus authority/epoch without a fallible step between them. Publish Root projections/capabilities before making the key HomeSession usable. Post-commit Host setup failure is post-admission failure, never “original bindings retained.” Failed precommit leaves the prior authority, REC, references and epoch intact; actual already-created resources remain truthfully reported.
5. If Store and attachment retain separate lease cells, admission must acquire both exclusively in fixed order without waiting, before REC writer; release both on any failure and commit both while held. A single shared authority is preferred because it eliminates a partial protective-set window. This preference does not require migrating all REC operations to new locks: if that would add writer→authority edges, retain REC's binding under its existing writer and coordinate only its commit.

## Lock consequences requiring implementation proof

Observed attachment dispatch order is frame serializer → custody file lock → attachment_gate → Inner, with the gates/source lock released before blocking pipe IO; metadata preparation/persistence release Inner before file work. Admission currently takes REC writer → source registry/Inner and ledger locks. Store audit reports Store reliance outside REC/Inner.

Place the namespace read lease outside attachment custody/file locks and before frame serialization for dispatch; pass it down. Admission takes authority exclusive → REC writer → existing source/ledger locks. Never acquire frame serializer, attachment_gate or attachment file lock under the admission writer. Never acquire authority read while already holding REC writer unless the entire REC locking design has been separately audited/reordered. In particular, blindly putting a shared lease inside every REC guard creates a possible reverse edge and is not concurred. A retained lease must not force Stop/EOF onto admission locks or preserve lifecycle gates across blocking writes. Keep expensive source hashing outside REC writer; bounded physical reobservations remain filesystem observations, not a snapshot guarantee.

`Host::resolve_attachment_submission` at current source lines1721–1724 first resolves cold metadata, then requires `Arc::ptr_eq(custody, &a.custody)` for its hot overlay. A replacement slot capability therefore does **not** restore old hot joins: the new capability can return only the truthful cold historical view; the old one refuses the new epoch before reading. Existing source-request/attachment-wait evidence can still retain the actual original live facts. Concurrence expressly excludes any claim of automatic restoration or promotion of that cold record. An implementation test must cover this exact pointer mismatch and prove the cold fallback cannot assert current no-send, current successful outcome, or live native authority. The persistence method acquires its own operation lease and may now refuse stale epoch. A hidden retained outer read guard would cause recursive acquisition and could defeat the intended admission/persistence schedule. The implementation must preserve in-memory completion/outcome even when this separately leased persistence refuses.
