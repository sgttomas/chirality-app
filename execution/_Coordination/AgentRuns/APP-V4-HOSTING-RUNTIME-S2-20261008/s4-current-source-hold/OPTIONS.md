## Option A — fixture-only owned direct children across the complete path

Scope candidate: an explicitly cfg(test)-reachable capability minted only by constructing an exact reviewed no-fork/no-exec fixture helper; not a boolean on arbitrary HostConfig, caller-selected executable or stock supplier. Keep production group behavior unchanged and held. Two real direct processes (probe and App-server mock) would be separately owned; no real descendants or group operations permitted. Source-created fixture provenance is the basis for no-descendant fixture scope, not a runtime census of arbitrary processes.

Every actual Child, from spawn until final reap, needs one exclusive custody owner. No raw numeric signal entry, competing Child alias, alternate wait/try_wait or EOF reader reap outside that owner. A positive direct-child signal can only be considered while exclusive original waitable lifetime is proven; no signal after any reap, failed custody proof, foreign/automatic reaping or ambiguous owner. A mutex/H5 alone is insufficient. Platform process-lifetime and SIGCHLD/reaper assumptions must be evidenced and independently accepted for this narrowly controlled harness before execution. Do not infer them from the old successful WNOWAIT run.

Required path inventory before code: immediately postspawn setup; stdout/stderr extraction; fcntl failure; label timeout/output/encoding failure; main allocation/admission failure; install/handoff; handshake error/timeout; stdout EOF before process exit; exit before EOF; Stop input closure; concurrent Stop/EOF; error after terminal publication scheduling; test panic/unwind and harness shutdown. All must retain the same original Child owner. Drop cannot simply detach a live or unreaped child. No unconditional numeric cleanup, no parked forever failure branch presented as bounded, no kill-after-reap or fabricated zero survivors. Cleanup failure must return an explicit unresolved fixture and prevent further process tests; how a test process safely terminates without abandoning responsibility is an unresolved acceptance condition, not a suggested unbounded keeper thread.

What it preserves if that complete design succeeds: actual OS spawn/config/env/label-pipe observation, actual mock handshake/frame path, Host start admission, actual live Store reader/publisher, actual direct-child EOF/exit, Stop-triggered terminal-worker publication and exported closure. What it does NOT preserve: production group signaling/census/H11, stock supplier identity/behavior, installed custody or native qualification. LT23 fixture descendant fields would require an explicit reviewed fixture-only semantics/source warrant for the no-descendant instrument; a direct-child completion must not masquerade as execution of production whole-tree cleanup. The producer method/receipt must name this changed test route. Existing receiver/cohort acceptance is a B-owned decision, not automatic format compatibility.

Estimated fence is not a two-line probe repair: hosting_successor.rs probe cleanup plus hosting.rs start failure/handshake/on_eof/Stop child-operation seams and private fixture ownership/tests. It reaches held lifecycle paths even if production branches remain unchanged. Therefore NOT implementation-ready and not the recommended smallest increment. If necessary, return a separate precise design, exclusive-wait proof and error disposal policy rather than reviving Route B wholesale.

Run only focused reviewed tests, default and successor feature states where applicable. No broad test pattern reaching held process fixtures.
