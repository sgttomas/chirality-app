## Closure and exit-fact custody

`close_generation` drains pending clients, marks eligible rows unknown-no-response, calls execution-custody close then persists its facts, loses OAuth observation, closes the request register/persists summaries and marks turns observationEnded. `ExecutionCustody::close` validates full H5 and deduplicates with its closed set: later Stop does not overwrite the first supplier-exit cause with supplier-stop. `RequestRegister::close` closes matching entries and counts only entries still outstanding; repeated close normally returns zero newly ended entries. Pending client counts similarly drain once. A later LT23 zero count cannot mean there were no unanswered requests at the earlier EOF. Preserve original closure events and historical request summaries; do not replace first counts with later zero or sum counts blindly.

No valid generation means execution-custody close emits no event, consistent with REC §1 no spawn/no generation. Register close is less strict and can mark its internal closed set using a null retained generation; this is not proof a native child existed. Repair must avoid treating a no-child Stop as generation closure merely because some internal methods tolerate null or historical values.

Ready EOF closes and writes LT12 with actual exitCode/signal, receipt position, malformed count, stderr bytes and first closure counts. It does not append `class:exit`. Stopping EOF appends that journal entry and notifies Stop. Later Stop-after-LT12 searches only `class:exit`, may wait its existing deadline, then uses null exitCode/signal; it adds forcedAfterGrace and descendant outcome. Thus LT12's known exit facts and later Stop's missing exit facts coexist today. Do not synthesize a new observed exit or declare those fallback nulls recovered. A future source-owned immutable exit receipt could preserve facts without reopening a closed journal, but that is a concrete repair design to review, not authority granted by this diagnosis.

Start increments attempt and enters verifying without clearing old generation/child_pid before actual spawn installation. A fresh verification has no H5, while a later attempt may retain prior H5/PID. A no-child Stop must not close/kill a prior generation as the current attempt, allocate a counter, infer zero descendants from `pid=None`, or emit `tree-ended` on absence alone. Numeric PID/group reuse is a source-identity risk in acting on an already-reaped child; this assessment identifies the stale-ID path, not a reproduced wrong-process signal.
