### MAJOR

**M-1. The owner's L-4 multi-entry registration cannot pass through the act
control: WR and AAC disagree on its shape, wording and reviewed-content form.**

- **Where.** WR-v0.2 §4.7 ME-3, §2.2 ID-3, §4.3 RB-4a and the schema's
  `$defs/a15_multi_descriptor`. AAC-v0.2 §1.2 (A15 row), §2 AI-2, §4.2 step 2,
  and the `aac.offer.schema.json` / `aac.capture-evidence.schema.json`
  `reviewedDraft.draft` patterns and `wording` enum.
- **What each side says.**
  - WR, ME-3: "One `a15_multi_descriptor` goes to DEL-01-04's act control,
    wording 'register workflow revisions'". The schema has one
    `descriptor_id` per act. Each entry carries `reviewed_entry` matching
    `^entry:(project|user):[^@]+@.+$`.
  - AAC, AI-2: "One or more A15 descriptors (WR-v0.1 RB-4, `a15_descriptor`;
    L-4: one per entry)". §4.2 step 2: "on several reviewed drafts at once
    (L-4)". The offer schema requires `descriptorId` on each entry. Its
    `wording` enum has only "register workflow revision". Both AAC schemas fix
    `reviewedDraft.draft` to `^draft:(project|user):[^@]+@.+$`.
  - RS-v0.9 already admits both forms: `^(draft|entry):(project|user):[^@]+@.+$`.
    WR RB-4a still says RS "does not yet admit WR's `entry:` form". That
    sentence is stale.
- **Check.** I took the valid two-entry A15 instance from
  `aac.offer.example.valid.json`, and the valid instance from
  `aac.capture-evidence.example.valid.json`, and changed only each entry's
  draft string to the `entry:` form. The installed `jsonschema` (4.26.0,
  Draft 2020-12) rejected both instances: "'entry:project:supports-adjust@…'
  does not match '^draft:(project|user):[^@]+@.+$'".
- **Why it matters.** DECISION-L L-4 (A, clarified) says library entries
  without a registration record are "registered in place, several per act
  allowed". R19-4 asks for "a multi-entry registration act (each entry's
  bytes bound; DEL-01-04's act control offers it for A15)". K-8 makes the act
  control the only capture path. As the files stand, the act control cannot
  compose an offer or capture evidence for the case the owner decided:
  - its formats refuse the reviewed content;
  - it expects N descriptors where WR sends one;
  - its wording enum lacks WR's fixed wording.

  AAC also reads L-4 as "several reviewed drafts", which is not the in-place
  library-entry case L-4 decides. Each side's prototype passes only against
  its own reading. AAC K-12b/c uses `draft:` strings; WR P-46/P-47 checks
  against an RS projection, not against AAC's schemas.
- **Fix.**
  1. AAC adopts WR's multi-descriptor: one descriptor identity per act, with
     entries listed under it.
  2. Widen both AAC patterns to `^(draft|entry):(project|user):[^@]+@.+$`, as
     RS-v0.9 does.
  3. Add "register workflow revisions" to the wording enum.
  4. Reword AAC §1.2, AI-2 and §4.2 step 2 for in-place library entries
     (LS-2).
  5. Add a cross-check case that validates a WR `a15_multi_descriptor`
     projected into an AAC offer.
  6. Delete WR RB-4a's stale sentence about RS.

**M-2. NIR's attachment design rests on a supplier fact that OBS-3 W-3
contradicts: `mention` supplies nothing to the model at 0.158.0.**

- **Where.** NIR-v0.2 §6, opening paragraph: "`skill` {name, path};
  `mention` {name, path}. The supplier reads a path itself." Also AT-3, AT-8,
  AO-1, and `nir.attachment-supply-record.schema.json`: `suppliedAs` includes
  `mention` and `skill`, and `supplierRead` is fixed to "not observed: Codex
  reads the path itself". The valid example supplies `load-table.csv` as
  `mention`.
- **What the observation says.** OBS_3_0.158.0.md §5, capture-only items
  c7, c8, r3, r4 and r9: `mention` with `WORKFLOW.md`, with the `SKILL.md`
  copy, and with the discovered skill's canonical path was "accepted; nothing
  reached the model (neither the bytes nor the path; only the text message)".
  A `skill` input works only for a discovered `SKILL.md` at its canonical
  path (W-1). R19-7 itself relies on this: "`mention` supplies nothing".
  NIR-v0.2 lists OBS-3 among its round-2 inputs but does not apply W-3 to §6.
- **Why it matters.** This is checks (3) and (4). At 0.158.0 a non-media file
  attached by `mention` never reaches the model. Yet the App would write a
  supply record that implies Codex read it: "Codex reads the path itself" is
  stated as a generated-types reading and overtaken by an observation in this
  run. The K-7 trial path (AT-8: "a message or attachment the person sends";
  form `draft-package`) has the same gap for any attachment route other than
  inline text.
- **Fix.**
  1. Cite OBS-3 W-3 in §6. Label `mention` "accepted; nothing reaches the
     model (observed, OBS-3, 0.158.0)", and `skill` "only for a discovered
     `SKILL.md` at its canonical path (W-1)".
  2. Choose a carrier that reaches the model for non-media files: inline
     text, or the path named in the person's text for the agent to read with
     its tools. Record the supply truthfully for whichever is chosen.
  3. Make `supplierRead` per form rather than one fixed sentence.
  4. Replace or relabel the `mention` example.
  5. Restate AT-8 to match.
