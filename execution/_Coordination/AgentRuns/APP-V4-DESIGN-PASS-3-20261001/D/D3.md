### 1.1 Main design choices

1. **Cards are a pure function of the register entry.** Every HOSTING
   register row maps to one card state; the card never holds an answer as
   authoritative, so reload and window close lose and answer nothing. Words
   keep write attempt, written, acknowledged, resolved by Codex and ended
   unanswered apart.
2. **Exact native forms.** A request's `availableDecisions` is offered
   exactly (OB-5 shape); otherwise the generated forms; amendment forms only
   when proposed; `timed_out` never. App words for tool permission never use
   accept/approve/approval/approved; native values are shown verbatim beside
   them.
3. **Explicit decline per kind.** Native negative forms where they exist; for
   the two kinds without one (`item/tool/requestUserInput`,
   `item/permissions/requestApproval`) a PROPOSED empty answer / empty grant,
   effect not observed. Under `untrusted` the only negative command form was
   `cancel`, which per the supplier's description also interrupts the turn;
   the card says so.
4. **No automatic decline, ever** (R17-9); supplier resolution shown as
   Codex's. **Secret answers** are never kept readable after the write.
5. **Outcomes only from observation**; an interruption is never "stopped";
   descendants are never implied finished; DEL-01-02's outcome labels are
   shown with Codex's own status beside them after relaunch.
6. **Start display (K-3):** "No model selected" until the person chooses;
   last explicit choice offered as a button, never applied.
7. **Attachments:** identity taken at selection and again when the turn input
   is written; a change or a missing file holds the item; "what Codex read"
   and "provider adoption" are always "not observed"; AO-1/AO-2 left open
   (TBD-003).
8. **Draft view** shows WR's states; refuses *registered* without the A15
   record and revision, and any local transition.
9. **App act control:** one kind, one subject, bound to the bytes shown; a
   standing facility opened only by the person; capture only from a
   host-owned **native confirmation** (P-2, PROPOSED), never from a webview
   button alone; **SEAL-2** (a key held by the signed App in the OS key store)
   PROPOSED so a reader can tell App captures from bytes another same-user
   process wrote; the limits that remain are stated. A15 offers come only from
   D5's descriptor; the act is recorded at capture; registration follows.
10. **Identity (K1-4):** name set in the App (a setting of the act control,
    assigned here), OS account, Codex account as DEL-01-05 reports it; always
    "identity not verified". The card's actor reference uses the same sources.
11. **Display placement (R17-7):** run panel and act log in the App host
    DEL-04-02's K-5/K-6 with EXEC SD-1…SD-5; nothing is modal or notified on
    an arrival. One INTEGRATION reading is returned (U-NIR-5): opening the act
    control from an arrival row by the person's click is not a reaction under
    EXEC RC-4.
