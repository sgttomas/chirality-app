# S1 offline distribution successor candidate

**PROPOSED ONLY. No technical adoption, supplier qualification, App qualification or release.**
These files answer the bounded CC-HOSTING-DISTRIBUTION-01 S1 assignment. They do not edit any accepted contract, schema, source pin or maintained consumer. Every fixture is synthetic; its pass means only internal consistency of supplied values.

## Contract surface

- `expected-reference.s1.schema.json`: immutable archive/acquisition/extraction reference, complete inventory, pin/platform, direct-vendor launcher, maintained generation identity and source correspondence. Independent review/adoption are deliberately outside these bytes.
- `adoption-attestation.s1.schema.json`: immutable review/adoption record bound to exact expected-reference bytes. Reviewer differs from author; reviewed revision and evidence are explicit. Acceptance of this proposal must explicitly adopt this separation from the staged prose's earlier embedded-review fields.
- `observed-verification.s1.schema.json`: complete observed inventory or visible absence; expected/attestation refs or visible absence; raw and parsed label; generated identity; launcher/configuration; five evidenced checks; generation, phase and timestamp; outcome and limits. The label parser is `codex-cli-space-version-v1`: exact `codex-cli <major.minor.patch>` with optional final LF. A future label syntax needs an explicit successor, never heuristic acceptance. `candidate_subject` may be null for an isolated reference probe, but a PKG-linked runtime observation must identify the exact App revision/build, package-record ID and pre-notarisation installer byte digest.
- `lifecycle-event.s1.schema.json`: an envelope around the unchanged v0.9 lifecycle schema; all properties, required fields and conditional rules survive. Definitions are hoisted unchanged to preserve their local references; original source path/hash and derivation are recorded. `verification_generation` binds an allocated verification attempt even when the original pre-spawn event has null generation. A started child uses that same generation. Early events may carry null verification, never LT-04, LT-24 or a verified claim.
- `pkg-identity.s1.schema.json`: an envelope around unchanged PKG-v0.2, including signatures, Option A/B, configuration and FP fields. Full published/packaged inventory artifacts supplement old summaries. `distribution_status` is `reference-equal`, `unverifiable`, or `mismatch`; it describes the static distribution comparison, not FP-2/W-4. Runtime observation is optional while assembling the package identity. Missing reference/inventory evidence remains `unverifiable`; known mismatch dominates. Option A remains representable under its old escalation and entitlement rules, but changed stock bytes cannot become reference-equal.
- `inventory-artifact.s1.schema.json`: digest-bound complete inventory artifact.

All artifact references use local relative path plus SHA-256 of exact file bytes. Resolve and hash bytes before parsing; whitespace reserialization changes identity. Unknown schema versions are rejected. Referenced evidence may be any byte format. No `qualified: true` field is accepted. Evidence content review and authority remain outside this pure model; file existence and matching digest alone never establish qualification.

## Trust and identity boundaries

The prototype's `selected_attestation_sha256` argument models a trusted selection **already established by the consuming build**. It is not an App caller-controlled production argument. S2 must supply an immutable build-selection document containing method/schema identities and exact expected/attestation artifact digests, with the selection document's exact-byte digest compiled into the App executable from the reviewed source/build recipe. Production checks compiled anchor → selection bytes → expected and attestation bytes. A resource path, environment value, development override or caller flag cannot choose the production trust anchor. Build/codesign integrity and stable installed custody establish the anchor's trust. Unsigned synthetic/development selection demonstrates consistency only. No final package digest is embedded back into the reference, attestation or build-selection document; later package evidence binds the signed App. The runtime witness artifact remains external to the measured installer/package contents. Embedding the witness into the installer whose digest it contains is forbidden because it creates a hash cycle. The package-record ID in candidate_subject is a logical identifier, not a digest of the PKG envelope.

Reference validity is scoped to its exact pin and generation provenance. Nothing here selects 0.160.0 for future qualification. PKG U-PKG-3/R23-22 must be evaluated against the actual candidate at build/qualification time, with the passed version-advance evidence for that selected pin. The artificial fixture pin 9.9.9 is not a supplier version claim.

## Semantic checks and retained obligations

`model.py` calls the original inventory value checker, the original PKG `identity_violations` and the original lifecycle transition table, pinned in `basis.json`. It does not execute the lifecycle model or any supplier/native tool. All original PK-R1–PK-R3 and PK-R5–PK-R9 remain active. PK-R4 concerns the separate unchanged terms record; `terms_violations` and that schema remain mandatory in the packaging pipeline. This successor neither supersedes the terms record nor waives its checks. The original signing validity, every-Mach-O observation, entitlements, FP-0/1/3, Option B reliance limits, notarisation, Gatekeeper, quarantine, EXP/FP-2/W-4 and native/package witnesses remain separately required. `mach_o_paths` models a complete witnessed Mach-O set; this model cannot discover it from bytes.

Outcome derivation gives known contradiction precedence, then missing/unverifiable inputs, then verified. Invalid inventories and changed roots/modes/bytes cannot be waived by development mode. LT-04 needs verified pre-spawn evidence. LT-24 needs pre-spawn evidence, an actual label, unverifiable result, the original explicit development-start event and unchanged announcement; it cannot waive mismatch. Runtime must establish the actual human authorization—an event value alone does not prove it. Prior unverified standing must continue through ready/closure. The original event schema and transition table are checked here; whole-stream ordering, restart bounds, handshake semantics, user authorization, home/custody enforcement and native lifecycle behavior still require the existing maintained consumer and later S4 implementation checks.

The model deliberately does not scan the filesystem, execute a probe, verify codesign, authenticate reviewers, inspect authorization evidence, discover build trust or qualify custody. Runtime must implement descriptor-relative no-follow traversal, reject unsupported entries and hardlinks, check complete pre/post inventory stability and revalidate immediately before spawn. Trusted stable installed custody and the residual check-to-exec race remain explicit limits. The record's `checks` are value-model inputs, never independently established facts merely because this test accepts them.

Read origins/hashes and delegated-harness-native parentage are in `basis.json`. The assignment prohibits MEMORY/host-identity writes and delegates integration and independent review to the parent. No native run, download, credential use, qualification claim or consumer migration occurred.
