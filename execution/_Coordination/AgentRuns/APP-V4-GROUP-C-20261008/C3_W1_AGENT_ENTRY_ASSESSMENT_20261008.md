# C3 W1 agent entry — bounded source assessment

**Status: conditional investigation, no W1 owner selection or implementation.** This examines whether the current stock-Codex/App boundary exposes a plausible entry for the proposed App-owned graph-insert operation. It does not qualify an agent tool, make a graph edit, register a tool, test a model or release a source contract. W1, S/T and recovery remain pending owner choices in `C3_OWNER_DECISION_BRIEF_20261008.md`.

## Actual current seam

- The committed stock-Codex 0.160.0 **experimental generated bundle** has `dynamicTools` on thread start. A dynamic tool specification has a function or namespace form; `item/tool/call` is a **server-to-client request** with `threadId`, `turnId`, `callId`, `tool`, optional namespace and arbitrary `arguments`. Those are correlation and tool-input fields, not an original owner-scope grant or human act. Its response carries `success` and content items. The retained 0.160.0 manifest inventories both generated variants, but only experimental bundle bytes are committed here; the actual stable thread-start field and runtime opt-in behavior were not checked. The accepted DEL-01-01 Hosting Design §§6.8/8.4 labels registration experimental-only **at its 0.158.0 observation** and says choosing it changes the App's familiar request set.
- Current `app/src-tauri/src/native_requests.rs` recognizes `item/tool/call` only to classify it `known-app-unsupported`, with App-rule origin `no-dynamic-tools` and the explicit error “App has no registered dynamic tools.” The Host receives server requests with generation, native request identity and receipt position, stores the request, and writes an explicit response or error. Current App code has no non-test `dynamicTools` registration path; its execution-compatibility view merely reports whether a thread-start record has a nonempty array.
- The previously selected CCE source observes that `conversation_send_text` → `Host::turn_start_text` submits a supplier turn. That does not give the agent an App-owned bounded-write entry. A later `fileChange` observation is post-operation evidence, not proof that the App controlled the edit before dispatch. The proposed W1 functions and private target-scope evidence do not exist in current App code.

Thus there is a **candidate protocol surface**, but no qualified agent entry today. The generated schema alone does not prove actual 0.160.0 supplier behavior, version stability, discoverability in an existing thread, model use, or preservation of request/caller custody through an App handler. The experimental registration label is a product qualification issue, not a license to patch or filter Codex. An App-owned MCP server might be another supported seam, but no source-backed registration/custody route was established by this bounded inspection; do not treat it as a selected fallback.

## First proof if W1 is selected

| Check | Required result before implementation reliance |
|---|---|
| Registration and original source | One disposable synthetic App-offered tool is registered through the stock-Codex 0.160.0 input under its actually required opt-in, without changing the user's Codex configuration or patching the supplier. Capture the exact thread-start source, generation and advertised tool identity. A prior thread does not silently gain it. |
| Request custody | An actual `item/tool/call` from that thread is associated with its original generation, request ID, thread, turn, call ID and advertised tool. Changed/replayed IDs, closed generation, wrong tool and malformed arguments refuse with an explicit answer; no request is left unanswered. |
| Authority separation | Tool arguments and model text remain untrusted proposed operation inputs. They cannot mint S original task scope, T effective treatment, A5/A12/A16 or a person identity. W1 can prepare a bounded preview only after separately held source evidence and actual manager selection pass; missing inputs return a refusal with no graph effect. |
| Same operation path | A genuine human entry and the tool entry converge on one selected S/T check, target/preimage/plan, App-owned deterministic insert, origin marking, outcome evidence and separate undo operation. Direct/accepted-proposal paths differ only as their real treatment requires; no universal grant prerequisite is invented. |
| Connected outcome | Exercise an actual supplier request, bounded App handler, response/unknown handling and a synthetic project target end to end. Inspect the exact preimage/postimage and an independently reread result. Cancellation, source closure, policy change and failed/uncertain write retain their actual standing. No person act or professional reliance is inferred. |

The first two rows can be probed independently of a real graph writer using an inert tool response and synthetic thread/project. The latter rows require selected S/T/W source contracts and reviewed code. A live model-backed probe would require the owner's separate sign-in/credential handling under App v4 LOOP_INIT; this assessment ran no such probe. The current deliberate unsupported behavior must remain truthful until a reviewed successor and its tests replace it.
