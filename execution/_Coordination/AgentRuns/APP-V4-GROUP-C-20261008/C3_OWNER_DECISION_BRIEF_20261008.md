## Decision 1 — original scope and one controlled graph operation (C3-D1)

The proposed integration writes one bounded result block into an existing project work graph. HELP_HUMAN previously selected **actual owner-accepted task scope plus an exact manager-selected target** as an incremental design direction; the owner has not yet ruled on the S/T/W package, and no App source-owning admission producer or controlled graph-operation entry exists. A chat turn, role label, file permission or A16 decision about another package cannot supply either. These are three complementary choices:

| Axis | Recommended source/design direction | What remains to prove |
|---|---|---|
| **S — scope** | A source-owning App interface admits the owner's original bounded task/project/operation scope with content identity and provenance. A live manager selection narrows it to one graph target and plan. A private, non-deserializable capability is minted and rechecked against the opened project, exact target/preimage/plan and current scope before dispatch. | Legitimate original input route, ambiguity handling, withdrawal/supersession, real source custody and race-aware recheck. This decision grants no actual graph write. |
| **T — treatment** | Classify the bounded insertion as an effectful change that *may* be directly applied within genuinely effective granted autonomy, with **proposal as the conservative default**. An accepted proposal binds its exact item through the applicable A5 path; an agent's direct path uses the actually established class/scope treatment and A12 evidence where that setting is required. A person using the genuine human route does not need an agent grant. | DEL-04-01 class/default/act basis, DEL-04-02 setting/control join, DEL-01-04 applicable capture, and proposal/direct lifecycle. Scope admission and routine tool permission do not substitute for these. |
| **W — writer and entries** | Select **W1: one App-owned deterministic insert operation** for both genuine human and agent entry paths. It prepares an exact preview, checks S/T and target preimage, performs one bounded insert, then independently rereads the postimage and retains definite or uncertain outcome. It marks origin and provides a reviewed undo route as a new operation, never an automatic rollback of an uncertain result. Stock Codex file-change notifications remain observations; asking a supplier turn to edit one file does not confine the turn. | A real supported agent tool/entry adapter and a real human entry, original caller custody, source-reviewed writer/outcome/undo contracts, OS permissions and negative cases. The named functions in the source packet are design sketches, not existing APIs. |

The alternative **W2**, observing a stock supplier file edit after the fact, cannot establish that the proposed bounded operation was enforced before dispatch. It can remain useful evidence about an ordinary supplier turn, but does not close this graph-integration route. The other defensible alternative is to **hold graph integration** and build only answer/review recording for now. If the owner chooses W1, the next work is a named, independently reviewed source successor across DEL-07-02, DEL-04-01/02/03, DEL-01-04 and the Host/role/DEL-02-03 receiving contracts. Its effect on completed Group A work goes to the owner under GC-7 and into the affected successor graph under GC-8. Selection of this direction releases **source/interface work only**, not code, a live graph edit, an A5/A12/A16 act, or professional reliance.

The bundled stock-Codex 0.160.0 protocol schema names `dynamicTools` on thread start and an `item/tool/call` server-to-client request, while the current App explicitly answers that request as unsupported because it registers no dynamic tools. This identifies a candidate supported-protocol seam, **not** a qualified or implemented agent entry. Source review and a connected test must establish whether it can carry original caller/request custody into the same W1 checks; a tool argument cannot mint S or T authority.

**Requested ruling D1:** select the recommended S/T/W source-design direction together; adjust a named axis; or retain the integration hold. Record the owner's exact words and any conditions in this run's `OWNER_DECISIONS.md` before source adoption.

## Decision 2 — in-progress recovery and capacity (C3-D2)

PRD V4-PM-05 says project status is recoverable across sessions from files. The selected transient CCE lifecycle A loses pre-freeze answer/review/dispatch status on process exit. A final cold account read does not repair that gap. The [comparative assessment](C3_PM05_RECOVERY_ASSESSMENT.md) has independent review but selects no storage or capacity policy:

| Route | Benefit | Material cost or gap |
|---|---|---|
| **R0: keep transient A** | Smallest implementation increment | In-progress status remains lost; cannot support whole-product PM-05 sufficiency. |
| **R1: immutable stage checkpoints** | Exact historical stage chain; can reuse much of the current account publication model after a new carrier is designed | A normal full path proposes six CAM lifetime identities. Under the current 64-identity App-instance bound, only ten such paths fit in an otherwise empty instance, fewer with cancellations or revisions. Admission/reservation and final-account capacity remain unresolved. |
| **R2: bounded current-status journal** | Reuses a finite per-undertaking journal across stages, spending one CAM identity for the final account; fits repeated work better if past full stage snapshots need not all be retained | New identity, project quota, two-slot/descriptor atomicity, single-writer, crash/recovery and retirement rules. The current snapshot must retain all recovery-critical exact artifacts and unresolved attempts or refuse advancement. Final CAM64 capacity still needs a separate product decision. |

**Recommended next selection:** use R2 as the **source-design and proof target**, conditional on the owner accepting recoverable current status plus recovery-critical exact answer/review/intent/outcome evidence, while allowing older full intermediate snapshots to be replaced. This is an inference from the at-scale use case and R1's quantified slot cost, not a claim that R2 is already safe or cheaper to build. Do not select a numerical project quota, exact retention/retirement policy, or final CAM capacity by implication. Require a reviewed product-fit budget, atomicity/retention design and crash/uncertain-outcome tests before implementation or a whole-product 90% claim. If complete immutable stage history is required, neither the simple R2 proposal nor R1 under the current 64 cap is ready as a product policy; revise the design before choosing.

**Requested ruling D2:** is recoverable *current* status with retained recovery-critical evidence sufficient, so R2 may become the design/proof target? Or must every intermediate full stage snapshot remain immutable? This answer shapes the recovery contract; it does not approve a storage implementation. The exact finite quota and final-account capacity need a later reviewed product-suitability choice.
