## Acquisition boundary — explicit inherited gap, not a new guarantee

Current generic discovery reads/parses a whole candidate before recognizing its
version;0.3/0.4's1MiB check explicitly happens after acquisition. This brief does
not silently call that pre-read protection. The minimal proposed consumer keeps
that inherited outer-candidate acquisition limitation visible, enforces original
0.5 byte size at most1MiB once identified, and claims no bounded total discovery
allocation or protection against an arbitrarily large malformed/late-version file.
HELP_HUMAN selected retaining this residual for the first development reader; it is not
hidden by a successful small fixture test or by the final composition budget.

A cap on every discovery file would change legacy0.1/0.2 behavior; an oversized
probe followed by unbounded fallback would still fail to bound malicious0.5.
Neither workaround is authorized here. If the receiving owner requires a true
pre-read guarantee, hold this sub-slice for a separately reviewed bounded format
classification/acquisition design and old-reader compatibility assessment. Do not
invent a regex/partial-JSON classifier or claim metadata size is a race-safe bound.

Where an exact0.5 reference is already independently known, use a real pre-read
1MiB-plus-sentinel cap; a filename, unvalidated renderer field or partial prefix
is not that independent reference. Refuse changed identity/version rather than
falling back to a wider unbounded read. No new IPC path is implied by this rule.

The selected base version is known to be0.4 before its separate read. Resolve its
canonical project-contained CRP reference under the same opened root, no-follow
regular file/ancestor rules, using an actual read limit of1MiB plus one sentinel
byte; refuse overflow, not merely metadata size. No recursive0.5 chain, directory
crawl, automatic alternate path, newest account or network fetch. Parse duplicate
keys strictly, validate0.4 shape and semantic consistency, and compare exact
original length/hash/ID and project identity. Changed/missing/unreadable/ambiguous
base stays explicitly unresolved; never validate against a convenient fixture.
This bounded base path does not cure the outer discovery gap or provide a global
memory bound; parsed structures/serialization overhead remain measured limits.

## Semantic and presentation obligations

- Outer0.5 required shape plus selected null-field gate and original byte cap.
- Exact embedded answer text UTF8 byte_length/hash, single complete JSON value,
  no duplicate keys/fences/trailing prose; existing message0.1 answer shape.
- Base raw-byte SHA/size/ID/question; claim IDs unique, support IDs belong to the
  resolved base, each answer claim cites support, carried gaps/contradictions
  exactly cover inherited identities. Presence is not entailment or quality.
- Recorded receipt home/generation/method/content/reference/position consistency
  follows existing CCE checker semantics. Public strings can be forged: passing
  these checks NEVER authenticates an original SourceRequest or role emission.
- Show recorded answer, recorded provenance and limits, current base resolution,
  outstanding manager review/integration and human responsibilities. Do not show
  a live/current-authorship badge, accepted/ready/performed status or a revived
  permission. Preserve raw account text/unknown fields policy and exact identity
  strings without JavaScript numeric truncation.
- All reads remain side-effect free: no canonical directory creation, lock,
  journal, capture, repair, unlink, retry, account publication or supplier start.
