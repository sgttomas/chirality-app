## 2. Fresh delegated conversation, before a contribution turn

C3's ordinary work coordinator proposes a private DelegatedTaskIntent containing
one frozen base/question/claim set, exact bounded assignment text, working-set
revision and an original initiating source. It is created only at an actual
App-owned initiation boundary for the already authorized undertaking: either
an actual person-requested task selection or an original source-bound manager
request handled by that coordinator. Renderer JSON, graph prose, role labels,
a public authorized/delegated flag or a restored record cannot create it.
The implementation owner must name that actual boundary and the retained
source handle in its adoption; until then no task is dispatched. This deliberately
leaves the unimplemented coordinator origin visible rather than fabricating it.

The manager-origin route additionally requires a current admitted parent
HELP_HUMAN or WORKING_ITEMS source and exact parent request/intent linkage.
The person-origin route retains the actual App interaction/task scope; it does
not impersonate a manager conversation. Eligibility is an evidence constraint,
not a new permission class. Neither route broadens native approval/sandbox,
project/home access, tools or file scope. Unknown delegation warrant refuses
this CCE task step, not unrelated ordinary Codex work.

The private role producer:

1. Freezes a fresh TASK composition from the current App common guidance and
   full TASK file, including original bytes, source state, content method/hash,
   role-set identity and intended home/model/provider. It fixes TASK for this
   new conversation; it does not change the parent's role or pass a history fork
   off as a new role. Missing/invalid guidance refuses before dispatch.
2. Submits a real thread/start through Host's existing additive guidance sender.
   No supplier base/configuration is replaced; user native policy remains native.
   It retains the original SourceRequest, exact sent composition and initiating
   DelegatedTaskIntent. The internal composition boolean is merely an input to
   composition; it is never the admission warrant.
3. Awaits actual complete write, successful correlated ThreadStartResponse and
   original Host active admission. Request registration, a ready-looking snapshot,
   agentRole, schema-valid result, partial write or generic bind is insufficient.
   Thread ID, actual Host object/pipe identity, home and full H5 come from that
   admission, not from the proposed intent.
4. Installs a private AdmittedRoleEntry linked to those original handles. A
   dispatched-but-failed start retains its real outcome; no automatic resend,
   invented no-send or role admission follows. The subsequent exact CCE answer
   turn is separately dispatched only after entry/currentness checks succeed.

No W1 graph insert, W2 writer or graph-edit approval surface is introduced.
Once admitted, Codex does ordinary work under its actual effective permissions;
the App observes and reports within OD-01's limits. This proposal does not select
a graph edit or prove exclusive file-change causality.

## 3. Private role source and lineage

AdmittedRoleEntry is held by the role owner, with an opaque entry identity,
immutable guidance/supply basis, original admission proof and a versioned current
continuation association. RoleSourceLease is a non-deserializable, non-Clone
borrow under that owner's guard; it cannot be made from RoleBinding, evidence(),
role JSON, a hash, generic insertion, copied receipts or history. Existing public
value-level RoleBinding/observe/bind facilities may remain for their current
purpose but do not enroll an entry in the lease-eligible registry.

The lease identifies both **original supply** and **current transport admission**:
original start Host/request/supply/guidance; any admitted same-role fork lineage;
current admitted start/resume/fork Host identity, H5, home and thread; entry and
continuation revision; and the caller's frozen C3 selection/intent revision.
Those identities are not collapsed into one generation or request reference.

- Resume is metadata-only, with no new role instructions or supply record.
  Validate the actual current resume receipt/admission for the same home/thread;
  retain the original supplied role/bytes as historical provenance. Do not require
  the original start H5 to remain current. It is the contribution's current
  admitted source that must be ready and unclosed.
- A fork is a genuinely admitted same-role child with its actual forkedFromId,
  parent entry/supply reference and distinct target thread/supply reference.
  Retain the original guidance and admitted ancestry; no new instructions on
  fork. A HELP_HUMAN/WORKING_ITEMS fork cannot become TASK by relabeling it.
  Mere presence of the source transcript proves neither this chain nor supply.
- The implementation must retain original source-owned lineage handles, not
  reconstruct ancestry by searching history or following latest JSON entries.
  Host replacement/H5 change needs an actual admitted continuation and an exact
  retained origin relation. Matching thread strings across homes/Hosts is not
  continuity. If origin custody is unavailable, CCE eligibility is unknown/refused.
- Editing/deleting current guidance-store files affects future-conversation
  notices only; it does not mutate the existing frozen role or its supply.
  A replaced private entry or changed continuation/intent revision invalidates
  the live lease even if public labels/digests happen to match.
- Cold restart may continue ordinary native conversation use while App provenance
  is unknown. Cold records cannot rehydrate this lease. A fresh genuinely admitted
  TASK conversation may start a new contribution; it does not recreate an old mint.

The registry must not introduce a second transcript or unbounded CCE lineage
copy. Leases borrow source-owned immutable entries; proof metadata and retained
buffers count under the Host proposal's bounded CCE envelope. If a chain cannot
be checked/retained within that scope, refuse advancement, never truncate ancestry
into a positive claim. No global Host-history memory bound is claimed.

## 4. Mint/recheck and separate review

The role owner issues a lease only while its guarded admitted entry and current
Host admission agree. Host validates original write/result and full source identity;
C3 validates exact intent/base/question/claim IDs. Prepare parsing, source-file reads
and potentially blocking work outside live locks. Reacquire the proposed order
CCE working-set → role owner → Host admission/source gate → Inner for the
role-only part, then compare
all original identities/revisions before a closed in-memory mint/freeze operation.
Map/home lookup releases its lock first. No Host frame/closure callback acquires
CCE/role locks; no arbitrary callback, supplier write or filesystem work runs
under this chain. Owners must prove the actual call graph has no reverse edge.
Existing independently valid JSON snapshots are not an atomic recheck.
Dispatch retains original source handles and revision pins, not a held role
mutex while awaiting a turn. Mint and final freeze acquire a fresh guarded
lease; the retained pin alone cannot establish current eligibility.

Original role-start closure does not erase historical supply; current contribution
source closure before mint refuses. After a genuine mint, closure preserves its
historical observation within CCE-A2 but cannot authorize a new stage. Cancellation
retires the capture/intent revision and late facts cannot revive it. Source loss,
REC unanswered/loss causes and no-resend rules remain with their existing owners.
No Stop/H11 implementation or new lifecycle row is licensed here.

A review uses another actually admitted HELP_HUMAN/WORKING_ITEMS conversation,
with distinct original request, turn and final item, bound to the exact selected
answer bytes/hash and original standing. Home/H5 may be shared, but full source
bindings must establish distinct conversations. A TASK answer cannot review
itself; a copied answer in another transcript cannot substitute for its mint.
If no eligible manager conversation exists, review remains unavailable; no role
is silently changed or invented. Any newly created manager conversation must
follow legitimate role selection/admission, not a role claim in C3 content.

Role supply always leaves adoption unknown. The lease establishes observed
carriage/origin only, not cognitive authorship, truth, instruction performance,
human identity, a grant, acceptance or professional reliance. CCR's proposed
positive content-only disposition remains separately versioned and unadopted;
genuine review emission cannot invent an accepted enum or integration plan.

## 5. EXEC/WR composition receiving

DEL-02-03 receives role/no-role and source-origin facts through this explicit
interface, without inferring a workflow run, checkpoint act, R3/R4/R7 or tool
permission. A CCE text turn in a conversation with a pending WR run-end notice
must first follow the existing owner-controlled notice path. Choose no silent
prepend and no bypass: until that owner completes/disposes the notice under its
existing rules, refuse CCE text admission while ordinary work remains governed
by its existing path. Then freeze/recheck the exact one-text ContributionIntent.
A notice becoming pending after preparation makes that preparation stale; no
hidden composition change can be accepted as the originally bound request.
The WR owner must supply a private composition/notice revision guard for this
home/thread, not a public no-notice boolean. Its recheck and the Host admission
of the exact frame need one reviewed ordering point: a notice already pending
there refuses CCE dispatch. Define how a later notice relates to an already
admitted request without holding a WR or Host lock across the actual supplier
write. No second scheduler or long-lived capacity reservation is authorized.
This adds a real WR-owner edge beyond the role-only lock chain in §4. The
combined order, release point and race semantics are an explicit EXEC/WR/Host
adoption obligation; if the existing call graph cannot support them, return the
precise cycle before implementation. A sequence of separately valid snapshots
is not a substitute.
No empty/extra supplier turn is invented merely to clear the notice. Any future
combined carrier needs its own explicit reviewed byte contract.
