## 1. Outcome and exact subject

Use one exact format0.4 account as the frozen evidence subject for one question.
Obtain (1) an actual agent-authored answer, (2) a separate manager-authored review
of that exact answer, and (3), only if independently authorized and evidenced,
a bounded integration edit to an existing ordinary project work graph. A saved
contribution record or manager's statement of integration cannot replace step3.
Human acceptance, professional reliance and any cross-undertaking coordination
or waiver remain with their owners. No source read, supplied role, message,
review or write synthesizes those acts.

Additive `connector.route-account.v0.5.schema.json` is a linked contribution
account, not a rewritten copy or relabeling of0.4. Its base reference binds the
same opened project identity, canonical CRP relative path, account ID, exact
original serialized byte length and SHA-256. Resolve and validate0.4 from actual
bytes through its existing owner; reject duplicate JSON keys, invalid0.4 or
ambiguous identity. Freeze its exact question and claim/fact/pair IDs. Original
format0.4 claims, contradictions, gaps and contribution reports remain what they
were;0.5 never converts an unverified report into performance evidence.

A cold0.4 may supply the evidence subject as a recorded account; it does not
restore CGP source custody or certify underlying truth. The answer must state
that limit. Base changes under the same ID/path are stale, not silently rebound.
No automatic selection of newest account, best answer or last manager report.

## 2. Real observed-authorship interface; missing seam made explicit

Current App sources contain these actual primitives:

- `Host::source_request` returns the original private SourceRequest for a scoped
  turn/start; SourceEvidence retains actual complete write, correlated native
  response, full generation, pipe epoch/identity and receipt positions.
- `Host::on_line` admits actual live `item/completed` and `turn/completed` frames
  into the private generation/position journal. `execution_custody` records
  pointer state; its snapshot alone contains no completed-message text proof.
- `runtime_session` history owner `binding(home,thread)` returns in-memory
  `RoleBinding` from original thread/start role supply. `role()`/`evidence()`
  JSON projections and imported serialized bindings are not that capability.
- `NativeHistory::accepted_items_observation` plus
  `Host::mint_accepted_items_page` bind a current correlated history page. They
  prove a history read, not original authorship. Supplier history may include
  injected items or fork-carried turns. It cannot mint this contribution.

There is **no existing C3 authored-contribution capability** joining these facts.
Specify a narrow source-owner-minted, non-deserializable capability in Host/role
owners for later implementation, with fresh currentness checking there. Renderer
JSON, booleans, schema validity, a claimed actor name, imported transcript,
source file, CCE cold bytes or public NativeHistory.receive never create it.
Scoped owner concurrence must cover this join before implementation selection.
The protocol labels observed in the inspected stock0.160.0 definitions are
method-shape evidence, not a permanent supplier pin; actual candidate/version
qualification follows the existing supplier qualification rules.

For each contribution require a newly App-submitted turn, exact original input
bytes binding the base/account/question and requested contribution kind, genuine
in-memory supplied-role binding for the same home/thread, actual correlated
turn/start identity, live completed agentMessage item text, and completed
terminal turn observation for that same full generation/thread/turn. TASK supplies
the answer; HELP_HUMAN or WORKING_ITEMS supplies the separate manager review.
Use distinct turns and message items; never infer a manager role from text,
agentRole, a fork relation or current unrelated role. Supplied role is not proof
of instruction adoption or person identity.

The exact `input_sha256` is over the decoded UTF-8 of the one CCE text input
in the original params.input (single text element for this bounded path), not
the RPC envelope. The message/content digest is over decoded agentMessage.text
UTF-8, preserving whitespace and line endings. Role guidance is separately
identified. SourceRequest.frame and journal frames are parsed JSON Values, not
original wire buffers. A frame reference uses method
`sha256:host_parsed_frame_json_utf8`, defined as the retained Value serialized
by the host's pinned serde_json::to_vec method; no wire hash or cross-library
canonicalization is claimed. Role bytes use `sha256:role_guidance_utf8`. Record
method identity and digest; unavailable original text is a gap.

The mint joins private original receipts and parsed live frames, rejecting replaced
sources, closed generations, unobserved write, mismatched item/turn IDs, incomplete
items, interrupted/failed turns, commentary-only output, duplicate/conflicting
final items, and missing or contradictory lifecycle evidence. Explicit final
answer phase is required; unreported phase is an eligibility gap, not guessed.
Retain fast-event-before-start-response ordering by original receipt positions;
do not impose an impossible response-before-event sequence. Ensure the item
belongs after the actual start dispatch, and that terminal/item evidence is
mutually consistent. Source loss before mint refuses. A genuinely minted observation retained in
the same active in-memory CCE set may be recorded after source closure, labelled
historical_after_source_close at recording. It cannot authorize a new mint,
turn, graph write or retry. No serialized/cold receipt can recreate that object.

Warrant: the qualified supplier emitted this exact authored content on that
request-bound turn under this observed supplied App role. It proves neither
cognition, source truth, entailment, authority, acceptance nor exclusive human/
model identity. A supplier-history item alone, copied answer or manually entered
actor label remains ineligible, not another “performed” report tier.

## 3. Agent answer and manager review content

Use the separate `connector.contribution-message.v0.1.schema.json` for precisely
one whole final-message JSON value, UTF-8, no duplicate keys, fences, trailing
text or extraction from arbitrary prose. Record its exact emitted text bytes
and SHA-256; do not reserialize and claim identical authored bytes. This selected
answer/review is a deliberate project artifact, not a transcript/page cache.
Retain no reasoning, unrelated messages, credentials, raw pages or supplier
settings. Source metadata are pointers/hashes and explicit observation limits.
Cold content is historical recorded authorship evidence, not reconstructed hot
source authenticity. This artifact boundary is subject to the native/RS owners'
scoped concurrence; it does not authorize a shadow history store.

Answer content binds base SHA-256 and exact question identity. It contains a
substantive answer_text plus cited answers/claims with exact base claim/fact/pair
IDs. The author must explicitly carry all base gap JSON pointers and contradiction
IDs, with unresolved treatment; it cannot clear them by omitting them. The host
checks references, scope and byte identity, not whether prose is true or
adequately reasoned. A model-generated but empty, malformed, wrong-account or
uncited answer fails preparation. Merely returning known hashes or “done” is not
a substantive answer; quality remains the manager's review, not a length heuristic.

The manager's separate final-message content binds exact answer-text SHA-256,
base SHA-256 and question ID. It provides review_text, per-claim findings,
remaining limitations, and one disposition: changes_requested, cannot_assess,
or reviewed_for_integration. This is an observed manager contribution, not a
person's A4/A5/A6/A7 act. It does not integrate anything. Unresolved source gaps,
contradictions, human responsibilities and prohibited promotions stay visible;
review cannot silently declare them resolved. Changed answer bytes/IDs require
a new review. Conflicting reviews stay separate and block any automatic choice;
no timestamp/last-writer winner. A chosen revision of the review must be explicit
and retain conflict history/limitations.

## 4. Authorized target and observed bounded integration

The selected target is an **existing** ordinary project work graph's evidence/
result row or section for this question. Parent selection of this source method
is not authorization to write any particular graph. No automatic target by
filename, project convention, renderer path or manager role label. Require the
actual trusted supplied task scope/target authorization plus explicit manager
selection of exact project-relative path and bounded byte interval (or an absent
section at a specific insertion offset in an existing graph). No new graph,
arbitrary rewrite, delete, move or rewrite of actor holds. No suitable separately
authorized target means integration remains outstanding.

Current C3 has no source-owned target-authorization capability. The actual
owning input is the project undertaking owner’s explicit scoped authorization
for this existing graph/section, supplied through its accepted task scope, plus
the manager’s exact target selection within that scope. No accepted machine-
readable grant or App interface connecting that input to C3 was identified.
The scope-owner-to-App custody bridge is therefore a distinct unresolved
implementation hold, separate from lifecycle A. Its design and owning review
must precede any integration implementation selection; a future adapter cannot
be assumed to know permission. In particular, a free-text “approved”,
serialized permission field, directory access or role supply cannot mint it.
This contract does not invent a shared grant/run format. Until that owner-bound
input and target selection are available, only answer/review preparation is
possible and graph integration is unavailable. Return any reserved authority
question to the owner; do not manufacture an extra universal human gate.

Manager review for integration also binds a host-frozen edit plan: exact target
identity, original full-file bytes/hash (including section-absence observation),
one insertion offset and block bytes, expected full postimage/hash, and
preservation of every original byte. This first treatment is insert-only inside
an existing graph: no replacement/deletion and no new file. The identified
question/result block must be absent in the preimage; an existing block requires
a separately reviewed correction path, not silent duplicate insertion. The resulting row/section must
contain the exact base-account, answer and review content identities. Avoid a
self-referential review hash: the review approves the plan payload that reserves
a dedicated review-reference field; after observing the review, the host fills
only that field with the exact review hash, recomputes the final edit bytes and
exposes them before any writer action. Any other change requires new review.
This narrow substitution must be explicitly named in the reviewed plan.

Use the existing supplier native file-change operation only where its genuine
live `fileChange` completed item names exactly this target, kind update with no
move, on a dedicated original request-bound writer turn. No commandExecution
success, free-text return, imported/history-only item, failed/declined patch,
multiple-file changes or new-file add qualifies. A narrow Host-owned mint must
bind this original operation evidence; no existing public C3 writer receipt is
assumed. The supplier diff is a report, not a new authoritative diff parser. The current
stock file-change interface does not expose an fd-bound per-target write

claim they exclude all races or other writes. Any proposed stronger guarantee

Independent host-owned preimage read must precede dispatch and match the plan;
postimage read after the completed operation and a second independently opened

full-file hashes and distinct preimage/postimage/reread references with kind,

observation order and selected
result-section anchors. Use no-follow project-contained regular UTF-8 reads

between the postimage and independent reread identity is uncertain/conflicting

record distinct pre/post identities and require post/reread agreement, not
unsupported pre/post inode equality. Preserve original
preimage, operation and postimage evidence and return for explicit reconciliation;

Observation claim is only **supplier operation reported completed and independently

### OPEN lifecycle selection A; no capacity-policy adoption

Proposed A is one active CCE working set sharing the existing one-payload/1MiB
budget, never a second parallel full-payload registry. Admission refuses while
any0.3/0.4/0.5 draft is prepared/in-flight or a CCE set already exists; it cannot
silently evict that draft. The user may explicitly cancel an old unconsumed
draft under existing CAM-R1 before starting CCE. While CCE is active, other
materialization preparation refuses rather than allocating a second payload.
Require spare capacity before admission; do not reserve/expose an account ID
or consume a64-slot entry until final valid freeze, per current CAM-R1. A CCE
working-set handle is transient process state, never an account identity.

The proposed working-set budget covers retained answer/review/plan text and
receipt metadata together. Count exact UTF-8/escaped eventual representation;
refuse excess without truncation. Borrow current source-owner native receipts
serially rather than copying journal/page histories into a CCE registry. Check
live source stability before every NEW mint and graph dispatch. At final freeze,
require either those current source objects or already-minted in-memory CCE
observations explicitly labelled historical; do not demand a fresh live join
merely to retain an already observed outcome. Original Host storage
has its existing limits, which this proposal does not enlarge or call bounded.
A missing original receipt yields a gap, not a synthetic reconstruction.

Before any integration write starts, explicit cancellation discards the
working-set payload and invalidates its handle; no account slot is consumed.
Once a graph operation is dispatched, cancellation cannot prove rollback or
release its sole working-set slot while an unresolved/actual outcome would be
lost. Retain its compact actual write/cancellation/uncertain evidence; refuse
new CCE or materialization until explicit reconciliation/final recording. Final
valid0.5 freeze atomically transfers the one payload to one ordinary CAM-R1
identity; no second copy or token revival. Final validation/RNG failure preserves
the active working set and observed outcome; it does not invent publication.
If source closure occurs after graph dispatch but before operation mint,
retain prior genuinely minted answer/review plus the original pending/uncertain
attempt and gap; integration is null even if a later file hash matches. A missing
operation witness cannot be backfilled by history. If the full integration join
was already minted before closure, archive that historical actual observation;
never say cancellation saved nothing. This exception is final-record retention
only, not fresh write/actor authority. Existing actual0.5 publication outcomes
then use CAM-R1's consumed tombstone/
Attempt retention. No automatic retry, reset, eviction or process restart.

This proposed pre-freeze mutual exclusion/outcome retention is **OPEN**, not an
already authorized CAM-R1 behavior change. Parent technical selection after
source/independent review is required before code. Existing64/one-payload policy
is untouched by this source candidate. The original source-bound native input
and role/target capabilities must be representable within this design; otherwise
return the exact conflict instead of adding another registry.

A loses unfinished answer/review/plan hot custody on process exit. Under PRD
V4-PM-05 this is an explicit **cross-session recovery limitation**: readable final
accounts do not establish recovery of the multi-turn undertaking. On restart,
show unfinished source/lifecycle status unknown where only pointer evidence
survives, no false “nothing happened”; independently inspect the authorized
target before deciding any repeat write. Test a crash after native write but
before0.5 freeze. No durable pre-freeze journal/retention policy is selected here.

Alternative B would persist each intermediate contribution using existing
account identities and later consume it only as historical recorded authorship,
with new live manager evidence. It spends separate64 slots and cannot revive
hot emission authority. It improves retained content but changes the allowed
historical contribution basis; it is **not selected**. If full pre-freeze
cross-session recovery is required for this increment, A is insufficient and
B or another explicitly reviewed durable design is required. Do not hide this
product consequence behind source-only schema validity.

### Preliminary review precision repairs

The referenced 0.4 account must pass its owning CRR semantic validator, not only
schema/hash checks. A source identity within one full Host generation cannot
carry conflicting method/hash/kind; a receipt position in that stream cannot
identify different events. Causal stages in a shared stream start after both
prior terminal and correlated response; positions in unrelated streams are not
numerically compared. Exact artifact bindings still establish cross-stream order.

Source closure before integration is distinct from explicit cancellation:
already minted answer-only or answer-plus-review observations may freeze as
historical records with integration outstanding and a source-closed gap. Closure
permits no new authorship mint, dispatch, write or retry. Explicit cancellation
before graph dispatch discards that active set and creates no final account.
After dispatch, cancellation/closure must retain the actual or uncertain outcome
as specified above; it cannot report that nothing was saved. These are proposed
OPEN lifecycle A rules, not executed production lifecycle tests.
