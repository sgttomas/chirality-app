# Visible autonomy and result standing

## Purpose and Objective Traceability

This deliverable lets the person see, at any moment of the work, what they have allowed the agent to do for each kind of operation, change that during the work, see where each directly applied change came from and how to undo or check it, and see how far each result can be trusted. What it shows is never stronger than the evidence received, so the person can validate to the degree the situation warrants. It contributes the receiving components that show these things, the conditions a host must supply for them, and the cases that examine them. It sets no policy, writes no record and builds no host control.

It covers SOW-075, SOW-076, SOW-077 and SOW-078, for OBJ-005 (useful autonomy with attributable human acts, result standing and reconstructable provenance). Its sources are PRD V4-AUT-01, V4-AUT-02 and V4-HOST-02, and HOST_INTEGRATION V4-HI-12, V4-HI-21, V4-HI-22, V4-HI-25, V4-HI-32, V4-HI-33, V4-HI-40 and V4-HI-42. The draft 4.0.0 release target names no exit criterion for this deliverable; `DEL-09-07` and `DEL-09-06`, which own its criterion 5 (the live SWBPIPE journey), rely on the grant display and on the origin and undo access this deliverable provides.

## Deliverable Definition — Ontology

- **OUT-001** — The autonomy and result-standing receiving components: the grant display, the change of a grant during work, the association of what is shown with the run's recorded settings, access to origin, undo and later checking for a directly applied change, the checkpoint overlay and the standing facets. Covers SOW-075, SOW-076, SOW-077 and SOW-078; supports OBJ-005.
- **OUT-002** — The host control, origin and undo contract: what a host must supply for each of those displays (its control for setting a grant, origin marks, an undo route, a later-check route, receipts and result standing) and what is shown when it does not. Covers SOW-075, SOW-076, SOW-077 and SOW-078; supports OBJ-005.
- **OUT-003** — The mid-run autonomy, standing and undo cases, with their results on an identified candidate, kept apart from any witness on a real host. Covers SOW-075, SOW-076, SOW-077 and SOW-078; supports OBJ-005.

Terms:

- **Grant display state.** For each operation class and scope, one of seven. *Effective (person-set)*: the person's grant-setting act is recorded and the control confirmed it; shown with its value and scope as set by the person. *Effective (policy default)*: an adopted policy-class record supplies the default; no person set it. *Requested by agent*: shown beside the governing state, never as a grant. *Set by person, not yet confirmed by control*: the earlier state still governs. *Unconfirmed*: a last-known value without current confirmation. *Not set*. *Refused (reason)*: shown beside the state that still governs. Only the two effective states can open direct application. A later setting supersedes an earlier one only when the control establishes it. An operation result never moves a class to effective or widens it.
- **Destination grants.** For a host's agent that contacts network destinations, the display also shows the allow list (each category switched on or off, and each named destination), the model service as allowed by the person's model choice, the items that stay off unless the person turned one on (analytics, a silent switch of model or provider, background downloads), each grant made during work with its scope (once, this run, always), each agent request for a destination, and every destination contacted. Destination grants and operation-class grants are shown apart and never merge into one "allowed" signal.
- **Settings version.** What is in force, requested or refused for a run at one moment: scope; for each operation class its grant value, class value and display state; who requested the setting and who set it; the grant-setting act or the policy-class record it rests on; the control's confirmation or its reason for refusing; and, for a host's agent, the destination settings. Each version has its own identity, which a request or an operation cites as the settings it was made under. Each version is handed to the run record when the run starts and at each change, and what the record returns is compared with what is shown.
- **Checkpoint overlay.** For each arrival at a declared checkpoint, the one disposition its checkpoint entries establish, under the names `DEL-02-01` defines: *not reached*, *waiting*, *performed*, *resolved negatively*, *lapsed* or *unknown*. *Waiting* means reached with the act not yet recorded, never that the run is held. A declaration whose required act is not one a checkpoint may require is shown as an invalid declaration; one whose required act is not recognised is shown as not established. A checkpoint is shown as plan guidance with its required act, subject and purpose; no hold, stop or block is shown. Showing a hold belongs to the later governance layer, which the owner takes up for a workflow that needs enforced checkpoints. A performed act that lapses after the run resumed is shown as lapsed at its time and nothing is shown as waiting again. An act performed after its run ended is shown as after run end and changes nothing in that run.
- **Standing facets.** Shown separately and never combined into a single "verified" or "approved" label: whether the result is current or historical; host checks, each named with the basis it was evaluated on; the host's stated limitations; human acts, each with kind, actor, recorder and lapse state; agent examination findings; evidence that is missing or unknown; and route and outcome (direct under a named setting, or a proposal with each item's disposition and actor).
- **Host contribution for a directly applied change.** An origin reference (supplied, missing, or mismatching the request); an undo route (offered, not offered, unknown); a later-check route (offered, not offered, unknown); and a receipt reference (supplied, missing, unresolvable). An undo is complete only when the host returns a receipt for it.
- **Labels.** One label for each act kind. "Accept" names edit acceptance only and "reject" its negative; "checked" names the person's mark only; a host result says "host checks passed" with the checks named; agent work is "examination" or "findings"; "approval" names engineering approval only; "tool permission" names a tool-permission answer. A declined act is shown as declined, never as the act.

Boundary:

- **CLM-001** — This deliverable owns what the person is shown about autonomy and standing, and the settings version it hands to the record. The control that sets a grant is the authority for the grant in force; the run record is the authority for what was recorded; the display is derived from both.
- **CLM-002** — `DEL-04-01` owns the act kinds, operation classes, grant values and the rule that resolves a treatment. `DEL-04-03` owns the run and act record, its writer and reader and the rule by which an act lapses. `DEL-03-02` owns the proposal lifecycle, outcomes and the origin of an agent's change. `DEL-03-01` owns read basis and the standing a read result carries. `DEL-02-03` owns the recording of checkpoint arrivals, requests and acts and what those entries mean, and `DEL-02-01` the disposition names. `DEL-05-01` owns the host loop's network-destination events. `DEL-03-03` owns the channel status and the model destination shown for an App conversation. `DEL-01-04` owns the placing of these displays in the App's own interface, their behaviour there and the App act control.

- **CLM-005** — The accountable professional owns professional reliance and every statement of certification, sealing, professional approval or code compliance.

## Production and Verification Method — Praxeology

The display is derived, never an authority: the grant in force is read from the control that set it, and what happened is read from the run record. Each facet of standing is shown from its own source and the facets are not combined. A missing input is shown as missing; nothing fills it. The settings version is the one content exchanged with the record, in both directions, so that what was shown and what was recorded can be compared version by version. Names here are names of meaning; field names, layout and timing are chosen in the implementation.

- **VER-001** — Executable check (observes the grant display state shown for each operation class, before and after a change during work): drive a person-set direct grant, a policy default, an agent's request, a setting not yet confirmed, a refusal, a loss of confirmation and an operation's success, and a checkpoint reached under a direct grant; compare each state shown with the grant the control reports.
- **VER-002** — Executable check (observes the settings versions shown against the settings versions the run record returns for the same run): compare them version by version for a run and a change during work, including a version absent on either side, an unconfirmed setting, a partly readable record, and a destination request closed by its turn's failure.
- **VER-003** — Executable check (observes the origin, undo, later-check and receipt elements shown for a directly applied change on a simulated host), combined with comparison with a named reference (the host's own origin marks and receipts on a real host, where supplied): invoke an offered undo, and exercise an absent route, an absent receipt, a mismatching origin and an unobserved outcome.
- **VER-004** — Executable check (observes each standing facet shown against the evidence supplied to it): supply current, historical, host-checks-passed, limited, content-lapsed, missing and unobserved results and compare every facet and evidence link with its source.
- **VER-005** — Executable check (observes the act kind, actor, recorder and label shown for each case of AC-005): include a performed act recorded by a separate recorder, fabricated attribution, and an independently evidenced act with no earlier act.
- **VER-006** — Judgment by a named role (a reviewer who did not write the host contract): trace each input the displays use to its owner, compare the exclusions of REQ-007 one for one with the decomposition's deliverable rows and its external dependency on SWBPIPE, and report any undecided value shown as decided or any host capability stated without the host's evidence.
- **VER-007** — Executable check (observes which acceptance criterion each case exercises, its result on the identified candidate, and whether the host in it was simulated or real).
- **VER-008** — Executable check (observes the disposition and wording the checkpoint overlay shows for each arrival against the checkpoint entries supplied to it): drive not reached, waiting, performed, resolved negatively, lapsed and unknown, an invalid declaration, an unrecognised required act, a lapse after the run resumed and an act after the run ended.
- **VER-009** — Executable check (observes the destination display against the destination events supplied to it in the form `DEL-05-01` reports them): supply an allow list by category and by named destination, a grant made during work in each scope, an agent's request, a decline, an item that stays off and contacted destinations; compare what is shown item by item; and confirm that a destination grant and an operation-class grant are shown apart.

## Governing Values and Decisions — Axiology

- **AX-002** — Graduated autonomy and later checking are kept useful while false attribution is excluded. Better means the person reaches the grant in force, and the origin and standing of a result, in fewer steps during work; never by showing a grant, an act or a standing that the control, the record or the host has not supplied.
- **AX-003** — The evidence shown is enough for inspection, attribution and proportionate validation, and stays with its owner: host evidence is shown by reference and no parallel authority is kept. Better means fewer results shown with evidence missing or unknown because more of the host's evidence is received; never by filling a gap from the App's own request log or from a successful operation.
- **TBD-001** — Operation-specific additions to the reserved acts are undecided (the owner, through the SWBPIPE session, with the App owner). Until decided, the display shows such an operation as having no policy basis.
- **TBD-004** — Whether any of these components is built as one shared with a host is undecided (the App and shared contract owners). No shared service is assumed.
