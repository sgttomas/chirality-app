# DEL-01-01 — Stock Codex hosting and supplier contract

## Purpose and Objective Traceability

This deliverable makes the standalone App a host for stock Codex. The App's Rust main process starts the unmodified, pinned Codex App Server as its own child, speaks its published JSON-RPC protocol over standard input and output, and hands what Codex produces to the rest of the App in Codex's own form. Before the App treats a Codex distribution as the pinned supplier it checks that it is that supplier, and it tells every receiver when it is not. Recovery, the native views, request answering, sign-in and provider access, and packaging are all built on this boundary.

It is the BACKEND_FEATURE_SLICE `DEL-01-01` of PKG-01 in the accepted decomposition. It serves OBJ-002 (the chosen App architecture) through SOW-097, SOW-099, SOW-100, SOW-101, SOW-118, SOW-119, SOW-121, SOW-131 and SOW-135; OBJ-001 through the supplier side of plan visibility and selected-version identification (SOW-128, shared with `DEL-01-03`); and OBJ-004 through qualification of the embedding protocol and the provider requirements it implies (SOW-149, shared with `DEL-01-05`). Its PRD sources are V4-APP-04, V4-CST-01, V4-CST-03, V4-EXE-02 and V4-EXE-03; its architecture sources are V4-ARC-01, V4-ARC-02, V4-ARC-03 and V4-ARC-05, the properties of ARCHITECTURE §3, the supplier assumptions of §6 and principles M-2, M-4, M-6 and M-7.

## Deliverable Definition — Ontology

- **OUT-001** — The hosting boundary: the code in the Rust main process that identifies and verifies the supplier distribution, starts, handshakes with, observes and stops one Codex child per App-owned Codex home, exchanges and correlates protocol frames, keeps the register of server requests, and delivers native frames to receivers. Supports SOW-097, SOW-099, SOW-101, SOW-118, SOW-119, SOW-131; OBJ-002.
- **OUT-002** — The supplier pin and what is derived from it: the declared pin, the expected distribution identity, the protocol types generated from that pin, the hand-kept supplement, and the version identity record given to receivers with each ready generation. Supports SOW-099, SOW-121, SOW-128, SOW-135; OBJ-001, OBJ-002.
- **OUT-003** — The seam to receivers: lifecycle and register facts for recovery; version identity and native plan items for the plan views; register operations for request answering; carriage of account methods, provider selection and guidance; observed supply and destination facts for records; the harness-capability account; and the provider requirement account. Supports SOW-097, SOW-101, SOW-128, SOW-131, SOW-149; OBJ-001, OBJ-002, OBJ-004.
- **OUT-004** — Supplier qualification on an identified candidate and the means of a deliberate upgrade: exchanges recorded from the stock supplier, each naming the pin it was captured at; selected-version checks; and the comparison run when the pin advances. Supports SOW-100, SOW-128, SOW-135, SOW-149; OBJ-001, OBJ-002, OBJ-004.

Terms:

- **Pin.** The one Codex version a candidate is built against. The current pin is Codex 0.167.0 (supplier tag `rust-v0.167.0`); it changes only by a pin advance under REQ-006.
- **App-owned Codex home.** A Codex home directory the App creates for its own use, named by a stable App-owned identity that is neither a credential nor a filesystem path. One child runs per home; nothing of one home's child settles, answers or is attributed to another's.
- **Generation.** One spawn of a child, identified by {App session, home, spawn counter}. Every frame, request and register entry carries its generation, and nothing from one generation settles or answers anything in another.
- **Distribution identity.** The complete inventory of the supplier's published vendor tree: every file's path, type, mode, size and content digest, and every directory's mode. A manifest digest of the files alone is not the identity.
- **Verified.** The version label the binary reports equals the pin, the distribution identity equals the expected identity for the pin, and the generated protocol output names the same pin. A label alone never verifies.
- **Unverified development run.** A run the person explicitly opts into on a distribution that cannot be verified and shows no mismatch. It is labelled `unverified-development` in the ready announcement, diagnostics and version display, and it qualifies nothing.
- **Register.** The main-process list of server requests awaiting an answer. An entry is created when the request is received and ends answered, declined, errored, resolved by the supplier, ended unanswered, or with its reply outcome unknown.
- **Native delivery.** A frame reaches receivers with the supplier's method, identifiers, payload and other top-level elements unchanged and in received order; generation, receipt position and classification travel beside it.
- **Supplement.** The small hand-kept set of protocol elements absent from the generated output. Each entry names its pin and the recorded exchange or generator output that evidences it.

Boundary:

- **CLM-001** — Process placement is settled for the whole App: the Rust host owns everything that writes the person's files or the App's records, talks to Codex, or captures a person's act; the web view presents, and sends only what the person initiates. In the Rust host this deliverable provides the frame exchange, the register and the write path for every request and answer; composing turns and validating answers belong to `DEL-01-04`, and account and provider calls to `DEL-01-05`. Where shared contracts and components live is undecided and affects no criterion here.
- **CLM-002** — Codex owns its agent engine, its account methods and its credentials. The App owns the receiving integration. The App has no agent engine of its own, no second harness, no generic protocol layer or translated event vocabulary between itself and Codex, no v3 Runtime service or socket, and makes no private modification of the supplier. Reuse of v3 code is optional; code qualifies only by meeting these criteria on the candidate.
- **CLM-003** — The qualification pin is the newest Codex version that has passed a version-advance check when the candidate is built. A check that finds relied-on behaviour changed returns the decision to the owner.
- **CLM-004** — `DEL-01-02` owns custody of sessions and requests across window loss, Codex stops and relaunch, the stop definitions, recovery reads and the App ledger. `DEL-01-03` owns plan, tool and delegation views and derives plan-revision identity. `DEL-01-04` owns request cards, answers, outcomes, attachments and the act control. `DEL-01-05` owns the App-owned homes, sign-in, provider configuration and per-conversation selection. `DEL-01-06` owns packaging, signing, notarisation and the package identity record. This deliverable creates each register entry, classifies it, writes the explicit error to an unfamiliar request and offers the answer path; it writes no durable record of its own.
- **CLM-005** — `DEL-02-01` owns the portable capability names that resolve to the harness-capability account. `DEL-02-02` composes a workflow's run-start text and `DEL-02-04` composes role guidance; this boundary carries both unchanged. `DEL-04-01` owns the operation policy and `DEL-04-03` the record format and writer. A person's acceptance, checking, approval and reliance are theirs; a tool-permission answer never stands for any of them. Execution, proposal acceptance, checking, approval and professional reliance are separate acts: none is inferred from another or from an execution outcome, and none is made a prerequisite of another that is independently evidenced.
- **CLM-006** — The person's Codex configuration, approval, sandbox and review-routing settings are theirs and are carried unchanged, apart from the permission level the person sets in the App (PRD V4-AUT-06), which the App sends to its Codex in place of the approval, sandbox and review-routing settings (in 4.0.0 the person answers the supplier's requests at every level, and the person's own configuration files are not changed), and the nonsecret session settings DEL-01-05 names, which the App applies to its own Codex process and lists for the person; a setting the supplier refuses is shown as refused. The boundary adds no allow list or destination gate to the App's Codex: the permission level is the supplier's own sandbox and approval setting, not a gate of the App's. The inherited environment variables the host removes by name from its Codex processes are a further stated exception, and are listed in the configuration identity. So is TMPDIR, which the App replaces for its Codex with a temporary folder it makes for that start; the configuration identity lists it beside the names the App removes. The App's own working folders (the version label probe's home, the connector's working folder and those temporary folders) are kept beside the App data folder, in a folder named after it, and never in a temporary folder or in the App data folder; each is made by the App inside the folder it established and recorded before it is used. Only a folder the App made in the same launch, and still holds, authorises the removal of what is in it, and the folder itself is kept. The App data folder and the person's own Codex home are never removed, whatever contains them. Where that folder holds an entry named as Codex names a file in its home, or anything made before the folder itself was, everything still in it is kept and reported, and nothing in it is read. What earlier launches left is kept and reported. With no project open, the working folder the App gives its Codex is a dedicated folder the App creates for that purpose. The App's own fixed locations for its records, settings and Codex homes are outside that folder. A location it is given for them, by a setting, an environment variable or the person's choice, is checked by the folder's identity when the App admits it, and is refused if it is that folder or inside it. The check is made at admission: a file that is already another name for a file inside that folder, and a location replaced after the check, are outside what it guarantees. The permission level the person sets in the App applies to that folder.

## Completion and Reliance Basis — Epistemology

- **REQ-001** — The App hosts the unmodified stock Codex App Server at the pin as its own child, over the published JSON-RPC interface on standard input and output, under Tauri 2, React and Vite. Only the main process holds the pipe, the protocol session and the register; losing, hiding or reloading a window never writes to, closes or signals the child. Every server request is registered at receipt. An unfamiliar request is answered at once with an explicit error. No timeout, silence, observer loss, restart or exit becomes a grant or an affirmative answer, and no App rule answers a tool-permission request affirmatively. The supplier and the processes it starts are handled as one unit: a deliberate stop ends the process group, and descendants that survive an exit are detected and reported, never assumed gone.
- **REQ-002** — Protocol types are produced by the supplier's own generators at the pin and are never edited by hand. Experimental standing is decided only by the difference between the stable and experimental generator variants. Well-formed frames are delivered natively. Unfamiliar notifications are delivered, marked unfamiliar and inspectable; malformed or oversize frames are counted and surfaced; the supplier's notification-suppression facility is not used; frames received before readiness are kept in order and delivered with the ready announcement. The supplier's base instructions are never set or replaced.
- **REQ-003** — Each ready announcement carries the version identity record: declared pin, observed version label, distribution identity, launcher and configuration identity without any credential, declared capabilities, generated-output identity, supplement identity and the verification result. Native plan items and plan updates reach the plan receiver unchanged with generation and receipt position. This is the supplier side of SOW-128; revision identity, the plan views and any registry are the receiver's.
- **REQ-004** — The product conforms to the placement in CLM-001 and holds the exclusions in CLM-002. Design choices rank maintainability, then functionality, then local models and privacy, use the few mainstream stacks already chosen and no release-candidate framework.
- **REQ-005** — The embedding protocol is qualified on the identified candidate. The provider requirement account states what Codex at the pin requires of a model provider (the Responses interface, and the tool forms it sends on that route) and separates what the supplier publishes from what was observed on an identified server. A named server example establishes no supported substitution.
- **REQ-006** — No receiver is told the supplier is ready until it is verified and the handshake has succeeded. A mismatch refuses the start. An unverifiable distribution refuses, except as an unverified development run. On an installed production build the supplier is executed only when, in addition, the running App's own signature validates against the publisher identity compiled into that build; a build with no compiled publisher identity cannot run the supplier as a production supplier. A pin advance is deliberate: the generated schema, the supplement and the recorded exchanges of the new pin are compared with those of the prior pin before the App relies on it. A candidate is built against the pin CLM-003 selects, and that pin is qualified only by this deliverable's criteria holding on that candidate. A selected pin or a generated basis is not qualification.
- **REQ-007** — This deliverable performs no act that CLM-004 gives to a sibling: no durable recovery, view, request card, account flow or package.
- **REQ-008** — This deliverable performs no act that CLM-005 gives elsewhere: no workflow semantics, guidance composition, operation policy, record writing or person's act.
- **REQ-009** — A request written to the supplier whose response was never observed has an unknown outcome, neither failed nor succeeded. When a generation closes, a reply that was prepared but not written leaves its request ended unanswered, and a reply whose write was admitted but not observed is reported as reply outcome unknown. A local write is never reported as receipt or acknowledgment.
- **REQ-010** — For each thread and turn the boundary observes the guidance content it actually carried to the supplier, by content identity, and the model and destination the supplier reported, and hands them with their origin to the record writer. A destination the supplier reported for a thread is not attributed to a turn that no report names. Each settlement is handed over with the origin of its answer: the person through the interface, a named App rule, or a decision made inside Codex.
- **REQ-011** — The harness-capability account places every supplier item kind, server request and client method of the pin in one capability group, with the signal that shows whether it is available and its stable or experimental standing.

- **AC-001** — On the identified candidate the stock child at the pin runs under the App's main process over standard input and output; closing, hiding and reloading the window leave the child, its session and a pending request untouched; an unfamiliar server request receives an explicit error; no elapsed time, window loss or restart produces an answer, and no tool-permission request is settled affirmatively by an App rule; a deliberate stop leaves no member of the supplier's process group running; descendants that survive an unexpected exit are reported, with how many; start, readiness, stop and exit are each reported with their generation; and a frame or reply from an earlier generation settles or answers nothing in a later one. Verify by VER-001. [REQ-001]
- **AC-002** — The protocol types in the candidate equal the output of the supplier's generators at the pin; an element is experimental exactly when it appears in the experimental generator variant and not in the stable one; every supplement entry names its pin and evidence; native, unfamiliar and malformed frames reach receivers as REQ-002 states; frames received before readiness reach receivers in received order with the ready announcement; and no frame the boundary writes sets the supplier's base instructions or uses notification suppression. Verify by VER-002. [REQ-002]
- **AC-003** — The version identity record a receiver gets agrees with the supplier binary's own report and with the distribution actually on disk, and a native plan item reaches the plan receiver byte-equal to what the supplier sent. Verify by VER-003. [REQ-003]
- **AC-004** — In the candidate the web view holds no pipe to Codex, composes no request to it and writes no record; each exclusion of CLM-002 holds; the candidate's shell is Tauri 2 with a React and Vite web view; and no framework on the product path is a release-candidate version. Verify by VER-004. [REQ-001, REQ-004]

- **AC-006** — A supplier tree that differs from the expected identity in any file, mode or member, a label that differs from the pin, and a generated output of another pin each refuse the start with the differing element named; an unverifiable tree runs only as a labelled unverified development run; an installed build without a matching compiled publisher identity does not execute the supplier as a production supplier; and a pin advance is accompanied by its schema, supplement and recorded-exchange comparison. Verify by VER-009. [REQ-010]

Verify by VER-011. [REQ-006]

## Production and Verification Method — Praxeology

Seams are tested against exchanges recorded once from the stock supplier and replayed; live supplier runs are few and are used only where a fact cannot be shown otherwise. A stand-in supplier process may drive lifecycle and register cases, but a stand-in establishes nothing about the supplier's own behaviour. Every result names the candidate, the pin and the date; a changed pin or interface reopens the checks it touches.

- **VER-001** — Executable check (observes the process tree, the pipe owner and the register on the candidate): start a turn that raises a request, close, hide and reload the window, send an unfamiliar server request, and wait in silence; stop the child deliberately, end it unexpectedly with a descendant alive, and replay a late frame and a late reply of a closed generation; compare the child, the pending entry, the frames written and the reported lifecycle facts with the operating system's process list before and after.
- **VER-002** — Comparison with the supplier's generator output at the pin: regenerate the stable and experimental variants, compare byte for byte with the candidate's types and compare the two variants with the experimental standing the candidate gives each element; read each supplement entry against its cited evidence; replay recorded native, unfamiliar and malformed frames, including frames sent before readiness, and compare what receivers get with what was recorded; inspect the frames the boundary wrote for base instructions and notification suppression.
- **VER-003** — Comparison with the supplier's own report: compare the version identity record with the binary's version output and a fresh inventory of the tree, and a delivered plan item with the recorded supplier frame.
- **VER-004** — Judgment by an independent reviewer, plus comparison with each framework's published releases: read the candidate's web view and host code for any pipe, request composition or record write in the web view and for each exclusion of CLM-002; read the candidate's manifests and lockfiles for the shell, web view and build tool and their versions.
- **VER-005** — Comparison with the supplier's published protocol at the pin, plus an executable check on a named local server: replay recorded exchanges, run the provider route against the server, and mark each requirement published, observed or not observed.
- **VER-006** — Executable check (observes the start decision): present trees altered in one file, one mode and one member, a wrong label, a generated output of another pin, an unverifiable tree with and without the development option, and an installed build with and without a matching publisher identity; for a pin advance, inspect the comparison of schema, supplement and recorded exchanges with the prior pin.
- **VER-007** — Judgment by an independent reviewer: trace each act named in CLM-004 and CLM-005 to its owner's code and confirm none is produced here.
- **VER-008** — Executable check (observes reported outcomes against the writes actually made): end a generation with a request unanswered, with a reply queued and with a reply admitted but unobserved, and withhold a response to a client request.
- **VER-009** — Comparison with the frames written to the supplier: for one turn, compare the handed-over guidance identities with digests of the recorded written frames, the reported model and destination with the recorded supplier frames, and each settlement's origin with the answer the examiner gave through the interface, the App rule configured for the case, or a request Codex resolved itself.
- **VER-010** — Comparison with the pin's generated output: enumerate its item kinds, server requests and client methods and check each against the account.
- **VER-011** — Comparison with the supplier's published release list: compare the candidate's pin with the supplier's releases at the candidate's build date and with the version-advance check result of each newer release, and read the results of VER-001 through VER-010 for that candidate and pin.

## Governing Values and Decisions — Axiology

- **AX-001** — Maintainability first, then functionality, then local models and privacy. Better means fewer App-maintained elements to touch when the pin advances — supplement entries and supplier-specific code outside the generated types — and never by dropping a native item or field from what receivers get, or by modifying the supplier.
- **AX-002** — What the App runs is what it says it runs. Better means more of the supplier distribution checked before it is executed and fewer starts that end unverifiable, and never by weakening verification to a version label or by letting a development run pass as the pinned supplier.
- **AX-003** — Only what was observed is reported. Better means fewer outcomes left unknown at a close or an exit, and never by inferring a receipt, an acknowledgment or an answer that was not observed.
