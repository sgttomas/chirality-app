# DEL-01-05 — Native ChatGPT sign-in and oMLX/local-provider access

## Purpose and Objective Traceability

This deliverable gives the person their model. Through Codex's own account and provider methods the App lets the person sign in with their ChatGPT account, use a local model server, keep both configured together, and choose between them for each conversation, with nothing chosen for them. In 4.0.0 the App offers the ChatGPT account only (see For 4.0.0). Credentials stay with Codex. The App also shows and records what its Codex connects to at start-up, and turns off what Codex's settings allow.

It is the BACKEND_FEATURE_SLICE `DEL-01-05` of PKG-01 in the accepted decomposition, serving OBJ-002 (user-selectable Codex access) and OBJ-004 (qualified provider interfaces and the local-server requirements a host receives).

## Deliverable Definition — Ontology

- **OUT-001** — Receiving of Codex's native ChatGPT sign-in, the account status shown, and the Codex account reported for the person-identity element of captured acts. Supports SOW-009, SOW-010; OBJ-002.
- **OUT-002** — Local model server access and its settings, the per-conversation choice of access and model, the start-up traffic settings, and the network view and its record. Supports SOW-011, SOW-012; OBJ-002.
- **OUT-003** — The App-owned Codex homes: the account home, the dedicated local home and the probe home, with what each shares with the person's own Codex and what each keeps to itself. Supports SOW-132, SOW-133; OBJ-002.
- **OUT-004** — Qualification of the account, provider and local-server interfaces on an identified candidate, the substitution of a compliant local server, and the local-server capability requirements handed to the host loop contract. Supports SOW-149, SOW-150; OBJ-002, OBJ-004.

Terms:

- **App-owned Codex home.** A Codex home directory the App creates for its own Codex, with a stable identity that is neither a credential nor a path. Every conversation belongs to exactly one home.
- **Account home.** The home for ChatGPT account conversations. It shares the person's Codex settings and MCP servers through links to the person's own files and keeps its own sign-in, held by Codex. Analytics is off in it as REQ-010 requires. The only additional departures from the person's Codex settings are the default provider and the permission level: the App starts this home's Codex with `model_provider="openai"` as a session setting, whatever default provider the person's settings name, because the pinned Codex runs a conversation only on the provider its process was started with; and approval, sandbox and review routing follow the permission level the person sets in the App (PRD V4-AUT-06). The person's MCP servers and every other setting remain in effect, the person's own Codex files are not written, and the account view says so when their settings name another default. Where first-use setup creates new App-owned settings, they are empty, so what neither they nor the permission level set, including where a sign-in is kept, is Codex's own default; before the person confirms, the App says what Codex can read by default and where the sign-in will be kept, and the person can read where Codex reports it keeps the sign-in before signing in (REQ-011). Where the person's own settings give the built-in provider another address, the account home's requests, with its sign-in, go there, as their own Codex would send them; the App neither adds nor removes that. A development build can pass Codex a same-machine address for its built-in provider through a startup input the release configuration does not read; where it does, that address takes the place of any the person's settings give. If a pinned Codex cannot share settings this way, the App keeps its own settings and says so.
- **Dedicated local home.** The home for conversations with a local model server. Its configuration is the App's own and nonsecret: provider `chirality-omlx` over the Responses interface, at the server address and with the model name the person sets in the local model settings. It shares nothing with the account home and holds the server's key in Codex custody. The App also starts this home's Codex with API-key model discovery off (`features.api_key_model_discovery=false`), so Codex makes no model catalogue request with the key, and with `cli_auth_credentials_store="file"`, so Codex keeps the key in that home's own file rather than in the person's keychain.
- **Local model settings.** The server address and the model name, set by the person in the App and kept in the dedicated local home's configuration, which only the App writes. The address is on the same machine (a loopback address). Until the person sets them the address offered is `http://127.0.0.1:8000/v1` and no model is named. The server requires a key; the key is never one of these settings.
- **Probe home.** A home used only when the supplier binary is asked for its version label. It is never an account home and hosts no conversation.
- **Access entry.** One way a conversation can reach a model: the ChatGPT account, in the account home, or the local model server, in the dedicated local home.
- **Selection state.** For a conversation: no model selected, a model and provider selected, and the person's last explicit choice for the project.
- **Start-up traffic.** Connections the App's Codex makes when it starts or starts a thread, before any turn the person sends.

Boundary:

- **CLM-001** — Codex owns its account methods and every credential. The App owns the receiving integration. The App holds no token; a key the person enters passes once through a native secure field to Codex and is never stored, logged, written to configuration, a command line or the child's environment, or shown to the web view. External-token login is not offered.
- **CLM-002** — Standalone OpenAI API-key access is omitted from this increment. Native plumbing and a key home saved by an earlier build are kept, neither offered nor deleted. Bringing it back is an owner scope decision.
- **CLM-003** — `DEL-01-01` hosts the Codex child for each home, carries the account methods and the provider selection, qualifies the embedding protocol and states what Codex requires of a provider. `DEL-01-04` presents the conversation start, where the selection state appears, and captures acts. `DEL-01-02` lists live work before an operation that would end it.
- **CLM-004** — `DEL-05-01` owns the host loop and its model contract; the external host owner builds the host's loop and enforces its endpoint and key boundary. A host's model interface is Chat Completions with tool calls; the App's provider interface is whatever Codex requires at the pin. Qualifying one says nothing about the other.

## Completion and Reliance Basis — Epistemology

- **REQ-001** — The App offers ChatGPT account sign-in through the selected Codex-native flow and starts the intended account-backed conversation with the credential held by Codex. The account is shown as Codex reports it, with pending, failed, absent and not-yet-read kept distinct, and no part of a key, token, sign-in address or code is shown outside a pending sign-in. The Codex account of the home that runs a conversation is reported as the reported email or "ChatGPT account (no email reported)"; the plan type is shown and not recorded.
- **REQ-002** — The App presents no standalone OpenAI API-key entry and makes no qualification claim for one. A key home saved earlier is left in place.
- **REQ-003** — The App's local model access entry uses the dedicated local home, where the local model server is reached as a Codex provider over the supplier's provider interface, at the address and with the model name the person sets in the local model settings. The App offers a local model server in no other way; an address the person's own Codex settings give the built-in provider stays in effect in the account home like their other settings. The server's key is entered in a native secure field and held by Codex. A configured key is shown as configured, not verified, until an actual conversation uses it. Changing the address removes a saved key through Codex's own sign-out before the new address is used, so a key entered for one server is not sent to another, except when restoring the address the App recorded for the saved key; that restoration keeps the key and does not require a prepared connection; if the sign-out cannot be established, the settings are not changed. The App keeps its own record of the address a saved key was entered for, and where that address cannot be established to be the one now set, nothing that could send the key starts. A Codex process is started in the dedicated local home only when no earlier one for that home is still running, and an address is not changed in a Codex session in which a key entry was begun, so that a key written late cannot fall under another address's record. The files of the dedicated local home are changed only by the App and its Codex; this safeguard does not survive their removal or replacement from outside while an earlier Codex of that home is running. An existing local conversation retains Codex's recorded provider and model. It continues only when the model name in the current local model settings matches its recorded model, using the server address the person currently set; otherwise the App identifies it as started under earlier settings and sends no turn. The App keeps no separate per-conversation record of the local settings at its start; continuation uses Codex's recorded model and the current local model settings. Before the person confirms an address change, the App states that conversations whose recorded model matches the model name in the proposed local model settings will continue with the server at the new address, and that the saved key will be removed and must be entered again, or, when the address the App recorded for the saved key is being restored, that the key is kept. A local provider defined in the person's own Codex settings is not offered for a conversation: the App says that it cannot run one in the account home and where local servers are set up.

No access entry or model is applied to a new conversation until the person chooses; the last explicit choice for the project may be offered, shown as such, and is never applied silently. A conversation's selection state is reported to the views and controls that depend on it. A conversation that cannot start for want of a model reads "not started — no model selected", and a workflow run "run not started — no model selected".

## Production and Verification Method — Praxeology

Account and provider methods are used as the pin publishes them, and what the App reads from Codex is read at run time, not assumed from the version. Recorded exchanges show the seams; sign-in, a local conversation and substitution each need the actual candidate, an actual account or server, and the person's own act. No credential is reproduced in any evidence.

- **VER-001** — Comparison with Codex's own account report and an examiner's observation: the person signs in on the candidate, with a pending, a failed and an absent sign-in and an account not yet read each shown; the account status and the account reported for a conversation are compared with what Codex reports, with and without an email; a conversation is run; and the App's files, logs and records are searched for the credential and for a plan type.
- **VER-002** — Executable check (observes the offered entries and the bytes of an earlier key home before and after a run).
- **VER-003** — Comparison with the local servers' own request logs and Codex's own account reports: set the server in the local model settings, observe how the route is shown before first use, enter the key natively, run a conversation, and search App-written files and the web view's messages for the key. Starting with a saved key, change the address, observing the notice before confirming and that cancelling changes nothing, and establish from Codex's account reports and both servers' request logs that, for an ordinary address change, the saved key is removed before any new or existing conversation uses the new address. Separately, restore the recorded address without a prepared connection and establish that the saved key is kept. Exercise a change during a running turn, a failed and an unconfirmed sign-out, a relaunch between change and use, two successive address changes, an address changed in the home's configuration outside the App while a key is saved, the restoration of the recorded address from that state, the App's record of the address removed after the connection was prepared and before the next message, an App ended while a key entry was in progress followed by a reopening, and an address change attempted in the Codex session in which a key was entered; compare the saved settings before and after each unsuccessful change; and use Codex's own reports and the servers' independent observations to establish the destination of each request and whether a former server's key arrived. Examine continuation with a matching and a different model name, and attempt an address that is not on the same machine. Read the access entries offered with a local provider defined in the person's Codex settings. No credential is reproduced in the evidence.
- **VER-004** — Comparison with the provider Codex reports for each conversation, witnessed by an examiner: run the scenario of EXAMINATION V4-EXM-12, start a new conversation with and without a last choice, attempt to start with no model, and read the reported selection state of each conversation.
- **VER-005** — Comparison with Codex's own configuration and account reads in each home: change a setting in the person's Codex and read it in the account home; name a local provider as the default in the person's Codex settings, read the provider Codex reports in the account home and the account view's notice, run a ChatGPT account conversation there and compare the person's files before and after; sign in and out on each side; read the dedicated local home; start the App, relaunch it and read each home's identity and each conversation's home before and after; read the probe home after a version probe. For the environment check, set every name on the removal list applicable to the path in the App's environment, launch a stand-in supplier through the host's ordinary and successor label-probe and app-server start paths, and compare each started process's own environment with that list and the app-server configuration identity.
- **VER-007** — Comparison with the supplier's published protocol at the pin: replay recorded account and provider exchanges and read the qualification against the exchanges and the candidate's observed results.
- **VER-008** — Comparison with the substitute server's own request log: set a second compliant server in the local model settings and run a conversation.
- **VER-009** — Judgment by an independent reviewer: read the handoff against the qualification evidence and the interface split of ARCHITECTURE §6.
- **VER-010** — Judgment by an independent reviewer: trace each act of REQ-009 to its owner's code.
- **VER-011** — Comparison with connections observed outside the App: start the App's Codex in each home with the person's plugin setting on and off, compare an operating-system level observation of its connections with the network view and the record, and compare the settings listed with the arguments the App started its Codex with.

## Governing Values and Decisions — Axiology

- **AX-001** — The person chooses the model and Codex holds the credentials. Better means fewer steps between the person's choice and a running conversation, and never by applying a default, choosing for the person, or bringing a credential into the App's hands.
- **AX-002** — The App's Codex contacts only what the person can see. Better means fewer start-up connections left on and more of them named in the network view, and never by using an unpublished supplier switch, by writing the person's own Codex files, by applying to the App's own Codex process a setting other than those REQ-010 and the home terms name and the App lists, or by describing operation as local-only when a connection remains.
- **AX-003** — A local server counts only when it was seen to work. Better means more of the provider interface observed on a named server, and never by reporting a published capability, a configured key or another server's result as this server's.
