## Distribution identity method: `codex-vendor-tree-v1`

The measured root is the platform vendor directory containing `bin/`, `codex-path/`, `codex-resources/` and `codex-package.json`. Include every descendant, including empty directories. Exclude the enclosing npm/archive container, wrapper, App code, expected-record file, generated protocol references, and runtime homes. Bundle location is resolved and recorded separately; it is not a relative-content digest input. The expected record itself is shipped outside the measured tree and bound to the reviewed App build.

For this selected package shape, only regular files and directories are supported. Reject symbolic links (including root and ancestor substitutions inside the resolved bundle boundary), devices, sockets, FIFOs and other entries. Do not follow or omit them. Reject hard-linked regular files (link count other than one), invalid UTF-8 names, path components `.`/`..`, absolute paths, duplicate paths and paths containing backslash, CR, LF or NUL. Names are case-sensitive exact bytes with `/` separators; perform no Unicode normalization or case folding. Reject any expected inventory that cannot be represented uniquely on the actual target filesystem. These restrictions deliberately bound this method; a future supplier package needing other entries requires reviewed method evolution, not silent exclusion.

Each regular-file entry contains relative path, type `file`, SHA-256 of its exact bytes, size in bytes and POSIX permission bits (`st_mode & 07777`). Each directory entry contains path, type `dir` and the same permission-bit field. Record the root directory as path `.` for mode comparison only; it is exempt from the descendant-component rule and never enters the file manifest. Ownership, timestamps, inode numbers and extended attributes are excluded from content equality; signatures embedded in files remain covered by file bytes. Signature validity, quarantine and entitlements remain separately evidenced PKG checks.

Compute the PKG §5.2 compatible manifest by sorting regular-file paths by UTF-8 bytes and hashing concatenated UTF-8 lines `<lowercase 64-hex SHA-256>  <relative path>\n`, exactly two spaces and one LF per entry including the final LF. No header or root prefix. Record algorithm `sha-256`, method `codex-vendor-tree-v1`, manifest and the entire inventory. Equality requires matching method, exact complete path/type sets, directory and root modes, and every file's mode, size and digest. The file manifest alone never establishes tree equality. The digest of the expected-record artifact binds the inventory as well as its file manifest; never identify the complete record by the file manifest alone.

## Expected-record provenance and bounded qualification

An expected record is an independently reviewed supplier-reference artifact produced by DEL-01-01, not a caller assertion or a runtime observation promoted in place. Required elements: schema/method version; supplier pin and platform; official archive source locator and archive digest with actual acquisition authorization/custody reference; extraction procedure and source-subtree locator; full inventory and manifest; launcher convention; maintained generated-output reference identity (pin, kind/variant, formatter policy, manifest); qualification evidence references with exact artifact digests; author, independent reviewer, reviewed revision and recorded technical adoption by the App implementation owner through HELP_HUMAN. A field reading `qualified: true` is insufficient.

To establish this bounded supplier reference, obtain separately authorized evidence of the archive/extraction chain, recompute full inventory using the selected method, establish observed label on that tree under isolated H-probe, join the selected pin to the maintained generation provenance and passed version-advance check, and independently verify those bindings and the adopted method. Record exactly which checks and which supplier tree were reviewed. The current 0.160.0 historical manifest and A-IN observation are inputs only; unresolved acquisition, generation-source correspondence or qualification evidence prevents minting the expected record. Reuse earlier evidence only after verifying its subject and scope; no automatic replay or execution is authorized here.

This supplier-reference qualification establishes the expected comparison basis. It does not qualify the App candidate, supplier behaviors outside those checks, signing/notary arrangement, access modes, or joined journeys. A source App revision/build recipe records which reference is selected; final build identity binds its packaged expected-record bytes. Final package identity is established later and need not be embedded back into the record, avoiding a self-referential hash. FP-2/W-4 consumes the already qualified reference and observes the actual package; it is not a prerequisite for creating that reference. No current record is asserted to satisfy this procedure.

## Launcher and configuration

Production resolves the resource root using the native bundle resolver, selects only its measured `bin/codex`, and prepends the same root's `codex-path` to PATH for both label probe and server. Before constructing PATH, reject a resolved `codex-path` prefix containing `:` or otherwise unrepresentable as one PATH entry; refuse that bundle location rather than silently searching different directories. Prepend only a representable prefix and preserve the inherited PATH remainder exactly, including its existing empty-entry semantics. It does not execute the npm wrapper or add its managed-package variables. Existing inherited wrapper variables must not silently alter this convention: remove `CODEX_MANAGED_PACKAGE_ROOT` and `CODEX_MANAGED_BY_NPM` for this direct-vendor mode and record those removals. Preserve credential-variable removal and all applicable ACCESS/home/K-12 behavior. Probe and account homes remain distinct and outside the tree. A development override remains explicitly typed and cannot select the production root or expected qualification reference.

Record resolved root, resolved executable, relative executable, working directory, argument vector, PATH prefix and remaining PATH provenance, App-supplied nonsecret configuration, removed environment variable names, home identities/link states and K-12 flags. Distinguish no npm-wrapper additions from actual App additions. Never serialize ambient environment wholesale, credential values, authentication files, or secret arguments. Redact secrets while retaining the nonsecret identity/provenance required by HOSTING; inherited configuration is not falsely labeled App-supplied.

## Verifier obligations and standing

Before executing the label probe, validate the expected record's schema and trusted build binding, traverse the complete actual tree without following links and compare all available expected values; known mismatch refuses without probe execution. Missing trustworthy expectation is `unverifiable`, never equality. Explicit LT-24 may permit a development probe after safe enumeration with no known mismatch, but does not supply a missing expected reference. Check actual label against the declared pin and maintained generated-output identity, preserving all three HOSTING §7.2 conditions. Revalidate the complete tree immediately before spawning the server. A known mismatch takes precedence over missing evidence and over LT-24.

Use descriptor-relative no-follow traversal/opening, pre/post file metadata and full-inventory checks; reject unstable reads, replaced directories and root changes. Reading by pathname after lstat is insufficient. All detected races refuse this start, with an explicit reason; they cannot be waived by development mode. Report the residual check-to-exec race honestly: filesystem observation cannot prove future immutability against concurrent hostile same-user mutation. Production assumes a trusted, stable installed bundle and parent path; record that custody assumption. A detected violation refuses, and a context unable to establish stable custody cannot claim `verified`. No permanent verified cache survives changed root, package/build/reference identity or generation. Handshake userAgent remains a consistency check only. An inability to read the tree is not a match.

Record expected-reference digest, observed inventory and manifest, generated identity, label, launcher/configuration identity, checks/time/generation, outcome and limits. LT-04 requires actual three-part verification. LT-24 retains existing unverified-development announcement/diagnostics/version wording and never overrides contradiction or satisfies FP-2/W-4.


## Representation and migration

`hosting.distribution-inventory.schema.json` defines the pure inventory value for method `codex-vendor-tree-v1`; `prototype/distribution_identity/` provides offline value checks and synthetic fixtures. It does not scan a filesystem, validate provenance or qualify a reference. The schema requires exact root and descendant entries; the semantic checker additionally checks uniqueness, parent directories, manifest correspondence and comparison. Actual filesystem representability, link counts, traversal stability and trusted custody require the later runtime verifier.

The existing lifecycle schema has closed versionIdentity, distribution-item and launcherRecord shapes. A versioned lifecycle successor must support an immutable verification-artifact reference and SHA-256 of its exact bytes. That artifact must carry the complete observed inventory, qualified expected-reference binding and launcher/configuration record specified here. Update lifecycle producers, maintained consumers and fixtures atomically. The existing PKG v0.2 schema likewise lacks complete inventories; a versioned successor must bind published and packaged inventories and their exact artifact digests to the qualified reference. Neither successor nor the full expected/observed qualification-record schema is delivered by this text amendment; those are explicit propagation gaps before verified production use. Do not insert unsupported fields in old records or treat a legacy pass as a new-method pass.

The qualified reference and observed record must be digest-checked before reliance. A resolvable path without the exact-byte digest is insufficient. No consumer may reconstruct JSON under a different serialization and call it the originally bound artifact. Unknown schema versions fail closed for new-method reliance; historical records remain inspectable at their original standing.
