# Current PROJECT/SOFTWARE amendment closure

Use this read-only profile when the accepted amendment selects current
`ScopeOfWork.md` and `deliverable.yaml` localities. DOMAIN and explicitly
adopted legacy lifecycle projects retain the other contract/method. Old files'
presence does not select them. TASK returns findings to the implementation owner;
it does not repair source, amend decisions or declare acceptance/release.

## Inputs and subject

Read the identified accepted amendment, its exact group-2 action/write boundary,
group-3 decision, current applied source, propagation dispositions and relevant
checks. For the current scope-change profile, these may be a committed amendment
and actual review record rather than the retained multi-file snapshot/register
layout. Bind each decision to the reviewed revision/content; a mutable proposal
is not accepted authority. An absent or contradictory decision basis prevents
closure and is returned with its actual uncertainty.

Audit the affected action set and intended uses, not the whole project. Follow
necessary consumer references beyond the directly edited localities: use native
reverse-needs/impact observations and named interfaces to find affected uses,
then inspect their conditions. Changed-file or changed-package coverage alone
is not consequence coverage. State the selected coverage and unknown bindings;
derived links do not prove that every consumer was declared. Preserve
source/candidate identity for each finding.

## Examine actions and propagation

- **ADD:** after incremental current setup, confirm the accepted entity/parent,
  substantive `ScopeOfWork.md` and valid `deliverable.yaml`. At amendment
  acceptance before that setup, report the addition as an outstanding setup
  obligation; its accepted deferral explains the missing locality but does not
  establish implementation closure.
- **MODIFY:** compare the actual PRD/decomposition/ScopeOfWork changes with the
  accepted exact revisions, stable IDs and prior contract basis. Inspect affected
  needs/pointers where their meaning changed. Unchanged declarations
  need no cosmetic edit.
- **REMOVE/RECLASSIFY/MERGE/SPLIT:** check accepted disposition, source retention,
  reserved IDs, all affected children/mappings and actual consumer conditions.
  Do not infer deletion, automatic need removal or a lifecycle transition.
- **Derivatives and other propagation:** verify each selected rerun against its
  actual changed inputs and intended use. Distinguish implemented, pending,
  explicitly deferred or superseded work, citing the deciding basis. A handoff
  does not prove that its receiving work occurred.

Use `zsh tools/validation/check_min_viable_fileset.sh --current <DEL-path> <DEL-ID>`
and `python3 tools/scope_of_work/validate_scope_of_work.py <ScopeOfWork-path> --json`
where relevant. The structural helper requires zsh/Python/PyYAML; contract format
validation is distinct from substantive examination. Native
`python3 -m tools.deliverables --project <project> check` and relevant queries
require Git/HEAD and Python/PyYAML. They observe declarations/references; inspect
the actual consumer conditions and evidence before any suitability finding.
If a tool is unavailable, read the affected sources directly and state the
unperformed check. Do not substitute a successful legacy structure audit for
these claims or manufacture `_STATUS.md`, `_CONTEXT.md` or other control files.

## Return

Return an action-by-action finding, evidence basis, coverage, unresolved conditions
and useful next action in the caller's selected output/review location. Report
amendment acceptance separately from actual implementation and propagation
closure. Where work is explicitly deferred, identify what is closed and what
remains; never report full closure while a required obligation is unestablished.
Severity and uncertainty are distinct. A source mismatch, missing evidence and
an intentionally pending consequence do not warrant the same finding.

Use existing governing/review material; no separate run directory, input manifest
or handoff file is required unless the selected consumer needs it. Do not rewrite
previous audit evidence. A retained record identifies the exact examined inputs
and limitations. Neither the report nor a passing validator authorizes source
changes, adoption, acceptance or release.
