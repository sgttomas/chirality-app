# Package activation and production

WORKING_ITEMS applies this method to a package-based undertaking; its general role also accepts other bounded undertakings.

1. Resolve PackageID, package path, selected deliverables, accepted source/decomposition basis, objective, completion criteria, authorization, dependencies, and write ownership. A single-deliverable undertaking selects that deliverable within its parent package.
2. Inspect the selected ScopeOfWork, needs, the code they name, relevant source evidence and Git state. Read historical control or recovery records only where the project actually adopts or needs them. Resolve each PROJECT/SOFTWARE representation as LEGACY_FOUR_DOC, SOW_V1, MIGRATION_DUAL, AMBIGUOUS, or INVALID. MIGRATION_DUAL requires the exact isolated conversion grant; ambiguous/invalid state remains blocked for dependent production. Do not require a lifecycle file for current SOW_V1 work.
3. Use `construct-local-work-graph` to derive the selected undertaking's work graph from consumer-local `deliverable.yaml` needs and scope. Include objectives, actual input/use conditions, read context, write ownership, integration owner, expected returns and concurrency. Assess each needed condition from evidence; retain source unknowns and reciprocal/technical holds. Record the descriptive posture and revise the plan as actual conditions change; a saved view does not become dependency authority. Where the decomposition names an objective check, a thin end-to-end path or a coupled core that touches the selected deliverables, carry it into the plan with its carrier.
4. Assign disjoint work whose actual input conditions permit the selected activity to TASK or an authorized ephemeral Type 2 instance. Each brief names its context, tools, writes, outputs, acceptance and the check that will be applied to the return, dependencies, and return path. Serialize overlapping writes. When a check is written for a criterion in a class the project's standing instructions single out for independent scrutiny, someone who did not write the check asks whether it could pass while the criterion is unmet.
5. Record, relay, amend, hold, replan, escalate, or route updates through the parent. Version amendments and preserve claim status and evidence. A direct-human manager presents cross-package decisions to the human.
6. Before integration, reconcile the concrete result and verification with affected ScopeOfWork and dependency conditions/pointers in the same change. The implementation owner carries this into every brief; TASKs report their slice's effects, and the integration owner checks the combined result. Revise what changed and preserve unchanged declarations. Use `bounded-reconciliation`; a no-edit finding needs only a brief return/PR statement. Missing required behavior remains unfinished work.
7. Verify the changed result, relevant consuming paths and permitted write scope.
Return usable outputs, checks and remaining conditions or reserved choices in the
actual review/change record. Follow
the owning project's Git conventions; integration is not owner acceptance or
release. Formal scope changes and explicitly adopted lifecycle decisions retain
their real authority. This method does not require routine receipts or a handoff
chain, and it does not itself require Git.

For representation conversion, load workflows/scope-of-work/resources/representation-migration.md. Each child brief names affected OUT-*, REQ-*, AC-*, VER-* IDs or the frozen mapping basis and exact migration authority.
